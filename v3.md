# relay-go Lua API (v3)

| | |
|---|---|
| **Status** | Draft — for iteration |

| **Applies to** | the planner Lua surface (`relay.lua`) and the agent Lua surface (`scripts/*.lua`) |

## Abstract

v2 made every operation name its executor, its identity, and its operands, and
made the safe form of every call the *only* form. That killed the implicit
behavior v1 had — but it taxed the common case to pay for the rare one. A
deploy to one barebone Linux box reads six layers of jail/executor/privilege
machinery it never uses, repeats `{ as_user = "root" }` on almost every line,
and cannot run a shell command without opting into a discouraged escape hatch.

v3 keeps everything v2 got right (typed ops, execute-as-you-go, verified
declarations, deterministic modules, LuaLS stubs) and inverts the default:
**the simple path is the default; sophistication is opt-in and never taxes the
simple case.** Concretely:

- `ctx` **is** the executor. `ctx.run(...)`, `ctx.fs.write(...)`,
  `ctx.http.check(...)`. No `ctx.target` for the one-host case.
- **`run` takes a plain string and runs it as a shell command.** The argv
  table remains for safe interpolation. The shell form is not an escape hatch;
  it is the primary form.
- **Privilege is declared once on the host** (`sudo = true`) and inherited by
  every op. `as_user` per op is an override, not a repetition.
- **No deploy model is built in.** relay ships no `app{}`, no `ctx.paths`, no
  release verbs. A release layout (capistrano-style or otherwise) is a *recipe* —
  a plain Lua module over core primitives you can read, copy, and edit (§11.14).
  Per-target data (values that resolve differently on each host) lives in an
  opt-in `vars{}` declaration; without it you use literals.
- **The FreeBSD jail is one optional declaration.** Register no `jail{}` and
  no jail concept exists in your script. Register one and `ctx` binds to the
  jail, `ctx.host` to the machine beneath — exactly as v2, but only then.
- **Platform is auto-detected.** The agent reports it; asserting it via the
  host's `expect` field is opt-in, never a requirement to get started.

The design invariant, stated once and enforced everywhere:

> **Opt-in features don't tax the simple case.** A one-host script with no
> jail, no sudo policy, and no `vars` references *nothing* about jails,
> executors, escalation strategies, release directories, or vars resolution —
> read it and you see a host, a task, and ops. Opt-in declarations
> (`jail{}`, `sudo`/`escalate`, `vars{}`, off-target phases, `finally`)
> introduce a concept a script didn't have; they never appear in a script
> that doesn't use them. If the simple case references machinery it doesn't
> use, the API failed.
>
> This makes **no claim that scaling is additive.** Single-host ↔ group, or
> adding a second target, is config editing — you're changing what a task
> *points at*, so `target` changes. That's a different script, not a leak, and
> not something the API owes you as "additive." The invariant is about
> *absence in the simple case*, not *edits during growth*.

## 1. Introduction

### 1.1 What relay is

A **CLI planner** (`relay`) drives a cross-compiled **agent** (`relay-agent`)
that runs typed operations on target hosts over a protobuf protocol. You
describe deploys in **Lua**; relay turns them into native agent ops — argv
execution, checksum-verified file writes, atomic symlink swaps, in-process
HTTP probes — instead of shell-over-SSH. Go was chosen so the agent
cross-compiles to any target arch in one command.

```
your machine                         target host (SSH, or local stdio)
  relay (planner)                       relay-agent (agent)
   │  read relay.lua, register topology
   │  ssh user@host ~/.relay/bin/relay-agent
   │  ── Handshake ──────────────────────▶  report user / uid / platform /
   │                                        protocol_version (§4.1)
   │  ── Request: typed op ──────────────▶  run it natively (os.Symlink, …)
   │  ◀──── Stream: stdout/stderr ────────   (live, as it runs)
   │  ◀────────── Response: result
```

The user's mental model, which v3 treats as the spec's north star, is four
steps: **define the target → reach it → give it a command → get the output.**

### 1.2 What went wrong in v2

v2 over-corrected on explicitness: it taxed the simple case to pay for the
rare one — repeating identity on every line, gating the obvious shell command
behind a discouraged escape hatch, picking a jail-serving executor on every
op, and baking one release model (`app{}`) into core. v3 inverts the default.
See §1.3 for the concrete changes and Appendix B for what is preserved.

### 1.3 What v3 changes

A table of the user-visible changes; rationale follows each in its section.

| Area | v2 | v3 |
|---|---|---|
| Default executor | `ctx.target.run(...)` | `ctx.run(...)` (`ctx.target` removed) |
| `run` command form | table primary; string needs `{shell=true}` | **string primary (shell); table = no-shell** |
| Privilege | `{ as_user = "root" }` on every op | **`sudo = true` on host; ops inherit** |
| Release layout | `app{}`/`ctx.paths`/`ctx.release.*` baked into core | **none in core; capistrano is a recipe over primitives (§11.14)** |
| Packages | `pkg.ensure`/`pkg.installed` in core | **none in core; pkg is a recipe over `run` + `ctx.self.platform.package_manager` (§11.15)** |
| `git` | `git.clone`/`sync`/`head` as a core op module | **none in core; git is a recipe over `run` (§11.16); `run { read_only = true }` makes its probes real reads** |
| Services | `service.*` as a core op module, one verb set over systemd/rc.d | **none in core; `systemd`/`rcd` recipes over `run` + a `service` dispatcher, because the two inits disagree (§11.17)** |
| `platform` (declared) | `host{ expect = {...} }` | **auto-detected; `expect` is opt-in assertion** |
| Users | `ssh_user`, `host.deploy_user`, `as_user` | **`user` (connect+default act), `as` per-op override** |
| Jail | always in scope via executor choice | **fully opt-in; absent ⇒ absent from the script** |
| Jail `fs` | mountpoint translation only, with `ctx.fs_root()` in script text | **`fs_access = "attach"` (default: runs inside the jail, kernel-confined, jail's passwd) or `"mountpoint"` (host-side, translated — the unprivileged mode); §10.2** |
| Jail lookup | `jname` (the `jls` name) | **`match` — a selector over the `jls` row (`jid`/`name`/`hostname`/`path`), table or predicate; §10.2** |
| Target handle | name strings only | **declarations return refs; `ctx.self` = current target scope** |
| Ad-hoc command | none (must write a task) | **`relay exec <target> -- <cmd>`** |
| Off-target work | inline `ctx.localhost.run(...)` inside a phase | **pinned phase (`target = "localhost"`/host) in the same list; `finally` cleanup hook (§6.2)** |

Everything else v2 established — typed ops, execute-as-you-go, verified
declarations, deterministic `require`, LuaLS stubs, the agent-Lua boundary —
is preserved (Appendix B).

## 2. Goals and non-goals

**Goals**

- A deploy to one barebone host is readable in under a screen and writable in
  under a minute, with no mention of jails, executors, escalation strategies,
  or release directories.
- Every sophisticated feature (jails, multi-host, sudoers, per-target data,
  tagged paths, agent Lua) is reachable by *adding* to a working script, not
  by restructuring it.
- The quick form of any operation is never discouraged, deprecated, or gated
  behind a flag. It is the documented primary form.
- Security-relevant facts (who an op runs as, what gets escalated) remain
  visible — declared once at the host, shown in every op's log line, overridable
  per op — without per-line repetition.

**Non-goals**

- Removing the sophisticated features. v3 keeps jails, the worker/sudoers
  model, tagged paths, and agent Lua. They move to opt-in sections, not the
  cutting room.
- A new protocol or a new agent architecture. v3 is a Lua-surface redesign;
  the protobuf ops and the agent's native implementations are reused.
- Backward compatibility with v2. v3 breaks the API; `relay init` regenerates
  stubs and the [migration table](#14-migration-v2--v3) covers the mechanical
  rewrite.

## 3. Design principles

1. **The simple path is the default path.** The form a new user reaches for is
   the form that works, is documented first, and is not flagged as an escape
   hatch. The safe/explicit/powerful form is one step away, never a prerequisite.

2. **Opt-in is invisible until used.** A feature a script doesn't use is
   absent from it — no `jail` in a non-jail deploy, no executor name in a
   one-host task, no escalation detail on an unprivileged host. This is the
   [design invariant](#abstract); every API decision is checked against it.

3. **Declare once, inherit.** A fact true of every operation on a host
   (identity, platform, escalation) is declared on the host and inherited. A
   per-call site may override; it does not repeat.

4. **Typed ops over shell — but shell is first-class.** Native agent ops are
   preferred where they add real value (idempotency, atomicity, checksums). A
   plain shell command is a normal, supported call, not a confession of
   failure. Use the argv table when interpolating untrusted data; use a string
   for literals and pipelines.

5. **One obvious way for the obvious thing.** Running a command has two forms
   by purpose (shell string vs. argv table), not three by ceremony. Each op
   has one calling convention.

6. **Progressive disclosure.** The first screen of documentation covers the
   80% case. Escalation matrices, jail dispatch, tagged paths, and agent Lua
   live in [§10](#10-advanced-opt-in), reached when a script needs them.

7. **The embedded language should behave like itself — or say loudly that it
   doesn't.** go-lua lacks Lua's pattern engine and octal literals; v3 does
   not hide this but ships typed helpers (`relay.split`, `relay.replace`,
   `relay.render`, `relay.env`, octal *string* modes) so the gaps never bite
   silently (Appendix A). Each helper is a *narrow* replacement, not a
   restored language: `render` is `{{.key}}` substitution, not
   `text/template`; `replace` is plain text, not `gsub`.

8. **Mechanics stay hidden; facts stay visible.** The agent owns `jls`,
   `jexec`, mountpoint translation, init-system dispatch. What is visible in a
   script is *that* an op targets the jail — not *how* the agent reaches it.
   Who an op runs as is visible (host default + log line + per-op override),
   not repeated.

## 4. Architecture

### 4.1 Two binaries, one protocol

`relay` (planner) reads `relay.lua`, connects to targets, and dispatches typed
ops. `relay-agent` (agent) receives ops and executes them natively in Go. They
speak the protobuf protocol in `relay-protocol/`. The two-binary split and the
wire shape are unchanged from v2; the version handshake below is the one
addition.

**Connect handshake.** The first frame after the ssh/stdio transport is up is
the agent's `Hello`, carrying the platform report (`os`/`arch`/`distro`/
`version`/`init`/`package_manager` — used by `expect` and `ctx.self.platform`,
§6/§10.5), the
connection identity (`user`/`uid`/`home`), and two version fields:

`home` is the connection user's home directory as `getpwuid` reports it — the
source `ctx.self.home` and every target-side `~/` expansion use (§5.1, §6).
It rides the handshake because its first consumers run *at connect*, before a
script could ask for it: `host.lock` resolving its default path (and a `~/`
lock path), and the workdir ladder's per-target default. Fetching it later
would mean an extra round-trip to answer a question the agent has already
answered. An op with a non-default `as` resolves *that* identity's home on the
target when it needs it; the handshake carries the connection user's, which is
what the connect-time consumers ask about.

A `Hello` field the planner **depends on** bumps `protocol_version`, unlike the
optional fields covered by the bump discipline below: an agent that predates
`home` sends nothing, and "the receiver can ignore an unknown field" does not
help a receiver that needs the value. The gate then does the right thing —
`planner > agent` is refused at connect with the reinstall message, instead of
a lock path silently resolving against an empty string.

- `protocol_version` — a monotonic `uint32` for wire compatibility (below).
- `agent_version` — the relay SemVer string this agent was built from;
  diagnostics only (`relay doctor`, logs), never consulted for compatibility.

**Version skew.** relay bundles its agent and ships it with
`relay agent install` (§9), so a matched planner/agent pair is the norm. Skew
arises only when a host pins an older agent, or two operators run different
relay versions against shared hosts. The rule is conservative and one-sided:

> A deploy is allowed only when **`planner.protocol_version ≤ agent.protocol_version`**.

The dangerous direction — planner newer than agent — is **rejected at
connect**, before any op:

> `agent on web01 speaks protocol v14; this relay speaks v17 and may send an op it doesn't recognize. Reinstall: relay agent install web01.`

The other direction is allowed with no warning: a newer agent serves every op
an older planner can emit.

**Bump discipline.** `protocol_version` bumps on any change to the set of op
kinds the agent must recognize — a new op kind (e.g. `fs.hash`) bumps, since a
newer planner may emit it at an older agent. Adding an optional field to an
existing message does **not** bump (protobuf ignores unknown optional fields,
so an older agent still serves the op).

**The protocol is additive-only.** Changing the *meaning* of an existing
field or op kind is forbidden — no version bump makes it safe. The gate is
one-sided (`planner ≤ agent`) and `Hello` flows agent→planner, so the agent
never learns the planner's version: a reinterpreted field would let an older
planner emit the field with old intent at a newer agent, which would apply
the new semantics — the *allowed* skew direction is exactly the unguarded
one. Express a semantic change as a new field or a new op kind; retire the
old one only after a deprecation horizon, served with its old semantics until
removal. (Removal has the same unguarded direction — an old planner emitting
a dropped op gets the typed `op`-kind error below, not silent misbehavior;
the horizon is what makes it rare.) The
alternative — the planner announces its version and the agent keeps
per-version behavior — buys a compatibility matrix inside the agent that
nothing needs while the protocol is young.

**Unknown op at runtime.** The connect gate makes an unrecognized op
unreachable in normal operation; if one nonetheless arrives, the agent
returns a typed `op`-kind error (§6.1) rather than crashing — the planner
never continues past an op the agent could not serve. `relay doctor` (§9)
flags any `planner > agent` host as "agent out of date."

### 4.2 Two Lua runtimes

| Runtime | Where it lives | Where it runs | Globals |
|---|---|---|---|
| **Planner Lua** | `relay.lua` + `require`d modules | the planner (your machine) | `host`, `vars`, `group`, `jail`, `task`, `relay`; inside a phase, `ctx` |
| **Agent Lua** | `scripts/*.lua` | the agent (the target) | `run`, `fs`, `log`, `json`, `relay`, `args` |

They share syntax and nothing else. A phase ships an agent script with
`ctx.eval_file("scripts/foo.lua")`; data crosses only as the `args` table you
pass in and the value the script `return`s. Agent Lua is
[advanced](#106-agent-lua-eval); most deploys never need it.

### 4.3 Declaration, then execution

A `relay.lua` runs in two moments:

1. **Declaration.** The top-level body runs first and *registers topology* —
   `host{}`, `vars{}`, `group{}`, `jail{}`, `task(...)`. No operations execute.
2. **Execution.** For each target, relay calls each phase's `run(ctx)`
   function. Every `ctx.*` op inside executes immediately against a connection
   opened lazily on first use, streams its output, and **returns its real
   result**.

So branching on a remote command's output is ordinary Lua, at deploy time:

```lua
local r = ctx.run("readlink /var/www/current")
if r.stdout ~= "" then ctx.log.info("active release: " .. r.stdout) end
```

**Four moments, four names.** Neither pass above is a single instant, and "plan
time" is not a synonym for "early". Every check, default, and error in this
document fires at exactly one of the four moments below, and says which:

| Term | When | What belongs there |
|---|---|---|
| **plan time** | the declaration pass, before any connection | topology registers; the CLI resolves the target; checks over what the script *wrote* — target inference, reserved names, nested groups, a relative `workdir`, `jail{ path }` under `"attach"`, literal `env_files` parsed and merged |
| **connect time** | per target, from the handshake to its first op | protocol-version check, platform probe, `expect`, `host.lock` (once per machine per session, so two jails on one jailer share it — §5.1), worker spawn, jail `match`/`path` resolution, and the per-target rungs of the ladders — `workdir`'s `~/` (it needs `ctx.self.home`) and both `function(ctx)` forms |
| **dispatch time** | inside a phase, when a value is used — an op's call site before it reaches the agent, and any `ctx` lookup | checks over what the script *computed* — tagged-path rules, privilege reachability, mode strings, `stdin`×password, `ctx.host` / `ctx.on` / `ctx.vars` lookups |
| **run time** | on the target, after the agent runs the op | only what the target alone can answer: a non-zero exit, a sudoers denial, a missing file |

The line between plan time and dispatch time is **written vs computed**: a
declaration is a literal the parser can read, an op argument is a value a phase
built (from `ctx.vars`, a `run` result, a `..` concatenation) and cannot exist
before that phase runs. So one rule can land at two moments — a relative
`workdir` in a `host{}` is a plan-time error, a bad `mode` on an `fs.write` is
a dispatch-time one.

Dispatch-time checks fire **before the op is sent**, so `--dry-run`
([§4.4](#44-dry-run)) still vets them end-to-end, and `relay validate`
([§9](#9-cli)) catches the subset whose arguments are literal in the source.
Connect time is lazy: a connection opens on a target's first op, so a target no
phase touches is never contacted.

### 4.4 Dry-run

`--dry-run` executes phases but skips mutating ops, logging what *would* have
happened. Read-only ops (`fs.read`, `fs.exists`, `http.check` and any
safe-method `http.request` that is not writing an `out_file`, any `run` marked
`read_only = true`, and every
`onlyif`/`unless` guard, §7.1) still
execute. A skipped op returns a stub so scripts that consume results don't
crash. The
stubs follow one pattern — an **optimistic primary** paired with an **honest
`dry_run = true`** flag:

- mutating `fs` ops → `{ dry_run = true, changed = true }`
- `run` → `{ exit_code = 0, stdout = "", stderr = "", ran = false, dry_run = true, executed = "<wrapped cmd>" }`
- `http.request` with a **non-safe** method (anything but `GET`/`HEAD`/`OPTIONS`), or any `http` call carrying `out_file` — writing a file is a mutation whatever the method — → `{ status = <expect_status, else 200>, body = "", headers = {}, url = <request url>, elapsed = 0, attempts = 0, size = 0, dry_run = true }` with `err = nil` ([§7.3](#73-http))

The optimistic primary (`changed = true`, `exit_code = 0`) lets a script walk
its happy-path cascade, so the dry-run trace shows downstream ops it would
trigger. The cost: a brancher that gates on `exit_code`
(`if r.exit_code ~= 0 then recover end`) takes the success branch under
`--dry-run`, so recovery logic isn't exercised by a dry run. Gate on
`r.ran and r.exit_code ~= 0` (or `not r.dry_run`) when the branch itself
matters. The `dry_run` flag is what a script checks when it cares that nothing
really ran. `ran = false` is definitive (the command provably did not execute);
`changed = true` is a **prediction, not a state-change claim** — relay cannot
know whether a stubbed mutating op would have altered the host, so it assumes
the optimistic case to keep the cascade visible. `executed` is the exact command
relay *would* have run after wrapping — so a dry run shows the real escalation
prefix, resolved argv, and env without dispatching. Op-level checks (privilege,
tagged-path combinations, mode strings) are **dispatch-time**
([§4.3](#43-declaration-then-execution)) — they fire at the call site, before
the op would be sent — so `--dry-run` vets a script end-to-end.

**Four `fs` ops need their own rule, because the generic stub is wrong for
them** ([§7.2](#72-fs)):

- **`fs.lock`** does not acquire and creates no file; it returns a synthetic
  token so the script walks the path it would take holding the lock. It is
  classified a read, but acquiring is both a mutation and a *cross-session*
  side effect: a preview that takes a real exclusive lock can block a real
  deploy or be blocked by one — the race `host.lock`'s own dry-run skip
  ([§5.1](#51-host--the-one-required-declaration)) exists to avoid.
- **`fs.unlock`** accepts a synthetic token and returns `(true, nil)`.
- **`fs.withlock`** runs `fn` **without acquiring**. Skipping `fn` would hide
  every op inside the lock — usually the whole migration — from the trace the
  preview exists to produce.
- **`fs.mktemp`** returns a synthetic path (`<dir>/<prefix>dryrun`, honoring its
  `dir`/`prefix` opts) and creates nothing. The generic mutating-op stub returns
  `{ dry_run = true, changed = true }`, but `mktemp`'s contract is a path string
  that every caller concatenates — the generic stub would crash every dry run
  that uses it.

The optimism above applies here too: `fs.lock` reporting success is the same
trade as a stubbed `run` exiting 0, so a script that bails when the lock is held
takes the happy path under a preview. And a *read* of a path that only a stubbed
op would have created still answers honestly — `fs.mktemp`'s synthetic path does
not exist, so `fs.read` on it returns `(nil, err)`, the same way a stubbed
`run`'s empty `stdout` disappoints a parser. Gate on `dry_run` where the branch
matters.

**A guard runs for real; the command it gates is what gets stubbed.** An
`onlyif` / `unless` guard ([§7.1](#71-run)) executes under `--dry-run`, and its
verdict decides the op's fate. Stubbing the guard would invert it: a stubbed
`run` exits 0, so every `onlyif` would pass and every `unless` would skip, and
the preview of an idempotency-guarded deploy would show precisely the ops the
real deploy skips — the one thing such a preview exists to get right. A guard is
a read by construction (`dpkg -l`, `test -f`), and §7.1 fences its opts so it
cannot be a general command; a guard that mutates is a misuse, the same trade
`read_only = true` makes explicit for probes. So a guarded `run` has two
outcomes under `--dry-run`, and the trace names which one happened:

- guard says *run* → the command is stubbed: `ran = false, dry_run = true`
- guard says *skip* → a real skip, identical to the one the deploy would take:
  `ran = false`, no `dry_run` flag

**Connect-time mechanics are real, even under `--dry-run`.** Dry-run stubs
scripted mutating ops; it does not stub the connection. relay still connects
(for the platform probe), and connect-time work runs for real: a
`via = "worker"` host spawns its root helper (§10.4); a jail target resolves
via `jls`, and a `jail{ path = function ... }` resolver runs for real (§10.2)
— which is why its probes want `read_only = true`, so the preview sees the
actual mountpoint. So `--dry-run` and `relay doctor` can start a root process on the
target — they trace the scripted ops, not the connection setup, and are not
hermetic. (Skipping the worker spawn would leave privileged-op wrapping
untraceable; the honest answer is that connect mechanics are observable.)

## 5. Topology

Every topology declaration — `host{}`, `jail{}`, `vars{}`, `group{}` —
**returns a ref**: a static, read-only handle to what it registered. A ref
carries the declaration's identity fields (normalized) and is accepted
**anywhere a target name is** — `task`'s `target`, `jail`'s `host`, `group`'s
`members`, and `ctx.on(...)`. Strings still work everywhere; refs are opt-in
for typo-safety, rename-safety, and LuaLS completion. Capturing the return is
optional — a one-host script ignores it.

```lua
local prod00 = host({ name = "prod00", hostname = "prod00.example.net", user = "deploy" })
local web    = jail({ name = "web", host = prod00 })          -- ref, not "prod00"

task("deploy", { target = web, phases = { ... } })            -- ref, not "web"
-- ctx.on(prod00).run(...)                                    -- ref, not "prod00"
```

Refs are **identity, not executors** — no `.run`/`.fs`/…; ops still fire only
inside phases via `ctx` (§6). Each target ref also carries a `.kind`
(`"host"` or `"jail"`) so kind branching works without name-guessing.

**Declaration order: name it after you declare it.** A name string inside a
declaration — `group`'s `members`, `jail`'s `host`, a task's `target` — is
resolved **when that declaration registers**, at plan time
([§4.3](#43-declaration-then-execution)), not in a later pass. The thing it
names must already be declared above it:

```lua
host({ name = "web01", ... })
host({ name = "web02", ... })
group({ name = "web", members = { "web01", "web02" } })   -- both exist by now
```

An unresolvable name is a plan-time error naming the field and what is missing
— *"group `web`: no host or jail named `web03`"* — reported at the line that
names it. The reserved `"localhost"` ([§5.1](#51-host--the-one-required-declaration))
is the one string that needs no declaration.

Resolution happens at the **declaration call**, not where the table was built,
so a recipe factory may hold a target name long before the target exists — what
matters is that `task(...)` runs after the `host{}` ([§11.14](#1114-a-deploy-recipe-plain-require)
does exactly this).

This is the order refs already impose (`web01` is nil until `host{}` returns
it), and strings follow it so the two stay interchangeable — the promise one
paragraph up. Resolving strings in a later pass would make them *more*
permissive than refs, and would empty the refs a declaration returns:
`group{}.members` is a list of refs and `jail{}.host` is the jailer's HostRef,
both readable on the next line ([§5.4](#54-jail--optional-advanced) reads
`web.host.hostname`). All it would buy is forward references, which relay's
declaration graph — jail → host, group → members, task → target, no cycles —
has no use for.

Two lookups deliberately resolve later, and neither is a declaration:
**`ctx.on("name")`** is a dispatch-time lookup inside a phase
([§10.1](#101-multiple-executors)), by which point the whole file has
registered; and the **CLI target** (`relay deploy web01`, [§9](#9-cli))
resolves after the declaration pass completes, against everything the file
declared. `vars{}` *values* are exempt too — they resolve per target when read
([§5.2](#52-vars--optional-static-and-lazy-per-target-data)), so a function var
may name anything. The one part of `vars{}` this rule does govern is the
**keys of a `relay.per_target` map**: those name targets, so they resolve at
the `vars{}` call like every other declaration site.

### 5.1 `host` — the one required declaration

`host{}` is the only topology declaration a minimal deploy needs. It names the
machine and how to reach it. Everything else is optional and defaults sensibly.

```lua
host({
  name     = "web01",                 -- CLI handle: `relay deploy web01`
  hostname = "web01.example.com",     -- what ssh dials; defaults to name
  user     = "deploy",                -- ssh user AND default acting identity
  port     = 22,                      -- optional, default 22
  identity = "~/.ssh/id_ed25519",     -- optional; path rules: §5.1 (operator-side)
})
```

The minimal real target — the four-step mental model — is:

```lua
host({ name = "web01", hostname = "web01.example.com", user = "deploy" })
```

The operator's own machine is reachable two ways:

- **`"localhost"` — the reserved target name** (no declaration). Usable
  directly as a task `target`, a pinned phase `target`, or
  `relay exec localhost -- …` (§9). It binds to exactly what `ctx.localhost`
  does — the bare operator identity, no SSH. This is the common case.
- **A named local target** when you need the operator box *with declared
  config* (a distinct acting identity, workdir, env, or lock):

```lua
host({ name = "buildbox", local_ = true, as = "builder" })  -- local_ because `local` is a Lua keyword
```

`"localhost"` is reserved: `host{}`/`jail{}`/`group{}` may not be named
`"localhost"` (plan-time error — it would collide with the bare operator
binding). `local_` is the flag (Lua's `local` is a keyword); it is not needed
for the bare `"localhost"` target, only for naming a configured local target.

**`sudo` — the one privilege knob for the common case** (see [§8](#8-privilege-the-common-case)):

```lua
host({ name = "web01", hostname = "web01.example.com", user = "deploy", sudo = true })
--                                   `sudo = true` ⇒ ops run as root by default
```

**`expect` — optional.** The agent reports its real platform on connect; you do
not need to declare it. Assert it only where a deploy genuinely depends on a
specific platform (see [§10.5](#105-assertions-host-expect--preconditions)):

```lua
host({
  name = "web01", hostname = "web01.example.com", user = "deploy", sudo = true,
  expect = { os = "linux", init = "systemd" },   -- assert at connect
})
```

`expect` is a *static identity assertion* — evaluated once at connect and
hard-failing on mismatch — distinct from the *in-phase preconditions* you
express with Lua `assert` mid-task (also
[§10.5](#105-assertions-host-expect--preconditions)).

**Full `host{}` reference** (every field optional except `name`):

| Field | Type | Default | Notes |
|---|---|---|---|
| `name` | string | — | required; CLI handle. **`"localhost"` is reserved** (rejected here — it's the bare operator target, usable as a `target` without a declaration; see below) |
| `hostname` | string | `name` | what ssh dials |
| `user` | string | current ssh default | ssh user **and** default acting identity |
| `port` | integer | 22 | ssh port |
| `identity` | string | ssh default | operator-side key path; `~/`→operator home, relative→config dir (§5.1) |
| `local_` | boolean | false | spawn agent locally over stdio instead of SSH |
| `as` | string | nil | default run-as identity for ops; `nil` = `user` (the connection user). §8 |
| `escalate` | string\|table | nil | how the connection user acquires another identity; `nil` = no escalation. `"sudo"` shorthand, or a table (`with`/`password`/`via`); §8, §10.4 |
| `sudo` | bool\|string | false | **sugar** for `as="root", escalate="sudo"` (`true`), or `as=<str>, escalate="sudo"` (a name); §8 |
| `expect` | table | — | static identity assertion at connect (§10.5) |
| `shell` | string | — | remote login shell override |
| `forward_agent` | boolean | false | pass `-A` to ssh; the operator's ssh-agent reaches the target session (below) |
| `tls` | table | — | default TLS settings for every `http` call that runs on this target — `ca`/`ca_pem`, `cert`/`key`, `server_name`, `insecure`; a per-call `tls` merges over it field by field. A private CA is a fleet fact, so it is declared here and inherited, not repeated at each probe. Paths resolve on the machine making the request. §7.3 |
| `workdir` | string\|function | nil | default working directory for `run` (`cwd`) and relative target paths (`fs.*`); `~/…`→`ctx.self.home`, `/abs` as-is, a relative literal is a plan-time error. `function(ctx)->string` resolved per target at connect time. §7.1 |
| `env` | table | — | inline env vars for every op on this host (keys must match `[A-Za-z_][A-Za-z0-9_]*`); sits on the `env`/`env_files` ladder (§7.1). Overrides `env_files`. |
| `env_files` | string\|array\|function | — | dotenv file(s) to load and merge, in order (later wins); one path, an array of paths, or `function(ctx)->string\|array` resolved per target. Paths resolve operator-side (§5.1). §7.1 |
| `env_expand` | boolean | true | expand `$VAR`/`${VAR}` in env values against the merged env map, as each rung of the ladder is read (§7.1); `$$` = a literal `$`; `false` = WYSIWYG (no expansion, no unescaping). An unknown reference is an error. Never reads OS env — use `relay.env()` for that. |
| `lock` | bool\|string | false | take an exclusive `flock` at connect to serialize concurrent relay sessions against this machine — **including sessions targeting its jails** (`true` = a default per-host path under the agent state dir; a string is an explicit target-side lock path, `~/`→ the connection user's home on this machine). Non-blocking: if held, relay aborts with a clear message and exits non-zero. Built on `fs.lock` (§7.2); skipped under `--dry-run`. |

**Deploy lock (`host.lock`).** Two operators — or CI plus a human —
deploying the same host race on symlink swaps and service restarts.
`host{ lock = true }` makes relay take an exclusive `flock` at connect (after
the platform probe, before any op); if it is already held, relay aborts with a
message like:

```
relay: another relay session is already running on web01
       (lock held at /home/deploy/.relay/web01.lock); aborting.
       If you are sure it is stuck, find and stop the holding relay process
       on the target, then retry.
```

`flock` auto-releases when the holding process exits, so there is **no
stale-lock state and no `--break-lock` escape hatch** — if it is held,
something is holding it. The lock gates **every** relay session against the
host (`deploy`, `task`, `relay exec`) so an ad-hoc command cannot race an
in-flight deploy. It is skipped under `--dry-run` (a preview is not a deploy).

**What the lock covers: one machine, one session.**

- **The unit is the physical machine**, not the target. `lock` is declared on
  `host{}` and there is no `jail{ lock }` ([§5.4](#54-jail--optional-advanced));
  a jail target uses **its jailer's `lock` declaration verbatim** — the same
  bool-or-path, resolved in the *host's* namespace, taken by the host agent
  whatever the jail's `fs_access` ([§10.2](#102-freebsd-jails)). So
  `host{ name = "prod00", lock = true }` serializes a `prod00` deploy against a
  deploy of any jail on prod00, which is the race worth stopping: they share
  the box, the pkg database, and the jail manager.
- **The unit is the session, not the member.** Within one relay run the lock
  is taken **once per machine**, at first connect to it, and held until the run
  ends. Members of a group that resolve to the same box — several jails on one
  jailer, or a host and its own jail — share that one lock and never collide
  with each other under any `strategy`. Different machines lock independently;
  per-host is the granularity, not per-group and not per-member.
- **First connect can be mid-run.** A target first reached inside a phase —
  `ctx.on(build00)`, a pinned phase on another host — takes that machine's
  lock when the phase connects, so a lock conflict there aborts partway
  through rather than at startup. Same rule, later moment.
- `~/` in an explicit lock path is the connection user's home **on the machine
  taking the lock**. On a jail target that is the jailer's home, not the
  jail's: the flock is a host-side file, and a path that read one way while
  landing another would be worse than verbose.

The cost of per-machine granularity is real and deliberate: two jails on one
jailer cannot deploy concurrently *in separate sessions*, even though their
filesystems are disjoint. Within one session they can, by the session rule
above. A script
that needs finer serialization leaves `lock` off and takes its own with
`ctx.fs.withlock` in a phase ([§7.2](#72-fs)) — the primitive `host.lock` is
built on. See [open question — per-jail deploy locks](#oq-per-jail-lock).

`host{}` returns a **HostRef** — `.kind == "host"` plus the fields above
(normalized: `hostname` defaults to `name`, `port` to 22, `sudo` sugar
expands to `as`/`escalate`). Read them off the ref for identity
(`web01.hostname`, `web01.user`, `web01.as`, `web01.escalate`) or pass the
ref where a target name is expected.

**Path resolution — two anchors.** Paths resolve against two different
anchors depending on which side of the wire they sit on. Operator-side is
plan-time fixed; target-side is per-target workdir.

| side | `~/…` | `/abs` | `rel` |
|---|---|---|---|
| **operator** (`identity`, `eval_file`, `fs.upload` src, `fs.download` dst, `env_files`) | operator `$HOME` | as-is | **config dir** |
| **target** (`run` `cwd`, `fs.*`, `fs.upload` dst, `fs.download` src) | `ctx.self.home` | as-is | resolved workdir (§7.1) |

The **config dir** is the directory containing the `relay.lua` relay loaded
(`-c/--config`, default `relay.lua` in the process cwd) — a **fixed, plan-time
anchor**, independent of the process cwd: `cd /tmp && relay -c
/srv/app/relay.lua` makes `/srv/app` (not `/tmp`) the anchor for every
operator-side relative path. On `ctx.localhost` both anchors sit on the same
machine but are computed independently — they coincide only when no `workdir`
is set (localhost's default workdir is the config dir). If a build phase sets
`workdir`, its `cwd` moves while the operator-side upload source stays pinned
to the config dir; reference build outputs by absolute path.

**`~` expansion — one rule, both sides.** Only a path that **starts with**
`~/` expands (that leading `~/` → home); a `~` anywhere else — bare, mid-name,
`~word`, or a `~/` appearing mid-path (`foo/~/bar`) — is a literal character,
never an error. There is no `~user` form on either side — write an absolute
path or build from `ctx.self.home`. Target-side `~/` → `ctx.self.home`
(`getpwuid`, §6), the same value `ctx.self.home` reports — it does **not**
track a per-op `as` override (for a different identity's home, use an absolute
path). Target-side paths otherwise resolve via namespace tags (§10.3).

**SSH agent forwarding.** Set `forward_agent = true` to pass `-A` to ssh, so
the operator's ssh-agent reaches the target's session. The relay-agent and its
child processes — notably any `run` that pulls from a private source, such as
the git recipe (§11.16) — can then authenticate using the operator's keys, with
no key stored on the server. Default is `false`: a forwarded agent is usable by
root on the target, so opt in only where you need it.

```lua
-- Cloning a private repo on the build host: forward the operator's key
host({ name = "build00", hostname = "build00.example.net", user = "ci",
       forward_agent = true })

-- ...then this works without a deploy key on build00:
--   git.sync(ctx.on("build00"), "git@github.com:org/repo.git", "/srv/repo")
```

For a routed jail target the ssh connection lands on the physical host
regardless, so one `forward_agent = true` on the jail's `host{}` covers
commands run on the **host** — but only those: the forwarded socket lives in
the host's namespace, so a `jexec`-ed jail-side command cannot see it, and a
private repo cloned inside the jail needs a deploy key there
([§11.16](#1116-a-git-recipe)).
The `env_reset`/sudoers interaction and other mechanics are in
[§10.4](#104-privilege-in-depth).

### 5.2 `vars` — optional, static and lazy per-target data

`vars{}` declares named values a script wants to share across tasks and
phases, **resolved for the current target when read**. It is general-purpose
key/value data — not a deploy model. A release layout is a *recipe* built on
top of this and the core ops ([§11.14](#1114-a-deploy-recipe-plain-require)).

**Without `vars{}`** you use literals and locals — nothing else is required:

```lua
local svc = require("recipe.service")   -- init dispatch (§11.17)

host({ name = "web01", hostname = "web01.example.com", user = "deploy", sudo = true })

task("deploy", function(ctx)
  ctx.fs.write("/etc/nginx/nginx.conf", NGINX_CONF, { mode = "0644" })
  svc.restart(ctx, "nginx")
end)
```

**With `vars{}`** — declare once, read the per-target value via `ctx.vars`:

```lua
vars({
  name = "myapp",                                       -- literal: same everywhere
  root = function(ctx) return relay.path.join(ctx.self.home, "myapp") end,  -- lazy: per target
  port = relay.per_target{ default = 3000, web02 = 3001 },  -- per-target override
  sha  = function(ctx)                                  -- lazy: computed on target
    return ctx.run({"git", "-C", ctx.vars.root, "rev-parse", "--short", "HEAD"}).stdout
  end,
})
```

Each value is one of three shapes:

| Shape | Resolves to | Example |
|---|---|---|
| **literal** (string/number/bool/table) | itself, same on every target | `"myapp"`, `5`, `{ retries = 3 }` |
| **per-target map** `relay.per_target{ default = V, [name] = V, … }` | `default`, overridden by `ctx.self.name` | `relay.per_target{ default = 3000, web02 = 3001 }` |
| **function** `function(ctx) -> V` | called with `ctx` per target; full power — any target context or command | `function(ctx) return relay.path.join(ctx.self.home, "myapp") end` |

**A bare table is always a literal.** The per-target shape requires the
explicit `relay.per_target` marker, so relay never has to guess which of the
two a table meant:

```lua
vars({
  ports = { web01 = 8080, web02 = 8081 },                  -- literal: a lookup table you index
  port  = relay.per_target{ default = 3000, web02 = 3001 }, -- per-target: relay indexes it for you
})

-- on web02:
ctx.vars.ports        --> { web01 = 8080, web02 = 8081 }   (the table, unchanged)
ctx.vars.ports.web02  --> 8081                             (you index it)
ctx.vars.port         --> 3001                             (relay indexed it)
```

Without the marker these two are the same Lua value and any rule relay picked
would silently mis-read one of them. The alternative — "a table with a
`default` key is per-target" — makes some literal tables unrepresentable and
turns a data-shaped word into a reserved key. The marker reserves nothing:
`relay.per_target` copies the mapping and tags the copy via its metatable, so
no key name is claimed, `pairs()` over the map sees only your keys, and the
table you passed in stays an ordinary table.

**Resolution order**, when a phase reads `ctx.vars.NAME`: a `function` value is
called with `ctx`; a `relay.per_target` value is looked up by
`ctx.self.name`, falling back to `default`; anything else is returned as-is.

Rules for the per-target map:

- **Keys are target names** — a declared `host{}` or `jail{}` name, or the
  reserved `"localhost"` — plus the optional `default`. A key naming no
  declared target is an error at the `vars{}` call, reported at that line
  (declaration order applies exactly as in [§5](#5-topology): declare a target
  before naming it).
- **Group names are not keys.** A group is a set of targets, and allowing both
  would raise a precedence question (a member listed directly *and* via its
  group; a member in two listed groups) for a shape whose whole value is being
  obvious. Use the function form, which can read `ctx.group`.
- **`default` is optional.** A target with no entry and no `default` is an
  error naming the var and the target, not a silent `nil` — a `nil` here
  concatenates into a path or a command and fails somewhere far away. Both
  the key set and the target set are known without connecting, so
  `relay validate` ([§9](#9-cli)) catches it at plan time.
- **Only valid as a top-level `vars{}` value.** `relay.per_target` nested
  inside a literal table (`cfg = { port = relay.per_target{…} }`) is an error
  at the `vars{}` call; relay resolves var values, not arbitrary interior
  nodes.
- **`relay.per_target` must be called.** Passing the function itself
  (`port = relay.per_target` — dropped braces, still valid Lua) is an error at
  the `vars{}` call. So is any other relay-provided function used as a var
  value; your own functions are the function shape and stay valid.
- **`--var NAME=value` replaces the whole map**, giving every target that
  value ([§9](#9-cli)). It does not merge into one key: the override exists so
  CI can pin a value fleet-wide, and a flag that silently edited one entry of a
  declared map would be the harder thing to reason about.

**`ctx.vars.NAME`** is the resolved value for the *current* target — the
scalar, never the marked map. Resolution is lazy and **memoized per
(target, name)** for the run — a function var that shells out runs once per
target, not once per read. Literals and per-target maps resolve without a
connection — `--dry-run` shows the real value, and `relay validate` checks a
map's keys against the declared targets without connecting. Function vars are
evaluated on first read inside a phase (where `ctx` and the connection exist),
so referencing one at plan time is a plan-time error.

The function form is the general escape hatch: `ctx.self.home` / `.user` /
`.platform`, `ctx.run`, anything on `ctx` is available. The common case — a
path under the acting user's home — is one line:

```lua
-- on host "deploy1" acting as deploy1 → "/home/deploy1/myapp"
-- on host "deploy2" acting as deploy2 → "/home/deploy2/myapp"
-- one declaration, per-target truth.
root = function(ctx) return relay.path.join(ctx.self.home, "myapp") end
```

`vars{}` returns a **VarsRef** — a read-only handle to the declared specs
(useful for LuaLS / direct inspection); the *resolved* values are always read
via `ctx.vars`. Referencing `ctx.vars.NAME` for an undeclared name is a
dispatch-time error naming the missing key — the read happens inside a phase,
though the declared name set is known at plan time, so `relay validate`
([§9](#9-cli)) catches a literal `ctx.vars.typo` without connecting.

### 5.3 `group` — optional

A named set of targets. Members may be hosts or jails, given as refs or name
strings.

```lua
local svc   = require("recipe.service")
local web01 = host({ name = "web01", ... })
local web02 = host({ name = "web02", ... })
group({ name = "web", members = { web01, web02 } })   -- refs (or { "web01", "web02" })

task("deploy", {
  target = "web",                       -- runs once per member; ctx binds to each
  run = function(ctx)
    svc.restart(ctx, "myapp")
  end,
})
```

`group{}` returns a **GroupRef** — `.name` and `.members` (a list of refs; name
strings resolve at registration, so every member must be declared above the
`group{}` — [§5](#5-topology)). In a group task, `ctx` binds to each
member in turn; `ctx.self.name` is the current member's name. To act on a
*specific* other host from within a phase, use
[`ctx.on(...)`](#101-multiple-executors).

**Groups are flat — no nested groups.** `members` are hosts or jails only; a
`GroupRef` is not a valid member, and `group{}` registration rejects one at
plan time. relay's concurrency is a single-level fan-out, not a DAG
([§10.7](#107-concurrency-fan-out-not-dags)); nesting would add cycle
detection, dedup, and per-level strategy interaction for no runtime power a
flattened group doesn't already have. Compose in Lua instead — a group is
just a member list you build from refs you already hold:

```lua
local prod = { web01, web02, db01, db02 }   -- host refs (or name strings)
group({ name = "prod", members = prod })     -- inline the table if you prefer
```

### 5.4 `jail` — optional, advanced

A FreeBSD jail is a deploy target in its own right. **Register no `jail{}` and
no jail concept appears in your script.** Register one and `ctx` binds to the
jail, `ctx.host` to the physical machine beneath it. See
[§10.2](#102-freebsd-jails).

```lua
jail({
  name      = "web",       -- CLI handle and task target
  host      = "prod00",    -- REQUIRED: a host{} declared ABOVE this jail (ref or
                           --   name; resolved at registration, §5) to SSH into
  match     = nil,         -- OPTIONAL: how to find the jail in `jls` — a table of
                           --   column equalities or a predicate over one row;
                           --   defaults to { name = <this jail's name> } (§10.2)
  fs_access = "attach",    -- OPTIONAL: how `fs.*` reaches the jail's files —
                           --   "attach" (default, in-jail, needs a root agent)
                           --   or "mountpoint" (host-side, translated) (§10.2)
  path      = nil,         -- OPTIONAL: the jail's host-side mountpoint, string or
                           --   function; overrides the `jls` row. Mountpoint
                           --   mode only (§10.2)
})
```

**No `lock` field, by design.** A deploy lock serializes a machine, and a jail
is not one. Deploying this jail takes `prod00`'s lock if `prod00` declared one
— its declaration verbatim, taken host-side — so a jail deploy and a host
deploy on the same box cannot race ([§5.1](#51-host--the-one-required-declaration)).
Per-jail serialization, if a script wants it, is `ctx.fs.withlock` in a phase.

**Two ways a jail is reached, two declarations.** A jail is either *routed*
(SSH lands on the physical host; the agent resolves it via `jls` and routes
ops through `jexec`/mountpoint) or *direct* (the jail has its own sshd and IP;
SSH lands inside it). These are different, and `jail{}` models only the first:

- **Routed jail ⇒ `jail{}`.** Use this declaration. `host` is required and
  must name a declared `host{}`; the agent SSHs into it and routes. `ctx` is
  the jail, `ctx.host` is that physical host's executor.
- **Direct-SSH jail ⇒ `host{}`.** If SSH reaches the jail directly, the jail
  is a host — declare it as one. No `jexec`, no `ctx.host` (dispatch-time error).
  To also operate the physical machine, declare it as a second `host{}` and
  reach it with `ctx.on(...)`.

`jail{}` unambiguously means "I cannot SSH into this jail; route me through
its host." There is no `hostname` field on `jail{}`: it read like an SSH target
while meaning a `jls` lookup key, overloading `host{}.hostname`. Lookup is
`match` instead — a selector over the `jls` sweep, which covers the hostname
key (and every other column) without the ambiguous spelling
([§10.2](#102-freebsd-jails)). For an optional metadata link in the *other*
direction (marking a `host{}` as a direct-SSH jail of some physical machine),
see [open question — metadata link for direct-SSH jails](#oq-jail-metadata).

`jail{}` returns a **JailRef** — `.kind == "jail"`, `.name`, `.fs_access`, and
`.host` (the jailer's HostRef, resolved from the `host` field). So
`web.host.hostname` reads the physical box's identity whether you declared
`host = prod00` or `host = "prod00"`. The jail's *own* resolved identity — jid,
jail name, hostname, mountpoint — is not known until connect; read it at run
time from `ctx.self.jail` ([§6](#6-tasks-and-ctx)).

## 6. Tasks and `ctx`

A **task** is a named, runnable unit: `deploy`, `rollback`, or anything you
name. It has a target and one or more **phases**. Inside a phase, **`ctx` is
the executor** bound to the current target — every operation hangs off `ctx`.

Two forms. **Single-phase sugar** (the common case):

```lua
task("smoke", function(ctx)
  ctx.run("curl -sf http://localhost/healthz")
end)
```

**Multi-phase** (ordered steps with names):

```lua
task("deploy", {
  target = "web01",
  phases = {
    { name = "build",   run = function(ctx) ... end },
    { name = "release", run = function(ctx) ... end },
    { name = "activate",run = function(ctx) ... end },
  },
})
```

**Target inference.** Either form may omit `target` only when the script
declares exactly one target — a single `host{}`, `jail{}`, or `group{}`;
that target is inferred. Zero declared targets is a plan-time error ("no
target declared; pass `target = ...` or declare a `host{}`"). Two or more
is a plan-time error ("task has no target; N targets declared — pass
`{ target = ..., phases = ... }`"). Inference is plan-time, before any
connection, and `relay deploy [target]` on the CLI still overrides it ([§9](#9-cli)).

Both the count and an explicit `target` string are read **when `task(...)`
registers** ([§5](#5-topology)) — so a task sits below the targets it names or
infers, the same order every other declaration follows.

A `target` (task or phase) is a declared `host{}`/`jail{}`/`group{}` name or
ref, **or the reserved `"localhost"`** (the operator machine, §5.1 — same
binding as `ctx.localhost`). `"localhost"` is explicit-only: it is never
inferred, so a target-less task with zero declarations is still a plan-time
error (not a silent localhost default).

Each phase:

| Field | Required | Meaning |
|---|---|---|
| `name` | yes | shown in logs; unique within the task |
| `run` | yes | the phase body: `function(ctx) ... end` |
| `target` | no | pin this phase to a declared `host{}`/`jail{}` name/ref or the reserved `"localhost"` — runs **once** there instead of fanning out (see [Pinned vs fan-out](#pinned-vs-fan-out-phases) below) |
| `as` | no | default run-as identity for the phase; narrows the task/host default (§8) |
| `workdir` | no | default working directory for the phase; narrows the task/host workdir (§7.1) |
| `env` | no | env for the phase's ops; narrows the task/host env (§7.1) |
| `env_files` | no | dotenv files for the phase; narrows the task/host `env_files` (§7.1) |
| `when` | no | `function(ctx): boolean`; phase skipped on false. **Pure predicate — must be side-effect-free** (§10.5) |

The `task{}` table accepts the same `as` field at task scope — it narrows the
host default for the whole task (e.g. `task("audit", { as = "nobody" })` for a
task that must *not* run as root), and the same is true for `workdir` and for
`env`/`env_files` — the working-directory and env ladders mirror the identity
ladder (§7.1). It also accepts a task-level **`when`** (skip all of a member's
phases) and the two hooks **`on_failure`** / **`finally`** ([§6.2](#62-failure-handling-on_failure-and-finally)).
See the identity precedence ladder in [§8](#8-privilege-the-common-case).

**Fan-out vs pinned phases.** A phase *without* a `target` field runs **per
member** of the task's `target` — once for a single host, once per member for a
group (`ctx` rebound each time). A phase *with* a `target` field is **pinned**
— it runs exactly once on that target. Work that must run once or on a
*different* host (build, migration, smoke test) is a pinned phase in the same
list — see [Pinned vs fan-out phases](#pinned-vs-fan-out-phases) below.

**`ctx` reference** — the executor bound to the current target:

```lua
ctx.run(...)                 -- run a command (§7.1)
ctx.fs.write(...)            -- filesystem (§7.2)
ctx.http.check(...)          -- health probe (§7.3)
ctx.log.info(...)            -- operator console (§7.4)
ctx.sleep(2)                 -- pace a hand-rolled poll loop (§7.5)
ctx.path(p)                  -- namespace-tagged Path for cross-frame ops (§10.3)
ctx.eval(src, args)          -- run an inline agent Lua script (§10.6)
ctx.eval_file(path, args)    -- run an agent Lua script file (§10.6)

-- Identity & scope (not executors):
ctx.self                     -- the current target's scope (see below)
ctx.vars                     -- declared vars, resolved for the current target (§5.2)
ctx.shared                   -- read/write bag, one per task run (see below)
ctx.group                    -- the GroupRef (nil if not a group task)

-- Other executors (§10):
ctx.localhost                -- the operator's machine
ctx.host                     -- executor for the physical host beneath a JAIL
                             --   target (dispatch-time error otherwise)
ctx.on(ref | "name")        -- any registered host/jail
```

**`ctx.self`** — the current target's scope, a fixed shape regardless of
target kind:

```lua
ctx.self.kind        -- "host" | "jail"
ctx.self.name        -- the target name (jail name or host name)
ctx.self.host        -- ALWAYS the physical box's HostRef — .name, .hostname,
                     --   .user, .port, .as, .escalate, … (§5.1). For a host target
                     --   this is the target itself; for a jail, the jailer.
ctx.self.jail        -- jail targets only (nil on a host): the resolved `jls`
                     --   row — { jid, name, hostname, path } (§10.2). `path` is
                     --   the host-side mountpoint; on a stopped jail only
                     --   `path` is set and the rest are nil.
ctx.self.user        -- the identity this scope runs as, after the host → task
                     --   → phase ladder (§8). ALWAYS a string — the connection
                     --   user when no `as` applies, never nil.
ctx.self.home        -- that identity's home directory, as the agent resolves
                     --   it (getpwuid). The per-target primitive behind "the
                     --   same path on every host" — see vars{} (§5.2). The
                     --   connection user's arrives on the `Hello` (§4.1); a
                     --   non-default `as` is resolved on the target.
ctx.self.workdir     -- the resolved working directory for this target (the
                     --   workdir ladder, §7.1): an op's cwd / a relative
                     --   target path resolves here. Read-only.
ctx.self.platform    -- the agent's detected platform (see below)
```

**`ctx.self.user` is resolved, not declared.** `nil` means "no default, use the
connection user" in a *declaration* (`host.as`, §5.1) — but `ctx.self.user`
reports the outcome of that resolution, so it is always a string. Otherwise
every consumer of "who am I running as" would have to write
`ctx.self.user or ctx.self.host.user`, and the one who forgets gets a `nil`
concat exactly on the hosts that declare no `as` — the simple case v3 is built
for. It reflects the **phase-resolved** identity: a per-op `as` overrides one
call and is deliberately not visible here, because a phase-scoped value cannot
track a per-op one (read it from the op's `executed` string instead, §13).

Host-identity always lives under `ctx.self.host.*` — never `ctx.self.hostname`
— so the spelling is uniform across host and jail targets. (On a host target
`ctx.self.name == ctx.self.host.name`; that coincidence is expected — branch
on `ctx.self.kind`, never on name equality.) `ctx.target_name` is gone; use
`ctx.self.name`.

`ctx.self` is a **scope, not a ref** — it is not accepted where a target
name/ref is (`task.target`, `group.members`, `ctx.on`); use the declared ref
(captured from `host{}`/`jail{}`) or, for the physical box, `ctx.self.host`
(a HostRef). The executor view comes from `ctx.on(<ref>)`, not `ctx.on(ctx.self)`.

**`ctx.self.platform`** — the target's platform as the agent reports it on
connect: always present, always the detected truth (never the declared
assertion — that's `host{ expect=... }`,
[§10.5](#105-assertions-host-expect--preconditions)).

```lua
ctx.self.platform.os              -- "linux" | "freebsd" | …    (agent runtime.GOOS)
ctx.self.platform.distro          -- "ubuntu" | "debian" | "alpine" | … | ""  (os-release ID)
ctx.self.platform.version         -- "22.04" | "11" | "14.0" | … | ""        (os-release VERSION_ID / uname -r, normalized)
ctx.self.platform.arch            -- "amd64" | "arm64" | "i386" | …
ctx.self.platform.init            -- "systemd" | "rcd" | "sysvinit" | ""
ctx.self.platform.package_manager -- "apt" | "pkg" | "dnf" | … | ""
```

`os` is the kernel family (the Go runtime's `GOOS`); `arch` is `GOARCH`. The
other four are probed: `init`/`package_manager` from the running init and
available tools; `distro`/`version` from `/etc/os-release` on Linux (the
freedesktop `ID`/`VERSION_ID` — `ubuntu`/`22.04`, `debian`/`11`,
`alpine`/`3.19`) and from `uname(2)`'s release for FreeBSD's `version`.
`distro` is `""` off Linux — under `os = "freebsd"` there is nothing to
distinguish.

**FreeBSD `version` is normalized to `MAJOR.MINOR`.** The raw release string
carries the build type and the patch level — `14.0-RELEASE`, `14.0-RELEASE-p6`
after a `freebsd-update`, `13.2-STABLE`, `15.0-CURRENT` — so the agent strips
everything from the first `-`: all four report `14.0`, `14.0`, `13.2`, `15.0`.
Reporting it raw would make `expect.version` unusable, since the value changes
under the operator on the first security patch; this keeps FreeBSD's grain the
same as Linux's `VERSION_ID` (a release line, not a point release). A
deploy that genuinely depends on a patch level reads it from `run("uname -r")`
or `freebsd-version -u` — an in-phase `assert`, not a connect-time `expect`.

Branch on what's really there without forcing an `expect`; `""` on any probed
field means the probe couldn't tell (no `/etc/os-release`, a rolling release
without `VERSION_ID`, a scratch container) — unverifiable, not a mismatch. Distinct
from `relay.goos`/`relay.goarch` ([Appendix A](#appendix-a--go-lua-gotchas)),
which is the *operator* machine's platform. On a jail target this is the
jailer host's report (the agent process runs there); a jail-internal
init/package_manager is not probed separately.

**Group tasks fan out per member.** For a group `target`, every *fan-out*
phase (no `target` field) runs once per member with `ctx` rebound to each.
*Pinned* phases (with `target`) run once, regardless of group size.

<a id="pinned-vs-fan-out-phases"></a>
**Pinned vs fan-out phases.** One ordered `phases` list; each phase either
fans out (no `target`) or is pinned to a single target
(`target = host|jail|ref|"localhost"`). The two mix freely, and **run order is
list order**:

```lua
task("deploy", {
  target = "web",            -- task target: the group (fan-out phases run per member)
  phases = {
    { name = "build",   target = "build00",  run = function(ctx)
        ctx.run("make release")                 -- ONE build, on build00
      end },
    { name = "migrate", target = "db00",      run = function(ctx)
        ctx.run("migrate up")                   -- shared DB, once
      end },
    { name = "deploy",  run = function(ctx)       -- fan-out: web01, web02
        ... end },
    { name = "smoke",   target = "localhost", run = function(ctx)
        ctx.http.check("https://app.example.com/healthz", { expect_status = 200 })
      end },
  },
})
```

- **Run order is list order.** build → migrate → deploy (fan-out) → smoke. No
  implicit "pre/main/post" buckets — position is the declaration.
- **`target` on a phase is a single box** — a `host{}`/`jail{}` name/ref or the
  reserved `"localhost"` (the operator's machine, same binding as
  `ctx.localhost`). Never a `group{}`: fan-out is a property of the task's
  group target inherited by target-less phases; a pinned phase is always one
  execution.
- **`ctx` is fully bound** to whichever target a phase runs on — `ctx.run`,
  `ctx.fs`, `ctx.self`, … all work. A pinned phase's `ctx` *is* its target (no
  `ctx.on(...)` hop); a fan-out phase's `ctx` is rebound per member.
- **Failure is fail-fast.** A failed phase (pinned or fan-out) stops the list;
  later phases don't run. `on_failure` / `finally`
  ([§6.2](#62-failure-handling-on_failure-and-finally)) fire per member; see
  there for the rules.
- **`--dry-run`:** reads execute, mutating actions are stubbed
  ([§4.4](#44-dry-run)), for pinned and fan-out alike.

<a id="pinned-phase-execution-model"></a>
**Execution model: pins are barriers.** How the one list schedules against a
group target under a `strategy` ([§10.7](#107-concurrency-fan-out-not-dags)):

- A pinned phase is a **barrier**: it starts only after every member has
  completed every earlier phase in the list, it runs exactly once on its
  target, and no member starts a later phase until it completes.
- Between barriers, a contiguous block of fan-out phases executes
  **member-major**: each member runs the block's phases in order as one
  sequential chain, and `strategy` schedules those chains across members.
  Under `serial`, web01 finishes the whole block (`deploy`, then a following
  fan-out `verify`) before web02 starts it — a member failure leaves later
  members untouched. `strategy` never reorders across a barrier.
- Under `rolling`, batching applies **per block**: a pinned phase closes the
  block, and the next block re-batches from the full member list. With
  `stage → migrate (pinned) → activate`, every batch completes `stage`
  before `migrate` runs, and only then does `activate` begin batching —
  batch 1 does not canary end-to-end through a pin. That is inherent, not a
  quirk: work worth pinning (a shared migration) cannot run per-batch, and
  once it has run, every remaining member faces its result.
- A pinned phase runs **once, at its list position** — never per member,
  never per batch. In the example above, `smoke` runs after the last member
  finishes `deploy`; it does **not** gate the rollout batch-by-batch.
  Per-batch gating is the `rolling` gate ([§10.7](#107-concurrency-fan-out-not-dags),
  [open question — the `rolling` gate shape](#oq-fanout-knobs)), not a pinned phase.

This replaces v3's earlier `scope = "once"` phase flag **and** the
`pre_phases`/`post_phases` split. Single-shot and off-target work is now just
a phase carrying its own `target`, so "where does this run?" is always
answered by a field you read — never by a bucket you have to remember.

**`ctx.shared`** — a read/write Lua table scoped to the **task run**,
shared across every phase (pinned and fan-out) and visible to `on_failure`
and `finally`. It
is the runtime counterpart of `ctx.vars`: `vars` are declared, resolved per
target, read-only; `shared` is written by phases as they execute, one bag for
the whole run.

The use case is the build-once / deploy-many shape: a **pinned** build phase
computes a value on one target (build host) that later fan-out phases need on
another
— an artifact path carrying a build-time SHA. Phases are separate closures,
so an upvalue can't bridge them, and `ctx.vars` can't either: a var is a
function of the *reading* target, so `vars.sha` evaluated on `web01` asks
web01's repo, not build00's. `ctx.shared` is the bridge.

```lua
task("deploy", {
  target = "web",
  phases = {
    { name = "build", target = "build00", run = function(ctx)
        local sha = ctx.run({"git", "-C", "/srv/repo", "rev-parse", "--short", "HEAD"}).stdout
        -- build00 -> operator (typed download); no build00->web ssh needed
        ctx.fs.download("/srv/repo/build/app-" .. sha .. ".tar.gz", "tmp/app-" .. sha .. ".tar.gz")
        ctx.shared.sha      = sha                       -- write once; build is pinned, runs before fan-out
        ctx.shared.artifact = "tmp/app-" .. sha .. ".tar.gz"   -- operator-side
      end },
    { name = "deploy", run = function(ctx)
        -- operator -> this member (fans out per member); then read ctx.shared
        ctx.fs.upload(ctx.shared.artifact, "/tmp/app-" .. ctx.shared.sha .. ".tar.gz")
        ctx.fs.extract("/tmp/app-" .. ctx.shared.sha .. ".tar.gz", "/var/www/app-" .. ctx.shared.sha)  -- read
      end },
  },
})
```

| aspect | rule |
|---|---|
| scope | one bag per **task run** — every phase, every fan-out member, the hooks |
| read of unset key | `nil` (not an error; same as any Lua table) |
| write | `ctx.shared.NAME = v`, from any phase |
| lifetime | cleared when the task run ends; not shared across tasks |
| `--dry-run` | writes execute (no host side effect); reads see written values |

**Scope is task-wide, not per-member.** A pinned phase's write is visible to
every member of a group fan-out — that is the point (build once, deploy N).
A pinned phase is a barrier (see [the execution model](#pinned-phase-execution-model)
above): its write completes before any member starts a later phase, so the
write is done before the first read; no race under any `strategy`.

**Footgun — don't mutate `ctx.shared` from fan-out phases under `parallel`.**
Under `strategy = "parallel"` ([§10.7](#107-concurrency-fan-out-not-dags)),
members run concurrently; a write from one member's fan-out phase is visible
to its siblings with no ordering guarantee. Reserve writes for pinned phases
(serial, done before fan-out) — fan-out phases should read. `finally`
likewise: read, don't write, under `parallel`. For data a single member's
phase chain needs, keep it in a local upvalue across adjacent phases or merge
those phases — same target, same `ctx`, no reason to split.

**On failure.** Keys written before a raise stay set; `on_failure` and
`finally` read them
(useful: "staging wrote files before failing — clean them up"). Remaining
phases are skipped ([§6.1](#61-error-model)), so a phase never sees a key a
later phase wrote.

### 6.1 Error model

**The rule:** **actions raise on error → the phase fails (fail-fast); reads
return `(value, err)` and don't fail the phase by themselves.** Suppress an
action's raise with `ignore_exit` / `pcall`; skip with guards; force a read to
fail the phase by `assert`-ing on its `err`.

- **Raise on error (actions):** `run`, `fs.write`/`append`/`remove`/`mkdir_all`/
  `symlink`/`copy`/`copy_dir`/`touch`/`chmod`/`chown`/`rename`/`archive`/`mktemp`/`upload`/`download`/`extract`.
  Return `{changed}` (or the full result incl. `ran`, for `run`) on success —
  `mktemp` is the one exception, returning the created path instead.
- **Return `(value, err)` (reads):** `fs.read`, `fs.exists`, `fs.readlink`,
  `fs.list`, `fs.stat`, `fs.realpath`, `fs.glob`, `fs.hash`, `fs.lock`,
  `fs.unlock`, `http.check`, `http.request`. `value` is the natural result (`string`, `bool`,
  table) on success and `nil` (or `false`, for `fs.exists`) on failure; `err` is
  `nil` on success, a string on failure. Reads **never raise** — not even
  `http.check`/`request` with `expect_status` (a violated `expect_status` sets `err`; wrap
  in `assert` to fail the phase). This mirrors Go/Lua stdlib (`os.ReadFile` →
  `([]byte, error)`, `io.open` → `file, err`): one convention across every read.
  (`http.request` is the one op whose `--dry-run` class follows its arguments —
  the safe methods GET/HEAD/OPTIONS execute unless the call writes an
  `out_file`, everything else is stubbed — but it
  always returns `(value, err)`; see §7.3. `fs.withlock` is the wrapper exception: it re-raises
  its function's errors after releasing the lock, unlike `fs.lock`/`fs.unlock`
  which return `(value, err)`; see §7.2. `fs.lock`/`fs.unlock` keep the read
  shape but carry their own `--dry-run` rule, since acquiring a lock is a side
  effect no other read has; see §4.4.)

`run { read_only = true }` (§7.1) is the one op that is classified a read
without adopting the read *shape*: it still returns the full result table and
still raises on a non-zero exit unless `ignore_exit = true`. The flag governs
dry-run and `when` eligibility, not the calling convention — a recipe's probe
should look like every other `run` at the call site, and `(value, err)` is not
what a caller wants from a command whose exit code *is* the answer.

**What fails a phase:**

| source | fails? | escape |
|---|---|---|
| action op error (`fs.write`, `fs.symlink`, …) | yes (raises) | `pcall` |
| `run` non-zero exit | yes | `ignore_exit = true` |
| `assert(cond, msg)` / `error(msg)` | yes | `pcall` |
| Lua runtime error (nil index, type error) | yes | `pcall` |
| SSH/RPC drop mid-op | yes (transport error raises) | — |
| `onlyif`/`unless` false (on `run`) | no — skips the command | — |
| `when` false (phase) | no — skips the phase | — |
| read returns `err`/nil (`fs.read`, `http.check`, …) | no — returns `(value, err)` | wrap in `assert` |

**Signaling failure (raising / bailing out).** A phase succeeds by returning
normally; **return values are ignored.** To stop the phase with a failure,
*raise*. Actions raise for you on failure; reads hand you `(value, err)` and
stay quiet — so a read whose failure should stop the phase goes through
`assert`:

```lua
-- 1. assert a precondition — the idiomatic bail (message on failure)
assert(ctx.fs.exists("/opt/app/.installed"),
       "app not installed; run bootstrap first")

-- 2. explicit bail with a computed reason
if free_disk_mb < 500 then
  error("insufficient disk: " .. free_disk_mb .. "MB free, need 500")
end

-- 3. let an action fail implicitly — fs.write on a bad path raises for you
ctx.fs.write(path, content)

-- 4. catch locally, decide whether the failure matters
local ok = pcall(function() ctx.run({"pg_dump", "app"}) end)
if not ok then ctx.log.warn("backup failed; continuing anyway") end
```

For a *soft* skip (not a failure), use `when` (phase) or `onlyif`/`unless`
(`run`) — those skip without failing.

**The `err` value.** When a phase fails, relay builds a structured error the
handler can branch on:

| field | always? | meaning |
|---|---|---|
| `kind` | yes | `"exit"` \| `"op"` \| `"assert"` \| `"lua"` \| `"transport"` \| `"cancelled"` |
| `phase` | yes | the phase that failed (single-phase task ⇒ task name) |
| `message` | yes | one-line human summary |
| `op` | when op-sourced | `"run"`, `"fs.write"`, … |
| `intent` | when op-sourced | the op as the user wrote it, with resolved `as` — e.g. `run("service nginx restart") as root` |
| `identity` | when op-sourced | the resolved uid chain — e.g. `deploy → root` (connection user → run-as user) |
| `executed` | op- or exit-sourced | the exact post-wrap byte string relay ran: escalation prefix (`sudo -n -u root …`, `doas -u …`, `jexec -u …`) + resolved argv + `cwd` + env. Copy-paste reproducible in a shell — except secret-marked env values (§7.1), shown as `<redacted>` (the real value still ran). |
| `exit_code`, `stdout`, `stderr` | `kind="exit"` only | the failing `run`'s raw OS result; `stderr` verbatim (truncated ~4 KB) |
| `traceback` | `kind="lua"` only | Lua stack trace |

**No permission pre-checks.** relay never validates sudoers, file perms,
ACLs, or passwords ahead of time — that is the OS's job, not relay's. relay
reads the host's declared escalation config ([§8](#8-privilege-the-common-case),
[§10.4](#104-privilege-in-depth)), wraps each op accordingly, runs it, and lets
the OS judge. On failure, the error carries the full reproducible context:
`intent` (what the user asked for), `executed` (what relay actually ran, after
wrapping), `identity` (the uid chain), and the raw OS result (`exit_code` /
`stderr`). A reader can paste `executed` into a shell and see the same failure
— that is the whole point. Server operators read `executed` + `stderr` and
know what went wrong; pattern-matched remediation hints are a later
optimization, not part of the core model.

`kind` taxonomy: `"exit"` (run non-zero), `"op"` (action op raised),
`"assert"` (your `assert`/`error`), `"lua"` (runtime error), `"transport"`
(connection/RPC drop), `"cancelled"` (nothing of this member's failed — a
sibling's failure stopped it under fail-fast; [§6.2](#cancelled-member)). The
value has a `__tostring` metamethod, so `tostring(err)` is
`"<phase>: <message>"` and log lines stay clean.

`"cancelled"` is the one kind `on_failure` never receives: no member code
raised it, so the hook that exists for a member's *own* failure does not fire.
It reaches scripts only as `summary.err` in `finally`. Two things raise it —
a sibling's failure under fail-fast, and an operator interrupt
([§9](#interrupting-a-run)).

**Two rules:**
1. **`kind="transport"` ⇒ `ctx` may be dead.** The hook still runs, but its own
   remote ops can fail too — be defensive (`pcall`) and notify via
   `ctx.localhost`, not remote cleanup.
2. **No recovery.** Raising fails the phase unconditionally; no hook can
   "swallow" an error and mark a failed task successful. Conditional failure
   belongs in the phase body with `pcall`, not in a hook.

### 6.2 Failure handling: `on_failure` and `finally`

Two task-table hooks. `on_failure` runs when a member fails; `finally` runs
per member after its phases, always. Both fan out per member like phases
(single-host ⇒ once; group ⇒ once per member, `ctx` bound to each). Phases
cover the success path; these cover what phases can't — the failure path, and
always-run cleanup. ("Always" is per member *that started* — a member the run
never reached fires no hooks, and one stopped mid-run fires `finally` but not
`on_failure`; see [pinned-phase failure](#pinned-phase-failure) and
[cancelled members](#cancelled-member) below.)

```lua
task("deploy", {
  target   = "web01",
  phases   = { ... },
  on_failure = function(ctx, err)     ... end,   -- failed member only
  finally    = function(ctx, summary) ... end,   -- every member, always
})
```

**`on_failure = function(ctx, err)`** — the failure path.

- Runs **only on failure**, `ctx` bound to the **failed member**. Under fan-out
  the hook fires per failed member regardless of `strategy` or `--fail-fast`
  ([§10.7](#107-concurrency-fan-out-not-dags)); what siblings do is
  independent. "Failed" means *this member's own* phase raised — a member
  stopped by someone else's failure ([pinned](#pinned-phase-failure),
  [cancelled](#cancelled-member)) fires no `on_failure`.
- Receives the structured `err` ([§6.1](#61-error-model)); branch on `err.kind`
  / `err.phase`.
- **String sugar:** `on_failure = "rollback"` runs that task on the failed
  member — the common case. The sugar is deliberately **coarse**: it fires on
  any phase failure and can't tell which phase mutated state, so a
  release-style deploy that fails *before* activation still runs rollback. If
  rollback must follow a specific phase (e.g. `activate`), use the function
  form and dispatch on `err.phase` (below).
- If the hook itself fails, both errors are reported; the original is never
  masked.
- `--dry-run` ⇒ the hook is shown in the trace, not executed.

**`finally = function(ctx, summary)`** — the always-run cleanup/report hook.
Runs after a member's phases complete (and after `on_failure`, if it failed),
regardless of success.

- Runs **per member**, `ctx` bound to that member — same fan-out as phases.
  Does **not** run on pinned-phase targets (build00, localhost); pinned
  cleanup is a phase in the list or the pinned phase's own body. (A pinned
  phase is fail-fast-gated, so always-run cleanup on a pinned target is a
  known gap — [open question — `finally` for pinned phases](#oq-pinned-finally).)
- `summary` is the member's run record (shape below); branch on `summary.ok`,
  `summary.err.phase`, or walk `summary.phases`.
- Reads `ctx.shared` like any phase (one bag per task run, §6). Don't **write**
  `ctx.shared` from `finally` under `parallel` (race, §6).
- **Cannot change pass/fail.** If `finally` raises, its error is reported
  alongside the phase error and the member stays failed; on success it cannot
  un-fail a member (same "no recovery" rule as `on_failure`).
- `--dry-run` ⇒ the hook is shown in the trace, not executed.

<a id="pinned-phase-failure"></a>
**Pinned-phase failure fails the task, not any member.** When a pinned phase
fails, no member's own code raised. Attribution:

- The task fails and the run stops at the pin (fail-fast, as ever). **No
  member fires `on_failure`** — that hook is for a member's *own* failed
  phase. Firing `on_failure = "rollback"` fleet-wide because a shared build
  died before touching anyone would be the coarse-sugar trap above, baked
  into the model.
- **`finally` runs iff the member started** — at least one of its fan-out
  phases has status `"ran"` or `"failed"`. This is the general rule, not a
  pin special case: it also covers members never reached under `serial` /
  `rolling` fail-fast. Under the barrier model
  ([§6](#pinned-phase-execution-model)), a mid-list pin failure means every
  member completed the earlier block — all get cleanup; a *leading* pin
  failure (build first) means no member started — none do.
- Every phase a member never reached records `status = "pending"` in its
  summary; the pinned row records `"failed"` with its err (same row for
  every member, as always).
- For a member stopped by a pin, `summary.ok = false` and `summary.err` is
  the pinned phase's error — `err.phase` names the pin, so `finally`
  dispatches on it like any other failure.
- The pinned target's own cleanup is the pinned phase's body (`pcall`,
  `fs.withlock` scoping) — member hooks never run against a pinned target.
  Whether pinned phases need their own `finally` is an
  [open question](#oq-pinned-finally).
- A pin failure never *cancels* a member, because a pin is a barrier: no
  member chain runs while a pinned phase does. At a pin failure every member
  has either completed the earlier block or not started — never mid-phase.
  Cancellation is a fan-out-only outcome (below).

<a id="cancelled-member"></a>
**Cancelled members under fail-fast.** `fail_fast = true` / `--fail-fast`
stops in-flight siblings when one member fails
([§10.7](#107-concurrency-fan-out-not-dags)). A member stopped that way is
**cancelled**: it started, nothing of its own failed, and it is neither
`failed` (no error of its own) nor `pending` (it was not "not reached").

- **Where it can happen:** `parallel` or `rolling` **with** fail-fast only.
  `serial` runs one member at a time, so there is no in-flight sibling to
  cancel; `parallel`'s continue-default and `rolling`'s drain-the-batch
  default let in-flight members finish normally; a pin failure is a barrier
  (above). No other *failure* produces a cancelled member.
- **The other trigger is the operator.** Ctrl-C cancels by these same rules,
  under every strategy, with only the message differing
  ([§9](#interrupting-a-run)). One outcome, two triggers — an interrupt is not
  a second concept.
- **Cancellation is checked at op dispatch, not mid-op.** The op already in
  flight runs to completion — relay does not kill the remote process, and its
  side effect stands. The member's chain stops at the *next* op, which raises
  `err.kind = "cancelled"`. Cancellation bounds new work; it does not undo
  work already done. That is exactly why a cancelled member gets `finally`.
- **`pcall` cannot resurrect a cancelled member.** The raise is an ordinary
  Lua error, so a `pcall` around one op can catch it — but every subsequent
  op dispatch raises again, and relay records the phase as `"cancelled"` and
  starts no further phase however the body returned. A swallowed cancel buys
  local Lua up to the next op, nothing more.
- **Hooks:** `on_failure` does **not** fire (the hook is for a member's own
  failed phase — same reason a pin failure fires none). `finally` **does** —
  a cancelled member started by definition, so the general started ⇒ cleanup
  rule applies, and a member cancelled mid-`stage` is precisely the one with
  a half-uploaded tarball to remove.
- **Summary:** the in-flight phase records `status = "cancelled"`, phases
  after it `"pending"`, phases before it their real outcome.
  `summary.ok = false` and `summary.err` is the cancellation error —
  `kind = "cancelled"`, `phase` = the member's own in-flight phase, `message`
  naming what stopped the run — the member and phase that triggered fail-fast,
  or the operator interrupt. It carries no
  `op` / `intent` / `executed` / `exit_code`: no op of this member's failed.
  (`summary.err` stays non-nil whenever `ok` is false, as everywhere else.)
- **Hazard:** a `finally` that dispatches on `summary.err.phase` alone treats
  a cancelled member like a failed one. Usually right — a member cancelled
  mid-`activate` may hold a half-swapped symlink — but gate on
  `summary.err.kind ~= "cancelled"` when only a real failure should roll back.

**The `summary` arg** — the member's full run record:

```lua
summary = {
  ok       = false,              -- this member succeeded end-to-end
  task     = "deploy",
  target   = "web01",            -- == ctx.self.name
  strategy = "rolling",
  phases   = {                   -- the phase list, this member's view
    { name = "build",   target = "build00",  status = "ran",    scope = "pinned" },
    { name = "deploy",                          status = "failed", err = <err>, scope = "fanout" },
    { name = "smoke",   target = "localhost", status = "pending", scope = "pinned" },
  },
  err      = <err>,              -- == the failed phase's err; nil if ok
  started  = 1710000000,         -- unix seconds, like fs.stat's mtime
  elapsed  = 3.4,
}
```

- `status`: `"ran"` | `"skipped"` (`when=false`) | `"failed"` | `"pending"`
  (not reached — fail-fast or a pinned-phase failure stopped the run before
  it) | `"cancelled"` (started, then stopped by a sibling's failure under
  fail-fast; [above](#cancelled-member)).
- `scope`: `"pinned"` (ran once globally; same row for every member) |
  `"fanout"` (per-member status).
- `err`: the structured error from §6.1; `nil` when `ok`. The error that
  ended this member's run: its own failed phase's err, or the failed pinned
  phase's err when a pin aborted the task. `== summary.phases[k].err` for the
  failing phase either way.
- Pinned phases appear in every member's summary (they ran once, in list
  order); fan-out phases reflect this member's own outcome.
- Which server / which group: `ctx.self.name` (== `summary.target`) and
  `ctx.group` (the GroupRef, `nil` if not a group task; §6).

**Auto-rollback (sugar):**

```lua
local svc = require("recipe.service")

task("deploy", {
  target = "web01",
  phases = {
    { name = "stage",    run = function(ctx)
        ctx.fs.upload(cfg.tarball, "/opt/app/app.tar.gz")
        ctx.fs.extract("/opt/app/app.tar.gz", "/opt/app")
      end },
    { name = "activate", run = function(ctx)
        ctx.fs.symlink("/opt/app", "/opt/app-active", { atomic = true })
      end },
  },
  on_failure = "rollback",
})

task("rollback", function(ctx)
  -- swap /opt/app-active back to the prior release, then restart
  svc.restart(ctx, "myapp")
end)
```

**Dispatch on the failing phase** — `err.phase` centralizes per-phase cleanup,
so there are no phase-level hooks:

```lua
local svc = require("recipe.service")

on_failure = function(ctx, err)
  ctx.log.error(("%s failed [%s]: %s"):format(err.phase, err.kind, err.message))

  if err.kind == "exit" and err.exit_code == 137 then
    return                       -- OOM-kill; transient, don't roll back
  end

  if err.kind == "transport" then
    ctx.localhost.run({"curl", "-sf", ALERT, "-d", ctx.self.name .. " unreachable"})
    return                       -- ctx likely dead; notify only
  end

  if err.phase == "migrate"  then restore_db_backup(ctx) end
  if err.phase == "activate" then rollback_to_prior(ctx) end

  if ctx.fs.exists("/opt/app/app.tar.gz") then ctx.fs.remove("/opt/app/app.tar.gz") end
  svc.restart(ctx, "myapp")
end
```

**Order, per member.** phases (fail-fast) → `on_failure` (if failed) →
`finally` (always). On success: phases → `finally`. A hook that itself fails
reports its error alongside; the original is never masked, and the member's
pass/fail is unaffected by hook outcome. Success-path hooks
(`before`/`after`/`on_success`) are still just phases — phase 1 is your
"before," the last phase is your "after"; `err.phase` / `summary.err.phase`
give per-phase dispatch centrally, so there are no phase-level hooks.

**Per-member cleanup with `finally`:**

```lua
finally = function(ctx, summary)
  -- always: clean up this member's staged tarball
  local tmp = "/tmp/app-" .. (ctx.shared.sha or "") .. ".tar.gz"
  if ctx.fs.exists(tmp) then ctx.fs.remove(tmp) end

  if summary.ok then
    ctx.log.info(("%s deployed in %.1fs"):format(ctx.self.name, summary.elapsed))
    return
  end
  -- failed: dispatch on which phase
  if summary.err.phase == "activate" then rollback_to_prior(ctx) end
end
```

## 7. Operations (core)

Every operation hangs off `ctx` (the current target) and runs immediately,
returning its real result. The forms below are the primary, documented forms.

This is the whole core surface, and it is short on purpose: the agent
implements every one of these itself. Anything that drives a foreign binary —
packages, git, service control — is `run` with a name on it, and ships as an
editable recipe instead ([§11.17](#1117-the-corerecipe-line)).

### 7.1 `run`

**`run(cmd, opts?) -> { exit_code, stdout, stderr, ran, executed, timed_out? }`**
(field meanings in [§13](#13-result-shapes); `timed_out` is present only on a
`timeout` kill)

`cmd` is either a **string** (run as a shell command — the primary form) or a
**table** (an argv array, run with no shell — the safe-interpolation form).

```lua
-- String: shell. The primary form for literals and pipelines.
ctx.run("nginx -t")
ctx.run("apt-get install -y nginx")
ctx.run("tar -xzf app.tar.gz -C /opt/app")
ctx.run("uname -a")                         -- .stdout == "Linux web01 ...\n"

-- Table: argv, no shell. Use this when interpolating variable data.
local ref = "main"
ctx.run({"git", "checkout", ref})           -- `ref` is a single arg, never word-split
ctx.run({"curl", "-sf", url, "-o", path})   -- url/path can't inject shell
```

**Why both forms are first-class.** A shell string is the natural way to write
a command you already think of as a command (pipelines, `&&`, redirects). An
argv table is the natural way to keep a variable value from being
re-interpreted by a shell. v3 does not choose for you; it documents when each
is appropriate:

- Literal command, pipeline, or shell syntax → **string**.
- Command with a variable argument → **table**, so the variable is one argv
  element and cannot inject.
- Escalated op on a `via = "sudoers"` host → **table**, so sudo is handed the
  real command instead of `/bin/sh -c '…'` and a per-command rule can match it
  ([§10.4](#104-privilege-in-depth)).

```lua
-- DON'T: variable in a shell string risks injection / word-splitting
ctx.run("rm -rf " .. user_path)             -- user_path = "foo; rm -rf /"  💥

-- DO: table form keeps user_path as a single argument
ctx.run({"rm", "-rf", user_path})
```

The table form removes the *shell*, not the need to check the value: `rm -rf`
with `user_path = "/"` deletes exactly what you asked it to, argv or not.
Injection safety and input validation are different jobs.

**`opts`** (optional, both forms):

| Field | Default | Meaning |
|---|---|---|
| `cwd` | resolved workdir | working directory; the workdir ladder (below) |
| `env` | — | augment (not replace) the environment for this op; keys must match `[A-Za-z_][A-Za-z0-9_]*`. Top of the `env`/`env_files` ladder (host/task/phase below); see below. |
| `as` | resolved default | run as this identity (§8); the top of the identity ladder, overriding the host/task/phase default |
| `ignore_exit` | false | a non-zero exit fails the phase unless `true` |
| `read_only` | false | this command only *observes* the target: classify it as a **read**, so `--dry-run` executes it instead of stubbing it (see below) |
| `onlyif` | — | a guard; run the main command only if the guard succeeds (see below) |
| `unless` | — | a guard; run the main command unless the guard succeeds (see below) |
| `stdin` | — | a string piped to the child's stdin, then closed (see below) |
| `message` | — | a human label for the log line |
| `tty` | false | allocate a pseudo-terminal; merges stderr into stdout (see below) |
| `timeout` | — | seconds; on expiry send `kill_signal`, then `SIGKILL` after a 5s grace. `exit_code` is the wait status (`128 + signal`, §13) and the result carries `timed_out = true`. Pass `ignore_exit = true` to branch instead of failing the phase. `nil` = no timeout. |
| `kill_signal` | `SIGTERM` | signal name sent on `timeout`, before the SIGKILL grace (`"SIGTERM"`, `"SIGINT"`, …). Applies to the guards too (inherited like `cwd`/`env`/`as`). |

**`read_only` — declare a probe.** `--dry-run` stubs every `run`
([§4.4](#44-dry-run)), which is right for a command that changes something and
wrong for one that only looks: a probe comes back `exit_code = 0, stdout = ""`
and its caller reads a fabricated answer — the branch it gates then takes the
wrong side for the whole preview. `read_only = true` classifies the command as
a **read** ([§6.1](#61-error-model)), so it really executes under `--dry-run`
and returns the target's actual state. This is what lets a recipe ship probes
that behave like core reads — `git rev-parse HEAD`, `pkg info -e nginx` — and
it is why core does not need an op per tool
([§11.15](#1115-a-package-recipe-the-other-recipe-shape),
[§11.16](#1116-a-git-recipe)).

Two things it does not do. It does not change `run`'s contract: the return is
still the full result table and a non-zero exit still fails the phase unless
`ignore_exit = true` — one op, one shape, whatever the classification. And it
is not verified: relay cannot know whether your command mutates, so
`read_only` is an assertion by the author, the same class of promise as
`when`'s purity contract ([§10.5](#105-assertions-host-expect--preconditions)).
Marking a mutating command `read_only` makes `--dry-run` mutate the target,
which is exactly the promise dry-run exists to keep — so mark only what you
would be content to run against production during a preview.

**Working directory (`cwd`, `workdir`) — lowest → highest.** The working
directory for a `run` (its `cwd` opt) and for any relative target path (`fs.*`)
is the **most specific non-nil** rung of the ladder below — the scope closest
to the op wins:

1. `host.workdir` — the host default (lowest).
2. `task.workdir` — narrows the host default for a whole task.
3. `phase.workdir` — narrows the task/host default for a phase.
4. the per-op arg — `cwd` on `run`, the path itself on `fs.*` (highest).

A `workdir` is a string or `function(ctx) -> string`. A literal is checked at
**plan time**; the resolution is **per target at connect time**, because both
`~/` and the function form need a `ctx.self` that does not exist until the
handshake ([§4.3](#43-declaration-then-execution)). `~/…` expands to
`ctx.self.home` (per the uniform `~` rule, §5.1); `/abs`
is taken as-is; a relative `workdir`
is a plan-time error (it *is* the anchor, not relative to anything else). With
no `workdir` anywhere, the default is per-target deterministic: `ctx.self.home`
on a remote host, the config dir on `ctx.localhost`, the jail root on a jail
target — surfaced read-only as `ctx.self.workdir`. The ladder mirrors identity
precedence (`as`, §8) so "who does it" and "where it runs" compose the same
way.

**Environment (`env`, `env_files`).** The env a `run` runs with is the merge
of a ladder, narrowest wins:

1. `host.env_files` then `host.env` — the host default (lowest). `env_files`
   merge in list order (later wins); `host.env` (inline) overrides the files.
2. `task.env_files` / `task.env` — narrow the host default for a task.
3. `phase.env_files` / `phase.env` — narrow the task/host default for a phase.
4. the per-op `env` opt (highest).

`env_files` is one path, an array of paths, or `function(ctx) -> string|array`
(the function form resolves per target at connect time, like `workdir`). An entry may be
`relay.secret_file(path)` to mark every key parsed from that file secret
(§7.1, below). Paths resolve
**operator-side** — `~/`→operator home, `/abs`→as-is, `rel`→config dir (§5.1)
— so the planner reads them; the merged values flow to the agent in the op's
env list, folded as `/usr/bin/env -- K=V ...` so they survive sudoers
`env_reset` (§5.1). Files are dotenv-format: keys match
`[A-Za-z_][A-Za-z0-9_]*` (same rule as inline `env`); values unquoted,
single-, or double-quoted; an `export` prefix and `#` comments are allowed.

`env_expand` (host-level, default **true**; `false` to opt out) expands
`$VAR`/`${VAR}` in the merged env values against the merged map itself. It
never consults OS env — that path is the existing
`relay.env(name, default)` — so a parse depends only on the repo's files. An
expansion reference with no key in the map is an error (fail loud,
not silent-empty). **`$$` is a literal `$`** (the compose/systemd convention),
for values that legitimately contain one — a generated password, or a
`${PLACEHOLDER}` the *application* expands at runtime. Without the escape such
a value would be unrepresentable without turning expansion off for the whole
host. Under `env_expand = false` nothing is expanded and nothing is unescaped:
`$$` stays two characters, because WYSIWYG means what it says.

**When the map is built.** Parse, merge, and expand happen as each rung of the
ladder is read, which is three different moments
([§4.3](#43-declaration-then-execution)) — and every one of them can fail on a
missing file, a parse error, a bad key, or a circular reference:

- **plan time** — literal `env`/`env_files` on `host{}`, the task, or a phase.
  This is the common case, so the common failure (a typo'd path, a malformed
  dotenv) still fails before relay connects to anything.
- **connect time** — a `function(ctx)` `env_files`, resolved per target, then
  parsed and merged into that target's map.
- **dispatch time** — the per-op `env` opt, merged over the rest at the call
  site. Its values expand against the resulting map, so an op may legitimately
  reference a key a lower rung supplied.

The ladder mirrors `cwd`/`as` so "who does it", "where it runs",
and "what env it sees" compose the same way.

**Secrets (`relay.secret`, `relay.secret_file`).** A value or a whole dotenv
file can be marked secret so relay **redacts it in every record** — `executed`
(§6.1), error messages (§13), and the audit log (`--log-file`, §9) — while the
**real value still reaches the child process**. Redaction lives at the
recording layer, never in dispatch.

`relay.secret(v)` tags one inline `env` value:

```lua
ctx.run("migrate", { env = {
    APP_ENV     = "production",
    DB_PASSWORD = relay.secret(ctx.vars.db_password),   -- recorded as <redacted>
}})
```

`relay.secret_file(path)` tags a dotenv so **every key parsed from it** is
secret — the common case, since secrets usually live in a file, not inline:

```lua
host({ ..., env_files = { "app.env", relay.secret_file("secrets.env") } })
```

Both are **markers, not behavior** — they label data for the recording layer;
the child sees the real value through the `/usr/bin/env -- K=V` wrap exactly as
an unmarked value would. The file path is recorded as-is (it sits in
`relay.lua`; the audit record carries merged env values, not source paths) —
only the parsed values are redacted. Type-check: an `env` value is
`string | secret-marker`; an `env_files` entry is `string | secret-file-marker`;
anything else is an error, raised when that rung is read (plan time for a
declared one, dispatch time for a per-op `env`).
`escalate.password` (§10.4) takes the same
markers — the secret reaches the child via stdin (`sudo -S`), not `env`, but
the redaction and marker rules are identical.

Three boundaries, stated plainly:

1. **Opt-in — relay never guesses from key names.** A forgotten
   `relay.secret` / `relay.secret_file` logs the value verbatim. Explicit beats
   magic (the reason §42 rejected name-based guessing); marking is your job.
2. **Redacts relay's records only — not the child's output.** A command that
   prints its own env (`run("printenv")`, a service logging its config) still
   leaks via captured stdout, which `--log-file` carries verbatim. Relay can't
   prevent that — the program's doing.
3. **Never argv.** A secret in argv
   (`run({"tool","--pw",secret})`) is `ps`-visible on the target; redaction
   can't help, and `relay.secret` does not apply there. Route secrets through
   `env` or stdin (`escalate.password`, §10.4) — both are non-argv channels.

A non-zero exit fails the phase by default. Assign the result and pass
`ignore_exit = true` to branch instead:

```lua
local r = ctx.run("grep -q '^myapp:' /etc/passwd", { ignore_exit = true })   -- note the colon
if r.exit_code ~= 0 then
  ctx.run("useradd -r myapp")
end
```

The trailing colon is the whole probe: `^myapp` also matches a `myapp2` line,
so the guard reports the account exists on a box where it does not.

**Idempotency without `&&`/`||`** — `onlyif` / `unless` run a guard first.
The guard value takes **the same two forms as `cmd`**: a string (run as a
shell command) or a table (an argv array, no shell). A guard that interpolates
variable data must use the argv form, for the same injection-safety reason as
`cmd`:

```lua
-- Install nginx only if it isn't already there (literal guard → string)
ctx.run("apt-get install -y nginx", { unless = "test -x /usr/sbin/nginx" })

-- Variable guard → argv table, injection-safe
local pkg = "nginx"
ctx.run({"apt-get", "install", "-y", pkg}, { unless = {"test", "-x", "/usr/sbin/" .. pkg} })
```

**`dpkg -l <pkg>` is not the probe**, tempting as it looks: it exits 0 for a
package that was removed with its config files left behind (`rc` state), so a
guard built on it skips the install on exactly the boxes that need it. A path
test is the honest one-liner; real package-state detection belongs in a recipe
(`pkg.installed`, [§11.15](#1115-a-package-recipe-the-other-recipe-shape)),
which is one of the reasons that recipe exists.

The guard's exit code is the predicate: `onlyif` runs the main command when
the guard exits 0; `unless` runs it when the guard exits non-zero. A guard
**never** fails the phase on its own exit — a non-zero `onlyif` guard is a
soft skip (`ran = false`), not an error.

**Guard opts are inherited, not nested.** The guard runs with the main
command's `cwd`, `env`, `as`, `timeout`, `kill_signal`, and shell form (string
vs. argv is already in the guard value). A guard value cannot carry its own
opts table — that would collide with the argv form. The remaining `opts`
fields do not apply to the guard:

- `onlyif` / `unless` — recursion is rejected.
- `ignore_exit` — the guard's exit *is* the predicate; it cannot be ignored.
- `tty` — would corrupt exit-code capture.
- `stdin`, `message` — main-command only.
- `read_only` — not applicable: a guard is always classified a read, so it
  executes under `--dry-run` and its verdict decides whether the main command
  is stubbed or skipped ([§4.4](#44-dry-run)).

**The guard gets its own `timeout` budget, not a share of one.** `timeout = 10`
on a `run` with a guard bounds the guard at 10s and the command at 10s — the
worst case doubles (plus the 5s SIGKILL grace on each) but stays bounded, and
neither has to reason about how much of a shared budget the other spent. A
guard killed by its timeout exits non-zero like any other failing guard, so
`onlyif` skips the main command and `unless` runs it; it never fails the phase
and never hangs it. That is the reason `timeout` inherits at all: a
main-command-only `timeout` would leave a hung guard blocking the deploy
forever, with `kill_signal` — meaningless without a timeout — already declared
inherited.

If a guard genuinely needs different execution opts (a different identity,
working directory, or environment), write it as an explicit `run` and branch
in Lua instead — `onlyif` / `unless` are sugar for the common, same-context
case:

```lua
-- Guard needs a different `as` than the main command → explicit form
local r = ctx.run({"test", "-x", "/usr/sbin/nginx"}, { ignore_exit = true, as = "root" })
if r.exit_code ~= 0 then
  ctx.run({"apt-get", "install", "-y", "nginx"}, { as = "myapp" })
end
```

**Stdin.** `opts.stdin` is a string piped to the child's standard input, then
closed. Default (nil) means no stdin — the child's stdin is `/dev/null`, never
inherited from the agent (an inherited stdin would let a command silently block
on input the script never sends). Lua strings are byte strings, so binary input
is fine:

```lua
-- Pipe a SQL dump into mysql. Reads return (value, err); check before use.
local dump, derr = ctx.localhost.fs.read("schema.sql")
assert(dump, "could not read schema.sql: " .. (derr or "?"))
ctx.run("mysql mydb", { stdin = dump })

-- Drive a prompt-driven tool
ctx.run("myapp setup", { stdin = "yes\nyes\nno\n" })

-- Works on the argv form too, and is injection-safe for the dump path
ctx.run({"mysql", "mydb"}, { stdin = dump })   -- reuse the checked dump above
```

**One stdin conflict — a per-op password wrap.** `sudo -S` reads the first line
of stdin as the password ([§10.4](#104-privilege-in-depth)), so an op whose
own wrap is `sudo -S -p '' -u U C` **cannot also set `opts.stdin`** — the
password would eat the first line of the script's data. relay rejects that
combination at dispatch time — the op's resolved identity decides whether it
gets a `-S` wrap at all — so it fails before the op is sent, and
`relay validate` flags the literal case without connecting: use `stdin` *or* a
per-op password escalation, not both. (Rare in practice — split the op, or grant NOPASSWD for that one command.)

The conflict is with the **wrap**, not with having a password at all. Under
`via = "worker"` (the default) the password is spent once at connect on
`sudo -S -p '' -i`; every op after that is a free drop from root and carries no
`-S`, so `stdin` and a password `escalate` compose there and relay does not
reject them. Only `via = "sudoers"` wraps per op, so only it conflicts.

**Pseudo-terminals (`tty`).** `opts.tty = true` allocates a pty for the child.
The consequences are deliberate and documented, because a pty changes the
result shape:

- **One stream.** A pty has a single output channel, so **stderr folds into
  stdout**; the result's `stderr` is empty (`""`). Scripts that branch on
  `stderr` must not set `tty = true`.
- **The child sees a terminal**, so it emits color, line-buffers instead of
  block-buffers, and interactive prompts behave (paired with `stdin`).
- **`stdin` flows through the pty**, so line editing and control characters
  work for interactive tools.

Default is **`tty = false`** — separated pipes, distinct `stdout`/`stderr` in
the result, predictable regardless of where `relay` runs. Set `tty = true` only
when a command specifically needs a terminal (color, a TUI, a prompt that
checks `isatty`). v2's "auto = on when the operator's terminal is a TTY" made
the result shape depend on the operator's environment; v3 defaults off so a
script means the same thing on a laptop and in CI.

```lua
-- A tool that disables color unless it sees a TTY
ctx.run("pytest", { tty = true })

-- Simpler: a flag-aware tool keeps stderr separate and is CI-friendly
ctx.run("pytest --color=yes")
```

**Live streaming.** With or without a pty, `stdout` and `stderr` stream to the
operator's console as they arrive (the architecture in §1.1), and the result
holds the full captured text once the command exits. With `tty = true` the
single merged stream is streamed live.

**Exit codes.** `exit_code` is the process wait status: `0` for success,
`1–255` for a normal non-zero exit, and `128 + signal` when the process is
killed by a signal (e.g. `137` = SIGKILL). A non-zero `exit_code` fails the
phase unless `ignore_exit = true`.

### 7.2 `fs`

Filesystem, native Go on the agent, idempotent where meaningful. Paths are in
the executor's own namespace (jail-relative on a jail target); a relative path
resolves via the workdir ladder (§7.1). Mutating ops return `{ changed }`.

```lua
ctx.fs.mkdir_all("/opt/myapp")                       -- à la os.MkdirAll
ctx.fs.write("/etc/myapp.conf", CONTENT, {           -- checksum-verified
  owner = "myapp", group = "myapp", mode = "0640",
})
ctx.fs.append("/var/log/myapp.log", "line\n")
ctx.fs.symlink("/opt/myapp/shared/.env", "/opt/myapp/.env", { force = true })
ctx.fs.symlink("/opt/app/r/20240101", "/opt/app/current", { atomic = true })
     -- atomic: temp symlink + rename(2) → zero-window pointer swap
     --   (the primitive every release-style activate/rollback is built on)
ctx.fs.remove("/tmp/stale")                          -- missing path = clean no-op
ctx.fs.remove("/opt/old", { recursive = true })      -- recursive is never the default
ctx.fs.copy("/src/file", "/dst/file")
ctx.fs.copy_dir("/src/dir", "/dst/dir")
ctx.fs.touch("/var/run/myapp.pid")
ctx.fs.upload("build/app.tar.gz", "/opt/app/app.tar.gz",   -- operator fs → target fs (streamed, see below)
  { owner = "myapp", group = "myapp", mode = "0755" })      -- same three opts as write; all optional
ctx.fs.download("/opt/app/app.tar.gz", "tmp/app.tar.gz")   -- target fs → operator fs (streamed)
ctx.fs.extract("/opt/app/app.tar.gz", "/opt/app")   -- untar into dest, creating it
ctx.fs.archive("/opt/app", "tmp/app.tar.gz")        -- reverse of extract: tar (+gzip) a path
ctx.fs.chmod("/etc/myapp.conf", "0640")             -- set mode on an existing file
ctx.fs.chown("/opt/app", { owner = "myapp", group = "myapp" })  -- omit a key ⇒ leave it unchanged
ctx.fs.rename("/opt/app/r/old", "/opt/app/r/20240101")  -- rename(2); atomic same-FS, cross-FS = error
ctx.fs.mktemp({ dir = "/tmp", prefix = "relay." })  -- → path of a fresh temp file (returns the path,
     --   not {changed}; { directory = true } ⇒ a temp dir). Raises on error like an action.

-- read-only ops (execute under --dry-run); all return (value, err):
local content, rerr  = ctx.fs.read("/etc/myapp.conf")       -- string, nil on error
local exists,  eerr  = ctx.fs.exists("/opt/myapp/.env")     -- bool,   nil on error
local target,  lerr  = ctx.fs.readlink("/opt/app/current")  -- symlink target (one hop), nil on error
local entries, derr  = ctx.fs.list("/opt/app/releases")     -- { "20240101", … }, nil on error
local st,      serr  = ctx.fs.stat("/opt/app/current")      -- { type, mode, uid, user, gid, group, size, mtime }
local rp,      perr  = ctx.fs.realpath("/opt/app/current")  -- fully resolved path (readlink -f), nil on error
local matches, gerr  = ctx.fs.glob("/opt/app/releases/*")   -- { "/opt/app/releases/20240101", … }; [] if none
local digest,  herr  = ctx.fs.hash("/opt/app/app.tar.gz")   -- sha256 hex (algo = "sha256" default), nil on error
```

**Modes are octal strings** — `"0640"`, not `0640` (which Lua reads as decimal
640). go-lua has no octal literals; an integer mode is a dispatch-time error
(caught at the call site before the op is sent, and by `relay validate` when
the mode is a literal).

**On a jail target, two of these are namespace-sensitive.** A symlink's target
is stored text, so it is written in the namespace of the *link*, not of the
machine running the op; and `owner`/`group` names resolve against the jail's
passwd under `fs_access = "attach"` but the host's under `"mountpoint"`, where
numeric uid/gid is the portable spelling. Both are specified in
[§10.2](#102-freebsd-jails) and [§10.3](#103-tagged-paths); neither matters on
a plain host target.

Reads follow the Lua/Go convention — `(value, err)`, never raising. `value` is
`nil` (for `fs.read`) or `false` (for `fs.exists`) on failure; `err` explains
why. Ignore `err` and the common `if ctx.fs.exists(p) then ...` still works
(Lua tests only the first return):

```lua
local c, err = ctx.fs.read("/etc/myapp.conf")
if not c then
  ctx.log.warn("could not read config: " .. (err or "?"))
else
  ctx.log.info("config is " .. #c .. " bytes")
end

-- to make a read's failure stop the phase, assert on it:
assert(c, "config unreadable: " .. (err or "?"))
```

**Metadata, move, and inventory.** Beyond create/destroy, `fs` covers the
verify-then-remediate loop without dropping to `run("chmod …")` / `run("find
…")`:

- **`fs.stat(path)` → `(info, err)`** — `info = { type, mode, uid, user, gid,
  group, size, mtime }`. `type` is `"file"`/`"dir"`/`"symlink"`/`"other"`;
  `mode` is the octal string (e.g. `"0755"`); `uid`/`gid` are numbers,
  `user`/`group` their resolved names (or `nil` if unresolvable); `mtime` is
  unix seconds. Returns `(nil, err)` for a missing path — so "does it exist
  *and* what is it" is one call, not `exists` + `run("stat …")`.
- **`fs.chmod(path, mode)` / `fs.chown(path, { owner, group })`** — set mode /
  owner-group on an existing path, standalone (the same fields `write`/`upload`
  reconcile at create time). `owner`/`group` are names or numeric uid/gid; omit
  a key to leave that half unchanged, and passing neither is a dispatch-time
  error (a `chown` that changes nothing is a typo, not a no-op). The table is a
  required operand, not an opts table — `chown` has no optional positional
  ([§12](#12-calling-conventions)). Actions — raise on error, return
  `{ changed }`.
- **`fs.rename(src, dst)`** — wraps `rename(2)`. Atomic where the OS offers it
  (same filesystem); a cross-filesystem rename is an **error**, not a silent
  copy+remove — if you need a cross-FS move, write it explicitly in Lua. The
  same primitive `symlink{atomic=true}` is built on, exposed for non-symlinks.
- **`fs.archive(src, dst, opts?)` / `fs.extract`** — a matched pair.
  `archive(src, dst_tarball, { compress = "gzip" })` tars `src` (file or dir)
  into `dst_tarball`; `compress = "none"` for an uncompressed tar (default
  `"gzip"`, matching `extract`'s auto-detect on read). Both paths resolve in
  the executor's namespace — `archive` is *not* a transfer op.
- **`fs.mktemp({ dir?, prefix?, directory? })` → path** — a fresh temp file (or
  dir with `directory = true`), under `dir` (default the OS temp dir) with
  `prefix` (default `"relay."`). The one mutating op that does **not** return
  `{changed}` — it returns the created path, since the path is the point. That
  shape is also why `--dry-run` gives it a synthetic path rather than the
  generic stub ([§4.4](#44-dry-run)).
- **`fs.realpath(path)` → `(string, err)`** — fully resolves a path, following
  every symlink (`readlink -f`); works on non-symlinks too (returns the
  canonical path). `readlink` is one hop; `realpath` is the whole chain.
- **`fs.glob(pattern)` → `({paths}, err)`** — shell glob (`*`/`?`/`[...]`, same
  syntax as `relay.path.match`) over the executor's filesystem. Returns `{}`
  (not `nil`) when nothing matches; `(nil, err)` on a bad pattern or an
  unreadable directory. `list` is one directory, non-recursive; `glob` is the
  pattern form.
- **`fs.hash(path, algo?)` → `(string, err)`** — hex digest of a file's
  contents, `algo` defaults to `"sha256"` (also `"sha1"`, `"md5"`). The
  transfer path already verifies integrity by checksum; `hash` verifies
  *content* — the "is this the artifact I expected?" / "already deployed?"
  gate.

**Streaming transfer — `upload`, `download`, and large writes.** File
bytes stream over the bidirectional channel in chunks keyed by request id,
checksum-verified; `WriteFileOp` carries only length and checksum, so no file
rides whole inside a protobuf op. Three Lua ops map onto this:

- **`fs.write` / `fs.append`** — the content is a Lua string the runtime
  already holds; it is streamed to the agent (not inlined in the op), verified
  by checksum, and applied atomically. This is the path for configs and
  anything that fits comfortably in Lua memory. There is no hard size cap, but
  a multi-GB Lua string is a smell — reach for `upload` instead, which never
  materializes the whole file in Lua. Templated content is `fs.write` of a
  `relay.render` result (Appendix A), not an `fs.template` op: rendering is
  pure string work with no target involvement, so it happens planner-side and
  `write` still sees a plain string — no new op, no new protocol message, and
  the atomic-write and checksum semantics are the ones already specified here.
- **`fs.upload(local_path, remote_path, { owner, group, mode })`** — the
  runtime opens `local_path` on the **operator** and streams it chunked to the
  agent; the operator file is never held whole in Lua or in one protobuf
  message. The agent writes a temp file beside the destination, `fsync`s, and
  `rename(2)`s it into place (the same atomic-swap primitive as
  `fs.symlink{ atomic = true }`), then reconciles `owner`/`group`/`mode` — the
  same three opts `fs.write` takes, each optional, each left as the OS creates
  it when omitted. `remote_path` resolves in the executor's namespace
  (jail-relative on a jail target; `~/`→`ctx.self.home`, relative→workdir).
- **`fs.download(remote_path, local_path)`** — the reverse. The agent streams
  `remote_path` (executor namespace) back over `FILE_DATA`; the runtime writes
  it to `local_path` on the **operator** atomically (temp + `rename(2)`),
  preserving the source `mode`. Like the other mutating ops it returns
  `{ changed }` — `{ changed = false }` when the operator file already matches
  the source by checksum, so a repeated download is a clean no-op.

**Operator-side is always operator-side.** `upload`'s source and `download`'s
destination are operator filesystem paths regardless of the executor — the
data has to originate or land on the operator. So
`ctx.on(remote).fs.upload("build/x", "/srv/x")` reads `build/x` from the
**operator** (not from `remote`) and writes `/srv/x` on `remote`; likewise
`ctx.on(remote).fs.download("/srv/x", "tmp/x")` lands `tmp/x` on the
operator. To move a file between two *remote* targets, download to the
operator then upload — or build on the operator and upload once. (A target's
own filesystem is reached with `fs.copy` / `fs.copy_dir`, which never cross
the wire.)

**Locking (`fs.lock`).** Advisory file locks, via `flock(2)`, for serializing
work on a target — most often guarding against two deploys hitting the same
host at once (see `host.lock`, §5.1, which is built on this primitive).

```lua
local svc = require("recipe.service")

-- Warn and bail if another deploy holds the lock (non-blocking)
local tok, lerr = ctx.fs.lock(relay.path.join(ctx.self.home, ".relay", "app.deploy"),
                              { blocking = false })
if not tok then
  error("another relay session is already running on " .. ctx.self.name ..
        ": " .. (lerr or "?"))
end
-- lock held until this connection closes; no unlock needed

-- Or block until exclusive (serialize a migration), scoped to a function
local rv = ctx.fs.withlock(relay.path.join(ctx.self.home, ".relay", "app.migrate"), {}, function()
  ctx.run("migrate-db")
  svc.restart(ctx, "app")
  return "migrated"
end)   -- lock released here, even if restart raised
```

- **`fs.lock(path, opts?) → (token, err)`** — acquires an advisory lock on
  `path` (created if missing, with `mode`). `opts`: `exclusive` (default
  `true`, `LOCK_EX` vs `LOCK_SH`), `blocking` (default `true`; `false` ⇒
  `LOCK_NB`, fail fast when held), `timeout` (seconds; `nil` = wait forever,
  `blocking` only), and `mode` (default `"0640"`, octal string, if the file is
  created). Returns `(token, err)`: an opaque string on success; `(nil, err)`
  if not acquired ("held by another process" / "timeout"). **Never raises** —
  failing to acquire is a condition the script decides about, not a framework
  error.
- **`fs.unlock(token) → (ok, err)`** — releases a held lock. Idempotent
  (`(false, "unknown token")` on a stale token, never raises). Optional in
  practice: every lock releases when the agent connection closes (task end /
  disconnect), and `flock` auto-releases on process death — so a killed agent
  never leaves a stale lock. Use `unlock` only to release mid-task.
- **`fs.withlock(path, opts, fn) → rv`** — acquire, run `fn()`, release on
  return *or error*, then re-raise any `fn` error (transparent — the phase
  fails as if `fn` ran bare; the lock is never leaked). Returns `fn`'s values
  on success.

Locks are **per-executor**: a lock taken on `ctx` is held on this target's
agent only, not on `ctx.on(other)`. The path resolves in the executor's
namespace (`~/`→`ctx.self.home`, relative→workdir), like every `fs.*` target
path.

**Locks are reads with a side effect, so `--dry-run` gives them a rule.**
`fs.lock`/`fs.unlock` are classified reads by *shape* — they return
`(value, err)` and never raise ([§6.1](#61-error-model)) — but acquiring
creates the lock file and, unlike every other read, affects other sessions. So
under `--dry-run` `fs.lock` acquires nothing and returns a synthetic token,
`fs.unlock` accepts that token, and `fs.withlock` runs its `fn` unlocked
([§4.4](#44-dry-run)). A preview neither blocks a real deploy nor is blocked by
one, which is the same call `host.lock` makes for itself
([§5.1](#51-host--the-one-required-declaration)).

### 7.3 `http`

An HTTP client for deploy probes, webhooks, and authenticated artifact
fetches. `check` is the GET-only health probe (the common case); `request` is
the general form for any method. On `ctx` (a host target) the call runs from
the agent; on `ctx.localhost` from the operator's machine (the honest scope for
a public URL). On a **jail** target it still runs from the agent, which lives on
the physical host, so it uses the host's network stack and not the jail's — a
loopback URL there is an error rather than a probe of the wrong box
([§10.2](#102-freebsd-jails)).

```lua
-- check: GET probe, the common case
ctx.localhost.http.check("https://example.com/healthz")
ctx.localhost.http.check(url, {
  expect_status    = 200,
  timeout          = 10,        -- per-attempt seconds
  retries          = 3,         -- extra attempts (total = 1 + retries)
  retry_wait       = 2,         -- seconds between attempts
  follow_redirects = true,      -- false returns a 3xx as-is, assertable
})

-- request: any method — the deploy-webhook path (cache flush, drain, register)
ctx.localhost.http.request("POST", "https://api.example.com/deploy/hook", {
  headers = { ["Content-Type"] = "application/json" },
  body    = '{"service":"web"}',
  timeout = 10,
})
```

`check(url, opts?)` is sugar for `request("GET", url, opts)`. Both take the
same opts, both return the read shape `(result, err)`
([§6.1](#61-error-model)), and neither **raises** — `err` is set on a transport
failure or an `expect_status` violation; assert to fail the phase:

```lua
local r, err = ctx.localhost.http.check(url, { expect_status = 200 })
assert(r and r.status == 200, "unhealthy: " .. (err or "?"))
```

**The line this surface draws.** relay is Go, so `net/http` — the whole client,
its TLS stack, its redirect and proxy handling, HTTP/2 — is already linked in
and costs nothing to expose. The temptation is to expose it, and the answer is
the one [§3](#3-design-principles) principle 7 gives for `relay.render`: ship
what the job needs, not the library behind it. A deploy does three things over
HTTP — probe a service, call a webhook, fetch an artifact from somewhere that
wants credentials — and the surface below is those three with nothing left
implicit: every knob a private-infra deploy needs (a private CA, a client
certificate, a proxy, a hostname that doesn't match the address) is here, and
the machinery a browser needs (a cookie jar, session state, streaming bodies
into Lua) is not, listed by name at the end so it is never assumed. This is the
foundation recipes build on — a Slack notifier, a load-balancer
register/deregister, a registry fetch are all a `request` with a table.

**Result.**

| Field | Type | Meaning |
|---|---|---|
| `status` | integer | HTTP status of the **last** attempt |
| `body` | string | response body, decoded, capped at `max_body`. `""` when `out_file` was used |
| `headers` | table | response headers, **lowercase** keys → string |
| `url` | string | the URL the response came from — the last hop of a redirect chain, else the request URL |
| `elapsed` | number | seconds for the **last attempt**, not the sum across retries and waits |
| `attempts` | integer | attempts made; `1` when the first succeeded |
| `size` | integer | bytes written, **only** when `out_file` was used |
| `truncated` | boolean | present and `true` **only** when `max_body` cut the body |
| `dry_run` | boolean | present and `true` **only** on a stubbed call (below) |

A repeated response header joins with `", "`, which is RFC 9110's own folding
rule and lossless for every header a deploy reads (`content-type`, `location`,
`etag`, `retry-after`). It is lossy for exactly one header, `set-cookie`, which
must not be folded — and relay has no cookie jar to feed it to anyway (see
**Non-features**). One flat string-valued table is worth that.

**Request opts.** One table for both calls; `request` takes the method as its
first argument. Everything is optional.

| Field | Default | Meaning |
|---|---|---|
| `headers` | — | table of name → string, a `relay.secret` marker, or an array of strings for a repeated header. Names are sent as written |
| `query` | — | query parameters **appended** to any the URL already carries (never replacing them); key → string/number/boolean, or an array for a repeated key. **relay percent-encodes them** — go-lua has no pattern engine (Appendix A), so a script cannot correctly encode a value it did not write |
| `body` | — | request body, a string |
| `body_file` | — | request body streamed from a file rather than held in memory; an executor-side path or tagged `Path` ([§10.3](#103-tagged-paths)) |
| `form` | — | table encoded `application/x-www-form-urlencoded` and sent as the body; sets `Content-Type` unless `headers` already did. Same encoding argument as `query` |
| `out_file` | — | stream the response body to this file instead of into `body`; executor-side path or tagged `Path`. `max_body` does not apply |
| `basic_auth` | — | `{ user = "...", password = relay.secret(...) }` |
| `expect_status` | — | assert the status: a number, an array of numbers, or a class string (`"2xx"`, `"3xx"`, `"4xx"`, `"5xx"`). A violation sets `err` **and** consumes a retry |
| `timeout` | — | seconds, **per attempt**, covering connect, TLS handshake, and the whole body read. `nil` = no timeout |
| `retries` | 0 | extra attempts (total = 1 + retries) |
| `retry_wait` | 1 | seconds between attempts |
| `follow_redirects` | true | `false` returns the 3xx as-is, assertable, with `location` in `headers` |
| `max_redirects` | 10 | hops before the attempt fails as a transport error |
| `max_body` | 1 MiB | cap on the body read into `result.body`; over it the body is cut and `truncated = true`. `0` = no cap |
| `user_agent` | `relay/<version>` | sugar for `headers["User-Agent"]` |
| `tls` | the host's `tls` | TLS settings (below); merges over the host declaration **field by field** |
| `proxy` | executor env | a proxy URL to force, or `false` to bypass the executor's `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` |
| `message` | — | a human label for the log line, as on `run` |

`body`, `body_file`, and `form` are mutually exclusive; two of them is a
dispatch-time error, not a silent precedence rule. relay never sniffs or
guesses `Content-Type` for `body`/`body_file` — `form` is the one case where it
sets a header, because the encoding is the point of the field.

**`http` has no `as`.** It is in-process in the agent, not a child process, so
there is no identity to become and [§8](#8-privilege-the-common-case)'s ladder
does not apply. A request that must originate from another identity is a `run`
of a client under that identity.

**TLS (`tls`).**

| Field | Default | Meaning |
|---|---|---|
| `ca` | system roots | executor-side path to a PEM bundle. **Replaces** the system pool rather than adding to it (Go's `RootCAs`); to trust both, concatenate both into one bundle |
| `ca_pem` | — | the same bundle as a literal PEM string, shipped with the op. Mutually exclusive with `ca` |
| `cert`, `key` | — | executor-side paths to a client certificate and its key (mTLS); both or neither |
| `server_name` | the URL's host | SNI and the name the certificate is verified against — for probing `https://10.0.0.7/healthz` against a cert issued for `app.example.com` |
| `insecure` | false | skip verification entirely. Logged at `warn` on every call and flagged by `relay validate` ([§9](#9-cli)) |

Paths here are **executor-side**, like every other path an op reads: agent-side
on `ctx`, operator-side on `ctx.localhost`, and the tagged-path rules apply
unchanged ([§10.3](#103-tagged-paths)) — there is no cross-machine read. That
is precisely why `ca_pem` exists: a CA bundle is public material that lives in
the repo next to `relay.lua`, and the machine doing the probing may never have
been given a copy, so the alternative is an `fs.upload` before every probe.

**A client key gets no `key_pem`, and that asymmetry is the point.** A CA
bundle is public; a private key is not. Making it one line to ship key material
through the protocol on every op is a default worth not having — mTLS from the
agent reads the key the box was provisioned with, mTLS from `ctx.localhost`
reads the operator's own.

**Declared once on the host, overridden per call.** A private CA is a fact
about a fleet, not about a call site, so `tls` is a `host{}` field
([§5.1](#51-host--the-one-required-declaration)) inherited by every `http` call
that runs on that target, and a per-call `tls` merges over it field by field:

```lua
host({ name = "web01", hostname = "web01.example.com", user = "deploy",
       tls = { ca = "/usr/local/share/certs/internal.pem" } })

ctx.http.check("https://internal.svc/healthz", { expect_status = 200 })
-- ...inherits the bundle. Override one field, keep the rest:
ctx.http.check("https://10.0.0.7/healthz", { tls = { server_name = "internal.svc" } })
```

`ctx.localhost` is the reserved bare-operator target with no declaration to
inherit from (§5.1), so an operator-side call carries its `tls` per call — or
declares a named local target (`host{ local_ = true, tls = { … } }`) once the
same settings repeat. On a **jail** target the request runs from the host agent
like every other `http` call ([§10.2](#102-freebsd-jails)), so the jailer's
`host{ tls }` is what applies — the same declaration that governs the host's
own probes, which is the only answer consistent with it being the same network
stack.

**What consumes a retry.** An attempt fails — and is retried, up to `retries`
times — on a transport error (connection refused, DNS failure, TLS handshake or
verification failure, `max_redirects` exceeded, a body read that dies
mid-stream, `timeout`) **or** on an `expect_status` violation. Without
`expect_status`, only transport errors retry: any response the server returns is
a successful attempt, whatever its status. That is `expect_status`'s real job.
Setting `err` on a violation is derivable by hand from `r.status`; driving the
retry loop is not, and it is what makes the health-probe idiom work —
`expect_status = 200` with `retries` means "poll until the app is up or the
attempts run out" ([§11.8](#118-healthcheck-with-retry)). The result reflects
the **last** attempt, so `r.status` after exhausted retries is the last status
seen.

**Retrying a non-idempotent method is at-least-once, and relay will not pretend
otherwise.** A transport error is not proof the server did nothing — it may
have processed the `POST` and died on the response. `retries` defaults to `0`,
so this is always something a script asked for; when a webhook is a
cache flush it is free, and when it is a payment or a queue submit it needs an
idempotency key in the request, which is the server's contract and not
something relay can supply.

**Dry-run follows the method, not the op name.** The **safe** methods — `GET`,
`HEAD`, `OPTIONS` (RFC 9110's own set) — execute under `--dry-run`, because a
probe is safe to preview and a stubbed probe would feed a fabricated answer to
the branch it gates ([§4.4](#44-dry-run)). Every other method is stubbed like
any mutating op, with §4.4's optimistic-primary pattern:

```lua
{ status = <optimistic>, body = "", headers = {}, url = <request url>,
  elapsed = 0, attempts = 0, size = 0, dry_run = true }   -- err is nil
```

The optimistic `status` is `expect_status` when that is a single number, its
first element when it is an array, `200` for a class string or when
`expect_status` is absent — so a preview of a deploy whose webhook is followed
by `assert(r.status == 200)` walks past the assert and traces the rest of the
phase, instead of stopping at the first webhook. Gate on `not r.dry_run` where
the branch itself matters.

**The one exception: `out_file` makes a call mutating whatever its method
is.** A `GET` that lands
a file on the target changes the target, and dry-run's promise is that scripted
mutations do not happen — so a call carrying `out_file` is stubbed exactly like
a `POST`, writes nothing, and returns the stub above with `size = 0`. The ops
downstream of it are stubbed too, so the preview stays consistent with itself:
nothing fetched, nothing extracted.

**Fetching an artifact is why `out_file` is core.** The obvious shell form —
`ctx.run({"curl", "-fsSL", "-H", "Authorization: Bearer " .. tok, url, "-o", p})`
— is banned by relay's own rule that secrets never go in argv
([§7.1](#71-run)), and it needs `curl` on the target besides. `request` with a
secret header and `out_file` is the compliant path: in-process, on every
platform the agent runs on, with the token redacted in every record.

```lua
local r, err = ctx.http.request("GET", ctx.vars.artifact_url, {
  headers       = { Authorization = relay.secret("Bearer " .. ctx.vars.registry_token) },
  out_file      = "/tmp/app.tar.gz",
  expect_status = 200,
  timeout       = 300,
})
assert(r, err)
ctx.fs.extract("/tmp/app.tar.gz", "/opt/app/releases/" .. ctx.vars.release_id)
```

`out_file` streams to a temporary file beside the destination and renames it
only once the attempt is **accepted** — status matched, body complete — so a
404, a truncated transfer, or an exhausted retry leaves no partial file to be
mistaken for an artifact. `max_body` exists for the same wound on the in-memory
path: it defaults to 1 MiB because a probe's body is a health JSON, and without
a cap a `check` against a URL that happens to serve a release tarball pulls it
into a Lua string on the agent. Bulk bytes go to a file, not into a script.

**Secrets.** Any string-valued opt may be a `relay.secret` marker — a header
value, a `query` or `form` value, `basic_auth.password` — with the same
contract as `env` ([§7.1](#71-run)): the real value goes on the wire,
`<redacted>` goes in every record (log line, error, `--log-file`). The record
for an `http` op is method, URL (with secret query values redacted), status,
attempts, and elapsed; **request and response bodies are never recorded**, the
same way `fs.write` records a length and a checksum rather than file bytes
([§7.2](#72-fs)), so a token in a JSON body is not leaked by relay either. The
one remaining leak is a script logging its own response
(`ctx.log.info(r.body)`).

**Go behaviors that are relay's behavior, stated rather than inherited
silently:**

- **Compression.** Go's transport requests `gzip` and decodes transparently, so
  `body` is the decoded text — *unless* the script sets `Accept-Encoding`
  itself, which turns the automatic decode off and hands the body over encoded.
  Set that header only if you mean it.
- **`Authorization` across a redirect.** Go's client drops it when a redirect
  crosses to a different host, and relay does not re-add it: an authenticated
  request redirected off-host arrives unauthenticated (usually a 401) rather
  than handing the credential to whoever the `location` points at.
- **HTTP/2** is negotiated automatically over TLS. There is no knob, and there
  is no HTTP/3.
- **Proxies** come from the **executor's** environment — the agent's process
  env on `ctx` (the ssh session's, not your shell's), the relay process's on
  `ctx.localhost`. `proxy` forces one; `proxy = false` bypasses.
- **Connection reuse** is per executor and per distinct `tls` config, held for
  the session. Mechanics the agent owns, not surface ([§3](#3-design-principles)
  principle 8).

**Non-features**, named so they are not assumed: no cookie jar and no session
state carried between calls (`set-cookie` folds like any other header); no
streaming a response into Lua — a body is a string or a file; no websockets,
SSE, or HTTP/3; no automatic JSON — `body` is a string a script builds and a
string it parses; no `Content-Type` sniffing; no per-call TLS version or cipher
selection (Go's defaults, and `insecure` for the case that actually comes up).
See [open question — `http` over a unix socket](#oq-http-unix-socket).

### 7.4 `log`

Logs to the operator's console, always (not an executor). Interleaves with op
output.

```lua
ctx.log.debug("...")
ctx.log.info("...")
ctx.log.warn("...")
ctx.log.error("...")
```

### 7.5 `sleep`

```lua
ctx.sleep(2)          -- block the phase for 2 seconds
ctx.sleep(0.25)       -- fractional seconds are fine — Lua numbers are float64
```

A pacing primitive for hand-rolled poll loops (wait for a port, back off
between retries). It is neither an action nor a read — it cannot fail, raises
nothing, and returns nothing. Under `--dry-run` it is a no-op (a dry run does
not wait). Prefer `http.check`'s built-in `retries`/`retry_wait` for HTTP
polling; reach for `sleep` only when the typed ops don't cover the loop.

**Seconds, like every other duration in v3** — `run`/`fs.lock`/`http`
`timeout`, `http.retry_wait`, `summary.elapsed`. Milliseconds are deliberately
not used anywhere: the usual reason to reach for them is a language that
cannot express a fraction, and Lua's numbers are float64, so `sleep(0.25)`
says what `sleep(250)` would. One unit across the API also removes the silent
1000× error — a `sleep` in ms sitting next to a `retry_wait` in seconds reads
identical and behaves nothing alike.

## 8. Privilege (the common case)

v3's privilege model is **declare the default once, inherit on every op,
override per op.** It separates three orthogonal concerns:

- **connection identity** — who ssh dials in as (`host.user`).
- **default run-as identity** — who ops run as by default (`host.as`; `nil` =
  the connection user).
- **escalation capability** — *how* the connection user becomes a different
  identity when an op asks for one (`host.escalate`; `nil` = no escalation
  possible).

The common case — ssh in as a user who can passwordless-sudo to root — sets
`as` and `escalate`, or uses the `sudo = true` shorthand for both:

```lua
local svc = require("recipe.service")

host({ name = "web01", hostname = "web01.example.com", user = "deploy",
       as = "root", escalate = "sudo" })
-- equivalent shorthand (the 90% case):
-- host({ name = "web01", ..., sudo = true })

task("deploy", function(ctx)
  ctx.fs.write("/etc/nginx/nginx.conf", CONF, { mode = "0644" })  -- as root (inherited)
  ctx.run("apt-get install -y nginx")                              -- as root (inherited)
  svc.restart(ctx, "nginx")                                        -- a recipe is `run` too → root
end)
```

**`sudo = true` is sugar, not the primary spelling.** It expands to
`as = "root", escalate = "sudo"` (which itself defaults to NOPASSWD and the
`worker` strategy). `sudo = "<name>"` expands to
`as = "<name>", escalate = "sudo"`. Use the sugar for the common case; reach
for the explicit fields when you need any knob beyond "root, passwordless sudo."

**The privilege declaration, simplest to most explicit:**

```lua
sudo = true                                     -- sugar: as="root", escalate="sudo"
as = "root",  escalate = "sudo"                 -- the expansion of the above
as = "postgres", escalate = "sudo"              -- default to a non-root identity
escalate = "sudo"                               -- as stays nil: default to myself,
                                                -- escalate per-op via { as = "root" }
escalate = { with = "sudo", via = "sudoers" }   -- full control (§10.4)
```

Defaults when omitted: `as = nil` (connection user), `escalate.with = "sudo"`,
`escalate.password = nil` (NOPASSWD), `escalate.via = "worker"` (relay spawns a
root helper once and forwards privileged ops — needs NOPASSWD to a root shell). Full `escalate` semantics
live in [§10.4](#104-privilege-in-depth); you reach them only when the common
case is not enough.

**Identity precedence (lowest → highest).** The run-as identity for an op is
the **most specific non-nil** rung of the ladder below — the scope closest to
the op wins:

1. `host.as` — the host default (lowest).
2. `task.as` — narrows the host default for a whole task (e.g.
   `task("audit", { as = "nobody" })` for a task that must *not* be root).
3. `phase.as` — narrows the task/host default for a phase.
4. per-op `as` — `ctx.run(..., { as = "root" })` (highest).

```lua
local svc = require("recipe.service")

host({ user = "deploy", as = "root", escalate = "sudo" })    -- (1) root default

task("deploy", { as = "deploy", phases = {                   -- (2) task narrows: not root
  { name = "build",   run = function(ctx)
      ctx.run("make release")                                 --   inherited → deploy
  end },
  { name = "install", as = "root", run = function(ctx)        -- (3) phase raises again
      ctx.run("apt-get install -y nginx")                     --   inherited → root
      svc.restart(ctx, "nginx")                               --   recipe's run → root too
      ctx.run("whoami", { as = "deploy" })                    -- (4) per-op override → deploy
  end },
}})
```

Four rungs, four different resolved identities — and the ladder earns its
keep in the `build` phase, which runs as `deploy` on a host whose default is
root. Narrowing downward is the common shape: a host declares the privilege it
*can* reach, a task or phase declares the identity it actually wants.

**Visibility is preserved** three ways, so v3 does not lose v2's security
property — it stops repeating it:

1. **The declaration is on the page.** `as = "root"` at the host (or a task, a
   phase) is a single, greppable statement of "these ops run as root."
2. **Every op's log line shows the identity.** `restart nginx (as root)` — you
   see who ran what in the output without reading the config.
3. **Per-op `as` overrides** are themselves logged.

**What fails, and when.** Omitting both `as` and `escalate` means ops run as
the connection user — correct for a host where that's all you need, and a
clear runtime `EACCES` where it isn't. Requesting an identity the host can't
acquire fails at the point relay tries to wrap the op; the error carries the
exact wrapped command and the OS's reply ([§6.1](#61-error-model)). relay never
pre-checks sudoers, file perms, or ACLs — that is the OS's job. The
sophisticated `worker` vs. `sudoers` strategy, the `password` knob,
and the `doas`/`sudo` tool choice live in [§10.4](#104-privilege-in-depth);
you reach them only when the common case is not enough.

## 9. CLI

```
relay <command> [target] [flags]
```

| Command | What it does |
|---|---|
| `relay exec [target] [--as <user>] -- <cmd...>` | **NEW.** Run a command on a declared target (or the reserved `localhost`), print stdout/stderr. No task, no phase body — but the target must be declared in `relay.lua` (or be `localhost`; §5.1) so its `user`/`sudo`/`lock` are reused. `--as` overrides the inherited identity for this one command. |
| `relay deploy [target]` | Run the `deploy` task. Target defaults to the task's declared target. |
| `relay task <name> [target]` | Run any named task. Target defaults exactly as `deploy`'s does. |
| `relay rollback [target]` | Run the `rollback` task — `task rollback` with a shorter name. |
| `relay doctor [target]` | Connect, handshake, detect platform, ping — a readiness check. Reports agent/planner `protocol_version` skew (§4.1), flagging any host whose agent is older than the planner. |
| `relay shell [target]` | Open an interactive SSH shell (`--root` to connect as root). |
| `relay list` | **NEW.** Print the declared tasks, targets (hosts/jails), and groups discovered in `relay.lua` — discovery without a deploy. |
| `relay validate` | **NEW.** No connection: parse `relay.lua`, resolve targets, run every plan-time check, run the dispatch-time checks whose arguments are literal in the source (privilege/path/mode validations), and the static-analysis pass (warn on `..` concatenation in a shell-form `run` or guard, a shell-form `run` or guard escalated on a `via = "sudoers"` host, mutating ops in a `when` body, a literal `tls = { insecure = true }` on a host or an `http` call). No connect, no dry-run side effects. |
| `relay doc [symbol]` | Read the Lua API in the terminal — a path, fragment, or type name. |
| `relay init` | Scaffold `relay.lua`, an example script, editor stubs, and a copy of `recipe/` (so `require("recipe.capistrano")` / `require("recipe.pkg")` / `require("recipe.git")` / `require("recipe.service")` resolve out of the box; §11.14–§11.17). |
| `relay agent install <host>` | Upload `relay-agent` to a host. |
| `relay version` | Print the version. |

Global flags: `-c/--config <file>` (default `relay.lua`), `--dry-run`,
`-v`/`-vv` (verbosity), `--var key=value` (may repeat; populates a
`relay.cli_vars` map readable in `relay.lua`, overriding `vars{}` entries of
the same name — the CI override path that doesn't need `relay.env`
indirection), `--json` (emit machine-readable per-op result lines instead of
the human console stream), `--log-file <path>` (append a JSON-lines audit
record per op to `<path>` — the same per-op shape as `--json` plus a
`run_start`/`run_end` envelope; secret-marked values redacted per §7.1; file
created `0600`; retention/rotation is the operator's job, not relay's).

**One argument order — verb, then target.** Every command that takes a target
puts it after the verb, and `task` names the task first: `relay task migrate
web01`. The alternate spellings `task <target> <name>` and `task <name>:<target>`
are gone. With two orders, `relay task foo bar` decides which word is the task by
which of them happens to be declared, so a typo'd task name reports a
target-lookup failure — the wrong error for the wrong word. `rollback` takes an
**optional** target for the same reason `deploy` does: it is the `rollback` task
under a shorter name, and it resolves its target the same way.

**`relay list`** — discover what a `relay.lua` declares, without running
anything:

```sh
relay list            # tasks, targets, groups
relay list tasks      # just task names
relay list targets    # just target names (+ kind)
```

**`relay validate`** — lint a `relay.lua` (parse, target resolution, every
plan-time check, and the literal half of the dispatch-time ones;
[§4.3](#43-declaration-then-execution)) with no connection. It is the home for
the static-analysis pass, which ships with it rather than later:

- a `..`-concatenated variable in a shell-form `run` or guard
  ([§7.1](#71-run)) — the injection shape.
- a shell-form `run` or guard that escalates (a non-default `as`, per the
  identity ladder) on a host with `escalate.via = "sudoers"`
  ([§10.4](#104-privilege-in-depth)) — it wraps as `sudo … /bin/sh -c '…'`, so
  a per-command sudoers rule denies it, and the guard case fails *silently* by
  flipping the guard's verdict. Unescalated ops are not flagged: they are not
  wrapped at all.
- a mutating op name inside a `when` body
  ([§10.5](#105-assertions-host-expect--preconditions)).
- a `relay.render` result used as a shell-form `run` or guard — rendering
  quotes nothing, so it is the `..` injection shape with extra steps
  (Appendix A).
- a `relay.render` call whose template argument is a **literal** — parsed for
  grammar errors (single-field actions only), so a `{{if .x}}` or a typo'd
  delimiter fails at lint time rather than mid-deploy (Appendix A).
- a literal `tls = { insecure = true }`, on a `host{}` or an `http` call
  ([§7.3](#73-http)) — certificate verification off is a deliberate choice a
  review should see, not a line that disappears into an opts table.

String-primary `run` is a deliberate ergonomic trade
([§12](#12-calling-conventions)); this lint is its compensating control, so
shipping it late would mean shipping the trade without the control. Both `run`
warnings name the argv form as the fix, and both are warnings rather than
errors — the shell form is legitimate on an unescalated op and on a `worker`
host.

**`relay exec`** — the ad-hoc command against a *declared* target:

```sh
relay exec web01 -- systemctl restart nginx         # argv: three tokens, no shell
relay exec web01 -- uname -a                        # argv
relay exec web01 -- "apt-get install -y nginx"      # one token ⇒ shell string
relay exec web01 --as deploy -- ls /srv             # override the host's identity default
relay exec localhost -- ls -la                      # the operator machine (reserved; no host{} needed)
```

**argv or shell, by `run`'s rule.** Several tokens after `--` are an **argv
array**, executed with no shell; a single token is a **shell string**, executed
with `/bin/sh -c` ([§7.1](#71-run)). Same two forms, same reason — globs, `&&`,
and redirection need the shell, and only the argv form is safe for a value you
paste in. Your own shell's quoting decides which form relay sees, so the
distinction is visible at the prompt: `-- "a && b"` is one token, `-- a && b`
would have been split by your shell before relay ever ran.

`<target>` is resolved through `relay.lua`, so its connection details,
privilege default, and lock ([§5.1](#51-host--the-one-required-declaration))
apply exactly as in a deploy. **`exec` inherits the host's `as`/`escalate`**,
so `relay exec web01 -- apt-get install -y nginx` escalates exactly like the
same command in a phase; `--as <user>` overrides it for the one command, the
CLI spelling of a per-op `as` ([§8](#8-privilege-the-common-case)). Inheriting
is the whole pitch — `exec` reuses the target's declared configuration rather
than being a second, weaker privilege model.

It is **not** a raw ad-hoc SSH client: there is no `user@host` form, and a
target that is neither declared nor the reserved `localhost` is a plan-time
error. For a one-off `ssh user@host cmd` outside
relay's topology, use `ssh`. (An ad-hoc `user@host` form inside `relay exec`
was considered and deferred — it would reinvent ssh's workdir/auth/quoting
story for no gain over `ssh` itself.)

It connects to the target, runs the command, streams output, and exits with
the command's exit code — the direct expression of "define target → reach it →
command → output."

<a id="interrupting-a-run"></a>
**Interrupting a run (Ctrl-C).** An operator interrupt is the *second trigger*
for an outcome the model already has, not a second concept: it cancels members
exactly as `--fail-fast` does ([§6.2](#cancelled-member)) — same `"cancelled"`
phase status, same `err.kind`, `finally` runs and `on_failure` does not. Only
the message differs, naming the interrupt rather than a failed sibling.

- **First Ctrl-C — stop and clean up.** Every in-flight member is cancelled at
  its next op dispatch. The op already running is **not killed**: relay does
  not kill remote processes, here for the same reason as under fail-fast — it
  cannot un-run one, and pretending otherwise would make the trace lie. Queued
  members never start. Every member that started runs its `finally`, which is
  the point of stopping gracefully at all — an interrupt during `stage` is
  exactly when a half-uploaded tarball needs removing. The console says what it
  is waiting for, so the wait is not mistaken for a hang.
- **Second Ctrl-C — abandon.** Stop waiting: remaining `finally` hooks are
  skipped, connections close, relay exits. Work already dispatched to a target
  keeps running there — relay reports that plainly rather than implying it
  stopped anything. Deploy locks still release, because the `flock` is held by
  the agent and the agent exits with its connection
  ([§5.1](#51-host--the-one-required-declaration)); an abandoned run leaves no
  stuck lock.
- **Exit code `130`** (`128 + SIGINT`) either way — the shell convention, and
  the same `128 + signal` arithmetic `run` results use ([§13](#13-result-shapes)).
  An interrupted run is a failed run: `summary.ok` is false for every cancelled
  member.
- **Under `--dry-run`** there is nothing in flight to drain and no hook to run
  (hooks are traced, not executed, §6.2), so the first Ctrl-C exits.
- **`relay shell` is the one carve-out.** It is an interactive session, so
  Ctrl-C goes to the remote program — that is what the shell is for. Everywhere
  else the interrupt is relay's, including a phase's `run { tty = true }`: that
  pty exists so the remote program behaves normally
  ([§7.1](#71-run)), not to turn the operator's terminal into a remote one.

## 10. Advanced (opt-in)

Every feature in this section is reached by *adding* to a working script. None
of it appears in a script that doesn't use it.

### 10.1 Multiple executors

The default executor is `ctx` (the task target). When a phase needs to act on a
*different* machine than the target, three more executors are available:

| Executor | Runs on | When present |
|---|---|---|
| `ctx` | the task target (host or jail) | always |
| `ctx.localhost` | the operator's machine | always |
| `ctx.host` | the physical host beneath a **jail** target | only when target is a jail (dispatch-time error otherwise) |
| `ctx.on(ref \| "name")` | any registered `host{}` or `jail{}` | always; unknown name/ref = dispatch-time error |

Each exposes the same op modules (`run`, `fs`, `http`) and runs them
in its own namespace — with one stated exception: `http` on a jail target dials
from the physical host ([§10.2](#102-freebsd-jails)). That is also how a recipe
picks a machine: hand it an
executor and every command inside it lands there — the reason tool wrappers
like git live in recipes rather than core
([§11.16](#1116-a-git-recipe)).

A multi-host deploy where one phase builds on a separate build host:

```lua
local build00 = host({ name = "build00", hostname = "build00.example.net", user = "ci" })
local web01   = host({ name = "web01",   hostname = "web01.example.com",   user = "deploy", sudo = true })

task("deploy", {
  target = web01,
  phases = {
    { name = "build", run = function(ctx)
        ctx.on(build00).run("make release")            -- a different host, by ref
        ctx.on(build00).fs.upload(...)                 -- same surface
      end },
    { name = "deploy", run = function(ctx)
        ctx.run("...")                                 -- ctx is web01, the target
      end },
  },
})
```

**`ctx` is sugar, not a special case.** There is no separate "target
executor" type; `ctx` is the executor bound to the current target — the same
object `ctx.on(<ref>)` returns for that target's ref (`ctx.self.host` on a
host target). `ctx.self` is a **scope, not a ref** (§6): do not pass it to
`ctx.on`, `task.target`, or `group.members` — pass the declared ref, or
`ctx.self.host` for the physical box. Naming `ctx` once reads better:

```lua
task("deploy", function(ctx)
  local jail = ctx            -- alias for readability; same object
  jail.fs.symlink("/opt/site/shared/.env", "/opt/site/current/.env")
end)
```

### 10.2 FreeBSD jails

A `jail{}` is a deploy target. relay connects to the physical `host`, finds the
jail once at connect, and routes each op to the machine that should run it. The
script names `ctx` (the jail) and `ctx.host` (the box beneath); no op argument
ever carries a JID or a mountpoint. (A `jail{}` declaration may name a
mountpoint — see `path` below — but that is one line of topology, not something
every call site repeats.)

**The key v3 property: a non-jail script contains nothing about jails.** The
executor model collapses to "the target" until you register a jail. Only then
do `ctx` (= jail) and `ctx.host` (= the machine beneath) become two distinct
things.

**Finding the jail — `match`.** At connect, once per physical host, relay runs
a single sweep and picks the jail's row:

```
jls -h jid name host.hostname path
```

```lua
match = { name = "web" }                      -- default: { name = <the jail's name> }
match = { hostname = "web.example.com" }      -- table: every key must equal that column
match = function(j)                           -- function: any predicate over one row
  return relay.split(j.name, "-")[1] == "web" -- e.g. manager names jails "web-<build>"
end
```

A row is `{ jid, name, hostname, path }` — the sweep's columns, nothing relay
invents. The table form is sugar for the equality predicate. The function form
exists because jail managers pick their own identifiers, and which column is
stable across a jail restart is a property of the manager, not something relay
can guess: `jid` is reassigned on every start, `name` may be a generated id,
`host.hostname` may be the only field an operator ever sets. Match on whichever
one your fleet holds fixed.

Exactly one row must match. Two or more is a connect-time error naming the
selector and the rows it hit; zero is the same error unless the jail is
deliberately stopped and `path` is declared (see below).

**Where each op runs.**

| Op on a jail target | runs | resolves paths |
|---|---|---|
| `run` | **inside the jail**, via `jexec` | this jail's paths as-is; a host or other-jail path ⇒ dispatch-time error |
| `fs.*`, `fs_access = "attach"` | **inside the jail**, in a helper the agent forks and attaches | the jail's own filesystem — the kernel resolves, exactly as for a process in the jail |
| `fs.*`, `fs_access = "mountpoint"` | **on the host**, path-translated | `<mountpoint>/<jail path>`, resolved by the host kernel |
| `http` | **on the host**, from the agent — both modes | not a path op; the URL carries its own address space |

**`http` is not routed into the jail** ([§7.3](#73-http)). The other three ops
address *this machine's own* resources — its files, its process table, its rc
system — so the executor has to name the namespace, because nothing else can.
An `http` call addresses an endpoint named in its argument; the executor picks
only the vantage point to dial from, which is the `ctx.localhost`-vs-`ctx`
axis, not the jail-vs-host one. Routing it would also have to be
`fs_access`-shaped — the attached helper does get the jail's VNET, but a
`"mountpoint"` agent cannot attach — and then one script line would mean two
different network stacks depending on a privilege declaration, which is the
one thing the two-mode design promises it never does.

The one spelling where the host stack is silently the *wrong machine* is a
loopback URL, so that spelling is an error rather than a wrong answer: on a
jail target, an `http` URL whose host is `127.0.0.0/8`, `::1`, or `localhost`
**raises**. It is an argument error, not an `err` — a probe pointed at the
wrong box must not read as "unhealthy". The check is at the op, so a URL
computed from `vars` is covered too. The same line on a host target stays
legal, and means what it says.

Two spellings say what a loopback URL was reaching for:

```lua
ctx.http.check("http://" .. ctx.self.jail.hostname .. ":8080/healthz")
ctx.run({ "fetch", "-qo", "/dev/null", url })      -- jexec-ed: the jail's stack
```

In a **non-VNET** jail the kernel rewrites a loopback bind to the jail's
primary address, so a service the jail believes is on `127.0.0.1:8080` really
is reachable from the host at the jail's address — the first line is the
answer. In a **VNET** jail the loopback is the jail's own and is unreachable
from the host unless its interface is bridged onto a network the host can
route to; where it is not, the second line is the answer (`fetch` is FreeBSD
base, so it is present in a base-flavored jail; a stripped jail may not have
it).

**`fs_access` — two modes, declared, not detected.**

**`"attach"` (the default).** The agent forks a helper, calls `jail_attach(2)`,
and runs the ordinary `fs` code inside the jail. The jail's root *is* the
kernel's root for that process, so absolute symlinks resolve against the jail's
`/`, `owner = "www"` resolves against the **jail's** passwd database, and no
path can leave the jail — there is no mountpoint arithmetic to escape from.

`jail_attach(2)` is root-only, so this mode needs a **root agent**: SSH as root,
or `escalate.via = "worker"` ([§10.4](#104-privilege-in-depth)). A non-root
agent under `sudoers` cannot reach it — `jexec` execs a binary that must exist
*inside* the jail, so authorizing an attached helper would mean staging
`relay-agent` into every jail. Connect-time error:

> `jail "web" needs fs_access="attach", but the agent on prod00 runs as "deploy", not root. Set fs_access="mountpoint" (§10.2), or give prod00 a root path (user = "root", or escalate = { via = "worker" }).`

**`"mountpoint"`.** `fs.*` runs on the host as the connection identity, and the
jail path is translated to `<mountpoint>/<path>`. This is the unprivileged mode.
FreeBSD jails share the host's UID space — uid 1001 in the jail is uid 1001 on
the host, the same number on the same inode — so a host user reads and writes
the jail files it owns with no root anywhere. For a fleet where the deploy user
cannot become root, this is the only mode that works, and v3 treats it as a
first-class shape, not a degraded fallback.

Three things it does differently. All follow from resolving host-side; none is
a defect awaiting a fix:

- **Names resolve against the host's passwd.** `owner = "www"` gets the *host's*
  `www`, which need not be the jail's. Use numeric uid/gid for jail paths, or
  set ownership from a `run` inside the jail.
- **Absolute symlinks are re-anchored, not confined.** When relay traverses a
  symlink under the mountpoint whose target is absolute, it re-prefixes that
  target with the mountpoint. Without this the jail's own
  `/opt/app/current -> /opt/app/releases/7` would read the *host's* `/opt/app`,
  and the release layout every deploy uses would silently break. This is a
  correctness rule and nothing more: relative targets, `..`, and any component
  the jail can rewrite are still resolved as-is.
- **Path traversal is not confined.** Every component below the mountpoint is
  writable from inside the jail, so a symlink planted there redirects a
  host-side write to wherever it points. Under an unprivileged agent the write
  still carries only that user's own permissions, so the blast radius is
  bounded by what they could already do. **Under a root agent it is not** — a
  root write that follows a jail-planted symlink lands anywhere on the host, so
  a jail's own root reaches the host's. That is why `"attach"` is the default
  and why `"mountpoint"` has to be typed out: choosing it on a root agent is a
  deliberate trade, not something relay will arrive at on its own.

**`path` — overriding the mountpoint.** The matched row already carries `path`,
so the common case needs nothing. Override it when `jls` reports a root the
useful filesystem sits below, or when there is no row at all:

```lua
path = "/zroot/jails/7"                          -- literal

path = function(j, host)                          -- j = the matched row
  return "/zroot/jails/" .. j.name .. "/root"
end

path = function(j, host)                          -- host = the physical host's executor
  local r = host.run({ "zfs", "get", "-H", "-o", "value", "mountpoint",
                       "zroot/jails/" .. j.name }, { read_only = true })
  return relay.split(r.stdout, "\n")[1]
end
```

The function runs **at connect**, once per host, after the sweep and before any
phase; its result is cached for the run. It runs under `--dry-run` too, so a
preview resolves the real mountpoint instead of previewing against a guess —
which is why the probe above is marked `read_only = true` ([§7.1](#71-run)).
Like `when`, it must not mutate the target, and relay cannot verify that it
doesn't.

relay validates the result at connect: absolute, exists, is a directory.
Anything else — including an error raised inside the function — is a
connect-time error naming the jail. `path` is consulted only under
`fs_access = "mountpoint"`; declaring it under `"attach"` is a plan-time error,
so a config can never imply a confinement it isn't getting.

**Stopped jails.** A stopped jail has no `jls` row, and `match` finds nothing.
With `path` declared, the target becomes **filesystem-only**: `fs_access` must
be `"mountpoint"` (there is no jail to attach to) and `run` is a
connect-time error — *"jail `web` is not running on prod00"*. Staging a release
into a jail before booting it keeps working. `http` keeps working too, since it
never entered the jail — but `ctx.self.jail` carries only `path` there, so a URL
built from `.hostname` is a nil concat, not a probe. Without `path`, it is a
connect-time error naming the selector that matched nothing.

**Commands, `jexec`, and sudoers rules.** A jail command op is
`jexec <name> <argv…>`. From a root agent that is a free drop
([§10.4](#104-privilege-in-depth)). From a non-root agent it is a raise, wrapped
`sudo -n` and authorized per command — which makes the exact line relay runs
part of the contract, because a sudoers rule is a literal argv match.

Only the wrapper is relay's. The inner argv is whatever your script passed to
`run`, directly or through a recipe ([§11.17](#1117-the-corerecipe-line)) —
`service nginx restart` below comes from `recipe/rcd.lua`, code in your config
dir, not from a spelling core chose for you:

```lua
rcd.restart(ctx, "nginx")           -- recipe/rcd.lua, on jail "web"
```
```
sudo -n /usr/sbin/jexec web service nginx restart
```
```
# /usr/local/etc/sudoers.d/relay
deploy ALL=(root) NOPASSWD: /usr/sbin/jexec web service nginx restart
```

relay wraps with the matched row's **`name`**, not its `jid`: a jid is
reassigned every time the jail restarts, so a rule pinned to one stops matching
without warning. If the manager regenerates names too, widen the jail slot
alone — sudo matches per argument, so `*` fills exactly that slot and the
command must still be `service nginx restart`:

```
deploy ALL=(root) NOPASSWD: /usr/sbin/jexec * service nginx restart
```

**Numeric names are the exception.** `jexec` resolves an all-digit argument as
a jid, never as a name, so a jail literally named `7` cannot be reached by
name at all — relay wraps those with the matched row's jid. That jid moves on
every restart, so no literal sudoers rule can survive it and the wildcard form
above is the only one that works. relay says so at connect rather than letting
the rule fail mid-deploy:

> `jail "marketing" has the numeric name "7", which jexec resolves as a jid, so relay wraps with jid 12 — a value that changes when the jail restarts. A sudoers rule naming a jid will stop matching; use the wildcard jail slot: deploy ALL=(root) NOPASSWD: /usr/sbin/jexec * service nginx restart`

A build-on-host, stage-into-jail deploy, on a root agent (so the default
`fs_access = "attach"`):

```lua
local rcd = require("recipe.rcd")     -- rc.d service control (§11.17)

host({ name = "prod00", hostname = "prod00.example.net",
       user = "deploy", as = "root", escalate = { via = "worker" } })

jail({ name = "web", host = "prod00" })   -- match = { name = "web" }, fs_access = "attach"

local SITE = "/home/deploy/site"      -- jail-relative; the jail sees it as-is
local RID  = os.date("%Y%m%d%H%M%S")   -- release id, plan time → same on every target

task("deploy", {
  target = "web",                       -- ctx binds to the JAIL
  phases = {
    -- Build on the physical host beneath the jail: ctx.host ops are NOT
    -- jexec-wrapped and see the host filesystem.
    { name = "build", run = function(ctx)
        ctx.host.run({ "task", "build" }, { cwd = "/home/deploy/build" })
      end },

    -- Stage into the jail: the host-tagged tarball is read on the host and
    -- streamed into the attached helper, which untars it inside the jail.
    { name = "stage", run = function(ctx)
        local release = relay.path.join(SITE, "releases", RID)
        ctx.fs.mkdir_all(release)
        ctx.fs.extract(ctx.host.path("/home/deploy/build/site.tar.gz"), release)
      end },

    -- The link lives inside the jail, so its stored target is jail-relative —
    -- the app reading it is inside too (§10.3).
    { name = "activate", run = function(ctx)
        local release = relay.path.join(SITE, "releases", RID)
        ctx.fs.symlink(release, relay.path.join(SITE, "current"), { atomic = true })
      end },

    -- The worker makes the agent root, so this is a free drop: `jexec web
    -- service site restart`, no sudo wrap and no sudoers rule. The recipe
    -- takes an executor, so `ctx` is what puts it inside the jail.
    { name = "restart", run = function(ctx)
        rcd.restart(ctx, "site")        -- inherits jail host's root default
      end },
  },
})
```

A **cross-namespace transfer under `"attach"`** — the `extract` above — is one
op with two sides: the agent reads the host-tagged tarball on the host and
streams it to the attached helper over the same chunked, checksum-verified
channel `upload`/`download` use ([§7.2](#72-fs)). The helper never sees a host
path, which is the point: the only bytes that cross are the ones the script
named.

Now the same deploy with **no root anywhere** — the unprivileged shape, and the
reason `fs_access = "mountpoint"` exists:

```lua
-- The agent connects as `deploy`, a user that exists on the host and in the
-- jail with the same uid. Jails share the host's UID space, so host-side
-- `deploy` owns the jail files it created. Two narrow sudoers rules cover the
-- only steps that genuinely need root — matchable because every escalated op
-- here is argv-form, not a shell string (§10.4).
local rcd = require("recipe.rcd")

host({ name = "jailer00", hostname = "jailer00.example.com", user = "deploy",
       escalate = { with = "sudo", via = "sudoers" } })

jail({
  name      = "marketing",
  host      = "jailer00",
  fs_access = "mountpoint",                            -- no root: cannot attach
  match     = { hostname = "marketing.example.com" },  -- the manager names jails
                                                       -- by its own numeric id;
                                                       -- hostname is what we set
  path      = function(j) return "/zroot/jails/" .. j.name end,   -- → /zroot/jails/7
})

local SITE = "/home/deploy/marketing"   -- jail-relative
local RID  = os.date("%Y%m%d%H%M%S")

task("deploy", {
  target = "marketing",
  phases = {
    -- Build on the host, against the jail's shared .env. The link lives on the
    -- host, so its stored target is the translated mountpoint path — the build
    -- tool reading it is host-side. Same uid on both sides, mode 0640, no
    -- privilege involved.
    { name = "build", target = "jailer00", run = function(ctx)
        ctx.fs.symlink(ctx.on("marketing").path(SITE .. "/shared/.env"),
                       "/home/deploy/build/.env", { force = true })
        ctx.run({ "npm", "run", "build" }, { cwd = "/home/deploy/build" })
      end },

    -- Host-side fs, translated to the mountpoint. Identical script text to the
    -- attach-mode version above — only the declaration changed.
    { name = "stage", run = function(ctx)
        local release = relay.path.join(SITE, "releases", RID)
        ctx.fs.mkdir_all(release)
        ctx.fs.extract(ctx.host.path("/home/deploy/build/site.tar.gz"), release)
        ctx.fs.symlink(release, relay.path.join(SITE, "current"), { atomic = true })
      end },

    -- The one privileged step. `deploy` is not root, so this is a raise. The
    -- jail's name is numeric, so relay wraps with its jid and the rule needs
    -- the wildcard jail slot:
    --   deploy ALL=(root) NOPASSWD: /usr/sbin/jexec * service nginx restart
    { name = "restart", run = function(ctx)
        rcd.restart(ctx, "nginx")
      end },
  },
})
```

Two properties worth naming. The phase bodies are the same in both scripts —
`fs_access` is a property of the machine's privilege, declared once, not
something every call site restates. And the second script never mentions
`/zroot/jails`, `jexec`, or a jid: the mountpoint appears once, in a `path`
function that derives it, and the sudoers rule is the only place the jail's
name is written by hand.

**Identity inside the jail.** Entering a jail is `jail_attach(2)`, which is
root-only, so a jail command op needs root on the physical host — the jail
host's root default, an explicit `as`, or a `sudo -n` raise authorized for that
one `jexec` line. Once inside, the identity is a free drop done by `jexec -u U`:
`as = "root"` is bare `jexec`, a non-root `U` is `jexec -u U`, and `U` resolves
against the **jail's** passwd.

`fs.*` follows its mode. Under `"attach"` the helper is already root inside the
jail, so a non-root `as` is the same free drop — `setuid` after attaching, `U`
from the jail's passwd. Under `"mountpoint"` there is no jail-side process and
no command to authorize, so `as` obeys the ordinary in-process rule
([§10.4](#104-privilege-in-depth)): reachable from a root agent or
`via = "worker"`, a dispatch-time error under `sudoers`.

All of this is mechanics the agent owns; the script says `ctx` (jail) vs
`ctx.host` (host) and lets the agent route.

### 10.3 Tagged paths

A path is a first-class, **namespace-tagged value**. Every executor view
produces them; any op accepts them. The agent resolves each to the frame the
op runs in. The mountpoint never appears in script text.

```lua
ctx.path(p)            -- tagged with the current target's namespace
ctx.host.path(p)       -- tagged with the host namespace
ctx.on(name).path(p)   -- tagged with that target's namespace
ctx.localhost.path(p)  -- tagged with the operator namespace
```

Each takes a **string** and returns an opaque **Path**; `tostring(p)` yields
the raw path in its own frame (jail-relative for a jail path). Build raw
strings with `relay.path.*` or `..` as usual, then tag at the call site:

```lua
-- ctx is a jail; ctx.host is the physical host beneath it.
-- host-tagged source is read untranslated on the host; the jail dest is
-- translated to the jail's mountpoint. One typed value, no mountpoint literal.
local id = ctx.vars.release_id            -- your deploy's id, however you source it
ctx.fs.extract(ctx.host.path("/home/deploy/build/site.tar.gz"),
               relay.path.join("/home/deploy/site/releases", id))
```

**Plain string = the current namespace.** The unmarked case stays obvious and
zero-tax: a path you pass untagged means "in this executor's own namespace"
(jail-relative on a jail target). Cross-namespace paths must be tagged — there
is no other way, and no silent fallback.

**Resolution is determined by where the op executes, not by where the path was
made:**

| Op (jail target) | executes… | resolves… |
|---|---|---|
| `fs.*`, `fs_access = "attach"` | **inside the jail** (attached helper) | this jail's paths as-is, by the kernel; a host or sibling-jail path is read on the host and **streamed** in ([§10.2](#102-freebsd-jails)) |
| `fs.*`, `fs_access = "mountpoint"` | **on the host** (via the mountpoint) | host paths as-is; **any** jail-of-this-host path → its mountpoint |
| `run` | **inside the jail** (`jexec`) | only *this* jail's paths as-is; a host/other-jail path ⇒ dispatch-time error |

And for an op on a host (`ctx.host.*`, or any non-jail `host{}`): host paths
as-is; any jail-of-this-host path → its mountpoint. A host op reaching into a
jail is always mountpoint-translated, whatever that jail's `fs_access` says —
`fs_access` governs `ctx.fs.*` on the jail target, not what the host can see.

Two hard rules, both enforced at **dispatch time** — at the op's call site,
before it reaches the agent. A `Path` is built inside the phase (from
`ctx.vars`, a `run` result, a concatenation), so its tag cannot be known before
the phase runs; `relay validate` catches the literal cases without connecting,
and `--dry-run` catches the rest, since the check precedes dispatch
([§4.3](#43-declaration-then-execution)):

- **R1** — a jail path is resolvable only by an op executing on that jail's
  own host (or inside the jail itself). A jail on hostA whose path reaches an
  op running on hostB fails: *"`db` is on hostA; this op runs on hostB; can't
  reach `db`'s files"*.
- **R2** — a host path fed to an op executing **inside a jail** fails:
  *"jail can't see host `/home/deploy/...`; run it as a host op, or nullfs-mount
  it"*.

**Every `fs.*` op accepts tagged paths uniformly** — every action and every
read in [§7.2](#72-fs), with no exceptions and no per-op matrix (the list is
deliberately not repeated here; it would drift the next time `fs` grows a
verb). `run` accepts a `Path` in any argv slot and
as `cwd`; the agent stringifies it after resolving:

```lua
-- Run a binary that lives inside the jail, but from a HOST command (not
-- jexec). ctx.path tags the binary jail-side; ctx.host.run resolves argv[0]
-- to the jail's mountpoint on the host. No ctx.fs_root(), no mountpoint leak.
ctx.host.run({ ctx.path("/home/deploy/site/current/migrate"), "up" })
```

This replaces v2's `ctx.fs_root() .. <jail path>` escape hatch, which leaked
the mountpoint into script text. The mountpoint is now mechanics the agent
owns, behind the tag.

**A symlink's target is written in the namespace of the link, not the
executor.** A symlink target is stored *text*, resolved later by whoever reads
the link, from wherever the link lives — so that, not the machine running the
op, decides which frame it is written in:

- link inside the jail, jail-tagged target ⇒ stored jail-relative. The reader
  is the app inside the jail, which sees `/opt/app/releases/7`, not a
  mountpoint. True under both `fs_access` modes: in mountpoint mode the op
  runs host-side but the text is still the jail's.
- link on the host, jail-tagged target ⇒ stored as the translated mountpoint
  path, because the reader is host-side.
- link inside the jail, host-tagged target ⇒ dispatch-time error (R2): the jail
  cannot see host paths, so no text would be correct.

`fs.readlink` is the inverse and returns the stored text tagged in the link's
own namespace, so feeding it straight into another op re-resolves correctly.

**Permission is not relay's problem under `fs_access = "mountpoint"`.** A
mountpoint-translated `fs.*` runs as the connection user; if it lacks
filesystem permission on the mountpoint, the OS error surfaces as-is. That is
the model working — jails share the host's UID space, so a deploy user that
owns the jail files it created can write them with no privilege at all
([§10.2](#102-freebsd-jails)). Under `fs_access = "attach"` the jail's own
permission semantics apply instead, because the op really is running inside the
jail: the jail's passwd resolves `owner`/`group`, and the jail's root — not the
host's — is what the path is relative to.

**Forgotten-tag hint.** A plain string is assumed to be in the current
namespace; if you meant the host, tag it. At execution, jail `fs.*` whose
plain-string source is missing in the jail **but exists at that same path on
the host** reports both, with the hint: *"`/home/deploy/build/x` not in jail
namespace; did you mean `ctx.host.path(...)`?"*

**Multi-jail on one host.** Sibling jails share a host, so their mountpoints
are both visible there. A cross-jail copy is one tagged source into the target
jail's `fs`:

```lua
-- ctx = jail2; copy a file from jail1's namespace into jail2's. Both resolve
-- to mountpoints on the shared host; the copy runs there.
ctx.fs.copy(ctx.on("jail1").path("/data/dump.sql"), "/restore/dump.sql")
```

### 10.4 Privilege in depth

The common case is `sudo = true` (i.e. `as = "root", escalate = "sudo"`). The
full `escalate` form is for hosts where passwordless-full-sudo isn't the shape
of what the connection user can do:

```lua
host({
  name = "prod00", hostname = "prod00.example.net", user = "deploy",
  as = "root",                       -- default identity (nil = connection user)
  escalate = {
    with     = "sudo",               -- "sudo" (default) | "doas" — the tool
    password = nil,                  -- nil (default) = NOPASSWD; a secret (relay.secret*) feeds sudo -S
    via      = "sudoers",            -- "worker" (default) | "sudoers" — relay's strategy
  },
})
```

The knobs answer distinct questions:

- **`as`** *(host-level, not inside `escalate`)* — the default run-as identity.
  `nil` = connection user.
- **`with`** — the *tool*: `sudo` or `doas`. Just the prefix relay wraps with.
  (Password mode is `sudo`-only — doas has no stdin-password flag.)
- **`password`** — `nil` (default) means NOPASSWD: the connection user reaches
  the target identity with no password (the common, supported case — set it up
  in sudoers, or ssh in as root so every op is a free drop). A **secret** value
  (`relay.secret(v)` or `relay.secret_file(path)`, §7.1) means the transition
  needs a password; relay feeds it to `sudo -S -p ''` on the child's **stdin**
  — never a tty, never argv (`ps`-invisible), redacted in every record like any
  secret. The password is a single-hop secret for *this connection's* ssh user
  (`A → U`); relay does not chain identities (`a → b → c`). `sudo`-only: doas
  has no `-S`, so `with = "doas"` plus a `password` is a plan-time error.
- **`via`** — relay's *strategy* for using the capability:
  - **`worker`** *(default)* — relay spawns a persistent root helper once at
    connect (needs NOPASSWD to a root shell), then every privileged op is a
    free drop from root. Supports in-process `fs.*` writes as any user. With a
    `password` set, the helper is spawned via `sudo -S -p '' -i` fed the secret
    once at connect — the password is sent exactly once and every drop after is
    free.
  - **`sudoers`** — no persistent root. The agent stays the connection user and
    prefixes each *command-shaped* op with `sudo -n [-u U]`, authorized per
    command by a narrow sudoers rule. The safer model for shared hosts; cannot
    reach an in-process `fs.*` drop (no command to authorize).

`via` also states the *breadth* of the grant, which is why there is no separate
knob for it: `worker` requires NOPASSWD to a root shell, `sudoers` requires only
the per-command rules for the ops you actually run. relay never reads sudoers —
under `sudoers` it wraps each op and lets sudo accept or deny it at runtime.

**Escalate with the argv form under `sudoers`.** sudo authorizes the argv it is
handed, so `run`'s two forms ([§7.1](#71-run)) ask sudoers two different
questions:

```sh
argv  →  sudo -n -u root jexec 5 service nginx restart
shell →  sudo -n -u root /bin/sh -c 'jexec 5 service nginx restart'
```

A rule for `/usr/sbin/jexec * service nginx restart` matches the first and
denies the second — sudo sees `/bin/sh` with `-c` and one argument, and the rule
names neither. With `-n` there is no prompt, so the op fails at runtime carrying
sudo's message, which names `/bin/sh` rather than the command you wrote. The
repair that suggests itself is worse than the failure: `NOPASSWD: /bin/sh -c *`
authorizes *every* command as root while still reading as a narrow rule in the
sudoers file — it deletes precisely the per-command model this strategy exists
for. (The shell form also resolves the binary through `sh`'s `PATH`, while
sudoers matches an absolute path — a second way the two disagree.)

Guards inherit `as` ([§7.1](#71-run)), so a shell-form `onlyif`/`unless` on an
escalated op hits the same denial with a **quieter** failure: a guard never
fails the phase, so a denied guard is a soft skip — `onlyif` skips the command,
`unless` runs it. The deploy makes a wrong decision instead of stopping.
`relay validate` warns on both shapes ([§9](#9-cli)).

None of this touches unescalated ops: with `U = A` there is no wrap and no
sudoers question, so a shell-form `run` is the right form there.

**The transition table.** Every op is one primitive transition **`A → U`**.
`A` is the identity the agent process *is* when it runs the op — the
connection user at connect (`host.user`), except under `via = "worker"`, where
the root helper spawned at connect makes `A = root` for every op that follows.
`U` is the op's `as` (per-op or host default); empty ⇒ `U = A`, run directly
with no transition. There is no implicit "become root" — a call names
`as = "root"` (or the `sudo = true` sugar), or it doesn't.

The transitions are asymmetric, and the API never hides which one a call is:

| `A` (actor) | `U` (target) | transition | mechanism | authorization |
|---|---|---|---|---|
| any | `A` / empty | **identity** | run directly | always |
| **root** | any `U` | **drop** | `setuid`/`setgid` (+ `jexec -u U` in a jail) | **free** — no rule, no password |
| non-root | root | **raise** | `sudo -n [-u root] C` (or `doas`) | **per-command** sudoers: `A ALL=(root) …: C` |
| non-root | other non-root | **cross** | `sudo -n -u U C` (or `doas`) | **per-command** sudoers: `A ALL=(U) …: C` |

Under a `password` secret the raise and cross rows change one detail: the wrap
becomes `sudo -S -p '' -u U C` and the password is written to the child's stdin
(the `-n` becomes `-S`). The authorization column is unchanged — sudoers must
still permit `A` to run `C` as `U`; the password only satisfies sudo's auth
prompt, it grants no new capability.

Two facts this encodes, never buried:

1. **Drop is free — and it belongs to *being root*, not to a strategy.** When
   `A = root`, any `U` is reachable with no sudoers rule and no password, so
   `escalate` is moot. This covers both an agent that lands as root over ssh
   and the `worker` strategy (which makes `A = root` at connect); it is
   detected at connect, not declared.
2. **A raise/cross is authorized per *command*, not per *identity*.**
   `sudo -n -u U C` asks the OS *"may `A` run `C` as `U`?"* — not *"may `A`
   become `U`?"*. A `deploy` carrying `deploy ALL=(root) NOPASSWD:
   /usr/sbin/service site restart` can run *that one command* as root with no
   path to a root shell. This is the `sudoers` strategy's whole point — and
   its limit: an in-process `fs.*` op has no command to authorize, so a
   non-root agent under `sudoers` cannot reach a non-default `U` (the
   dispatch-time error below).

`U`'s identity environment (`HOME`, `USER`, `LOGNAME`) is set on every path —
overlaid explicitly on a drop (a bare `setuid` changes credentials but not the
environment), inherited from `sudo -n -H`/`doas` on a raise/cross — so a drop
and a raise to the same `U` agree. Startup files (`~/.profile`, `~/.bashrc`,
`/etc/profile`) are deliberately not sourced; op `env = {…}` always wins. A
command needing a login environment asks for one explicitly
(`run({ "sh", "-lc", "…" })`).

**The three error sites** (the only places privilege surfaces as a failure), in
the order they can fire ([§4.3](#43-declaration-then-execution)):

- **connect time** — `worker` chosen but the connection user can't get a root
  shell:
  > `could not start a root worker on prod00: "deploy" is not authorized for a root shell. If "deploy" is only authorized for specific commands, use via="sudoers".`
- **dispatch time** — an in-process `fs.*` needs a non-default identity under
  `sudoers` on a non-root agent. The op's identity comes off the `as` ladder,
  so this is decided at the call site — before the op is sent, and by
  `relay validate` when the `as` is literal:
  > `fs.write as "postgres" is impossible under via="sudoers": the agent stays "deploy" and sudoers only wraps commands. Use via="worker", or run the agent as "postgres".`
- **run time** — a `sudoers` denial (the one case that can't be pre-checked):
  > `[service site restart] as root was denied: no NOPASSWD rule authorizes "deploy" to run it as root. Add 'deploy ALL=(root) NOPASSWD: /usr/sbin/service site restart'.`

**Connect-time validation.** relay confirms the escalation capability before
any phase runs: under NOPASSWD, that the root shell (`worker`) or sudo is
reachable; under a `password` secret, it runs `sudo -S -p '' -v` fed the
password to prove the credential. A wrong password surfaces here, as a
connect-time error — never retried mid-deploy.

Per-op `as` overrides the host default for individual ops; the host default
covers the rest.

**Agent forwarding under escalation.** When `host.forward_agent = true`
(§5.1), `-A` is all relay passes at connect; ssh/sshd create a forwarded
socket on the target and set `SSH_AUTH_SOCK` in the remote session's
environment. The relay-agent inherits that env, so the commands it spawns
(`run`, and whatever a recipe builds on it) authenticate through the forwarded
socket — no per-op wiring.

One footgun under `via = "sudoers"`: sudo's `env_reset` strips
`SSH_AUTH_SOCK` before the command runs, so an op escalated `as = "root"`
(e.g. a `git clone`) loses the agent silently — the failure is a confusing
`Permission denied (publickey)`. relay avoids this for op-supplied `env` by
folding them into a `/usr/bin/env -- K=V ... <argv>` that survives
`env_reset`; for agent forwarding, relay applies the same trick to
`SSH_AUTH_SOCK` when `forward_agent` is active, so forwarding works under
sudoers too. (The socket path then appears in `ps`/`-v` traces — the path is
not secret; the socket is protected by its filesystem permissions, the
credentials never leave the operator's agent.) If you bypass relay with a raw
`sudo git ...`, add `Defaults env_keep += SSH_AUTH_SOCK` to sudoers.

Two non-relay prerequisites: an agent must be running on the operator side
(`ssh-add`; `SSH_AUTH_SOCK` present in relay's environment — no agent means
`-A` forwards nothing), and sshd must `AllowAgentForwarding yes` (the OpenSSH
default; a `no-agent-forwarding` authorized_keys option or sshd override
blocks it, and ssh fails to forward without a loud error).

**Identity is the connection.** The ssh user (`host.user`) is the capability
ceiling: escalation is always the single transition `A → U` where `A` is that
user, authorized by sudoers for `A`. If `A` has no rule to reach `U`, no relay
feature changes that — relay uses only what `A` can do. So when the connection
user can't reach an identity a phase needs, **do not compose nested sudo**
(`sudo -u b sudo -u c …`); declare a second `host{}` that ssh's in as a user
who has the capability and pin the phase to it. Two declarations on one box
(`prod-deploy`, `prod-alex`) are two connections and two agents — the same
one-connection-per-target model a multi-host deploy already uses. Privilege is
not a mechanism layered on connections; it *is* which host decl you pin to.

### 10.5 Assertions: host `expect` & preconditions

relay distinguishes two kinds of "this must be true":

- **Static identity assertions** — facts about a host known at connect time
  (its platform). Declared once on the host; checked automatically.
- **In-phase preconditions** — facts about live state (a file exists, a service
  runs, a version matches). Expressed in Lua where you need them, so they are
  checked as the phase reaches them, not at connect.

**Static identity: `host{ expect = ... }`.** The agent reports its real
`os`/`arch`/`distro`/`version`/`init`/`package_manager` on connect; v3
auto-detects and uses these without you saying anything. Assert them only where
a deploy depends on a specific platform. A mismatch fails at connect, before
any op runs, naming both values:

```lua
host({
  name = "web01", hostname = "web01.example.com", user = "deploy",
  expect = { os = "linux", distro = "ubuntu", version = "22.04",
             init = "systemd", package_manager = "apt" },
})
-- If web01 is really Debian 12, relay hard-fails at connect:
--   expect mismatch on web01: distro=ubuntu != debian, version=22.04 != 12
```

Assert any subset — only what matters:

```lua
host({ name = "db01", ..., expect = { init = "systemd" } })   -- only init
host({ name = "edge", ..., expect = { arch = "arm64" } })     -- only arch
host({ name = "web01", ...,
       expect = { os = "linux", distro = "ubuntu", version = "22.04" } })  -- pin an LTS line
```

`os` is the coarse grain (kernel family); `distro`/`version` are the finer
grain a deploy often actually depends on. Matching is **exact string** —
`expect.version` compares verbatim against the reported value, so
`version = "22.04"` pins the LTS line (point releases live in a separate field
and don't perturb `VERSION_ID`; Debian `11`, RHEL `9`, Alpine `3.19` likewise).
The reported value is the *normalized* one, which is what makes the exact
match stable: on FreeBSD that is the `MAJOR.MINOR` prefix, so
`version = "14.0"` keeps matching after a `freebsd-update` bumps the running
kernel to `14.0-RELEASE-p6` ([§6](#6-tasks-and-ctx)).
If `expect` sets a field the agent reports as `""`, that is a mismatch with a
clear "agent couldn't determine <field>" message — you asked for a guarantee
the agent can't give (no `/etc/os-release`, a rolling release), not a soft skip.

This is opt-in. A script that doesn't care omits `expect` and gets the agent's
reported values. It fixes v2's trap (re-declaring what the agent already knows,
then hard-failing on your own typo) while keeping the assertion where a deploy
genuinely depends on a specific init or package manager.

**In-phase preconditions: Lua `assert` + `ctx`.** For anything not known at
connect, assert against the live state `ctx` returns. relay aborts the phase on
any error, so `assert` is already a hard stop — no special primitive needed:

```lua
local svc = require("recipe.service")

task("migrate", function(ctx)
  -- "Don't go farther if false": assert hard-aborts the phase
  local st = svc.status(ctx, "postgres")             -- nil on error
  assert(st and st.running, "postgres must be running")
  assert(ctx.fs.exists("/opt/app/conf"), "app not configured; run bootstrap")
  ctx.run("migrate-db")
end)
```

**Soft guards vs hard stops.** Two ways to gate a step; pick by intent:

| Mechanism | Scope | On false | Use when |
|---|---|---|---|
| `onlyif` / `unless` (on `run`) | one command | **skip** it (`ran=false`) | the op is conditionally needed (idempotency) |
| `when` (on a phase) | one phase | **skip** it | the phase is conditionally needed |
| `when` (on a task) | all of a member's phases | **skip** them | the whole member is conditionally needed |
| `host{ expect=... }` | whole host | **fail** at connect | the host must be a specific platform |
| Lua `assert(cond, msg)` | inline | **fail** the phase | live state must hold before proceeding |

Soft (`onlyif`/`unless`/`when`) = "skip if not applicable." Hard
(`expect`/`assert`) = "stop if wrong." Most "don't proceed unless X" is just
`assert(ctx...)`.

**`when` is a pure predicate.** A `when` (task or phase) is a guard, not a
phase body: it must be **side-effect-free** — read ops only (`fs.read`/
`exists`/`stat`, `http.check`, `run { read_only = true }`, `ctx.vars`,
`ctx.self`). No `fs.write`/`remove`, no shell-form `run` with side effects. Rationale: `when` is re-evaluated under retry and
fan-out, and under `--dry-run` its mutating ops would be stubbed (so the
predicate could return a different bool than in a real run — masking the very
logic `when` gates). `onlyif`/`unless` are fenced by construction (a command
value, no `ctx`); `when` gets full `ctx`, so the contract is by convention.
`relay validate` warns on a mutating op name inside a `when` body (same lint
family as the shell-form `..` check, §9).

> **Open (see §15).** A phase-level `expect = function(ctx) ... return bool end`
> — a hard sibling of soft `when`, evaluated when the phase runs — is deferred
> until a real plan wants it; Lua `assert` covers the need today. It would be a
> field on the phase table (not a global function), so it can't shadow Lua's
> built-in `assert`.

### 10.6 Agent Lua (`eval`)

For logic that wants **multiple operations co-located with the target in one
round-trip** — typically a loop of small `run` calls. Agent Lua has bare `run`,
`fs`, `log`, `json` — bare is allowed here precisely because an agent script
executes in exactly one place by construction. It has no `require`, so a
recipe is not reachable from it: an agent-side restart is
`run({ "service", name, "restart" })` ([§11.17](#1117-the-corerecipe-line)).

Two entry points, one call contract:

- **`ctx.eval(source, args?)`** — run an inline agent script from a Lua string.
  No file, no path resolution; the string lives in your `relay.lua` and is
  shipped to the agent as-is. For small, throwaway, or generated-on-the-fly
  logic where a separate file is overkill.
- **`ctx.eval_file(path, args?)`** — run an agent script from a file under your
  config dir. Prefer it for anything non-trivial: readable, reusable,
  editor-highlighted, linted by `relay validate`.

Both take an optional `args` table (it becomes the script's `args` global) and
return whatever the script `return`s. The call contract below covers both.

**`ctx.eval` — inline.** The source string is planner-side Lua source; it is
not a path and is never resolved against the filesystem:

```lua
-- One round-trip: report which of these paths already exist on the target.
local present = ctx.eval([[
  local out = {}
  for _, p in ipairs(args.paths) do
    out[p] = fs.stat(p) ~= nil       -- fs.stat returns (nil, err) for a missing path
  end
  return out
]], { paths = { "/etc/nginx/nginx.conf", "/var/www/myapp/current" } })

for p, ok in pairs(present) do
  if not ok then ctx.log.warn("missing on target: " .. p) end
end
```

**Path resolution (`eval_file`).** `eval_file`'s path resolves against the **config dir**
(the directory of the loaded `relay.lua`), exactly like `require`
([§11.14](#1114-a-deploy-recipe-plain-require)). It is never CWD-relative. `ctx.eval_file("scripts/foo.lua")`
always means `<config_dir>/scripts/foo.lua`, independent of where the operator
runs relay from. (The file is *read on the operator* and shipped to the agent
over the protocol; the agent never opens the path itself.)

```lua
-- In a phase:
local result = ctx.eval_file("scripts/seed-clients.lua", {
  bin = "/var/www/myapp/current/myapp-seed",
  clients = CLIENT_LIST,
})
```

```lua
-- scripts/seed-clients.lua — Agent Lua, self-contained (no `require`)
local existing = run({ args.bin, "list" }).stdout
for _, c in ipairs(args.clients) do
  if not existing:find(c.id, 1, true) then        -- plain find; no pattern engine
    run({ args.bin, "create", "--id", c.id, "--name", c.name })
    log.info("created " .. c.id)
  end
end
return { seeded = #args.clients }
```

**Call contract** (unchanged from v2):

1. The `args` table becomes the script's top-level `args` global; the script's
   `return <value>` becomes the phase-side return value.
2. Only plain Lua values cross the boundary (tables, numbers, strings,
   booleans, nil). Functions, userdata, and cyclic tables are an error.
3. Uncaught agent-side errors fail the phase with the agent's message and
   traceback; use `pcall` to handle failure.
4. `log.*` streams live; the return value carries data.
5. Inner `run()` follows phase rules (default `ignore_exit = false`).
6. No `require` — agent scripts are self-contained.

**Rule of thumb:** if you reach for `&&`, `||`, `$(...)`, or a pipe *inside a
single target*, you want Lua control flow — in the phase, or in
`eval`/`eval_file` — not a shell string stretched across targets.

### 10.7 Concurrency: fan-out, not DAGs

relay's concurrency scope is deliberately narrow: **parallelism across
targets, never within one.** One task = one sequential story per target. This
keeps execution legible and avoids a second (async) execution model.

**The unit of work** is the pair `(task, target)` — a member running its
fan-out phases in order. Concurrency schedules these units; it never splits a
phase. Pinned phases refine this: a pin is a **barrier** that runs once,
outside every member's chain, so a member's chain is its contiguous block of
fan-out phases between barriers. `strategy` schedules member chains within a
block, never across a barrier — full rules in
[§6's execution model](#pinned-phase-execution-model).

**Fan-out via `strategy`** (task-level, opt-in; default `serial`):

```lua
group({ name = "web", members = {"web01","web02","web03"} })

task("deploy", {
  target   = "web",
  strategy = "rolling",    -- serial (default) | parallel | rolling
  max      = 2,            -- parallel: concurrency cap; rolling: batch size
  phases   = { ... },
})
```

| strategy | behavior | use |
|---|---|---|
| `serial` (default) | one target at a time, in member order | current behavior; safe; the simple path |
| `parallel` | up to `max` targets at once | independent targets, fast fan-out |
| `rolling` | batches of `max`, with a gate between (healthcheck or delay) | canary / zero-downtime |

`serial` is the default, so a single-host script never mentions `strategy`.
Fan-out is pure opt-in; the simple-path invariant holds.

**`strategy` on a non-group target is a no-op.** `strategy` governs fan-out
*across a group's members*; a single declared host (`target = "web01"`) has
one member, so `serial` / `parallel` / `rolling` are identical there — the
phases run once, and `max` is ignored. It is not an error: a spec templated
between a group (prod) and a single host (dev) keeps the same `strategy`
field. (A typo'd `target` that *meant* a group is better caught by
`relay explain` / `--dry-run` showing the resolved target than by erroring on
a benign field.)

**Failure policy under fan-out.** When one member fails, what happens to its
siblings depends on `strategy`. The rule per strategy:

| strategy | on member failure | rationale |
|---|---|---|
| `serial` | **fail-fast** — do not start the next member | serial's value is ordered, observable progress; an operator who chose serial chose caution |
| `parallel` | **continue + collect** — in-flight members finish, queued members still start, all failures reported at end | fan-out implies independent targets; don't waste in-flight work; a full failure set aids triage |
| `rolling` | **drain the current batch, then halt** — the gate fails, the next batch never starts | rolling is canary / zero-downtime; a failed batch must stop the rollout (kubectl / Ansible `serial` both do this) |

Memorable form: **serial = fail-fast; parallel = continue; rolling =
parallel-within-batch + fail-fast-between-batches.**

`parallel`'s continue-default is overridable two ways:

- **Task field** `fail_fast = true` — the script declares it; survives across
  invocations.
- **CLI flag** `--fail-fast` — one-off override (e.g. an expensive deploy
  where continuing on a known-bad artifact wastes resources).

Under `--fail-fast` / `fail_fast = true`, the first failure cancels in-flight
members and queued members never start; `serial` is already fail-fast (flag is
a no-op), and `rolling` additionally cancels in-flight siblings inside the
failing batch. A cancelled member is a distinct outcome from a failed one —
its phase status, its `err.kind`, and which hooks it fires are all specified
in [§6.2](#cancelled-member). In short: the in-flight op finishes (relay kills
nothing), the chain stops at the next op, `finally` runs and `on_failure` does
not. A member that never started records every phase `"pending"` and fires no
hooks at all — not `"skipped"`, which means `when = false`.

**`on_failure` and `finally` are per member, regardless of strategy or
fail-fast policy** — with the one asymmetry fail-fast introduces: a **failed**
member fires both, a **cancelled** member fires only `finally`. The hooks run
against the member's `ctx` exactly as in
[§6.2](#62-failure-handling-on_failure-and-finally); what siblings do is
otherwise independent. The task's overall result is failure if any member
failed; the CLI reports per-target outcomes:

```
web01 ✓
web02 ✗ exit 1 [migrate: exit]
web03 ⊘ cancelled [migrate — web02 failed]
web04 · pending
```

**Streaming under fan-out.** Out-of-order bytes are a *display* problem only —
each `(task, target)` result is captured independently. The console mux keeps
output readable:

- Planner opens up to `max` agent connections concurrently.
- One writer owns stdout/stderr; it receives `(label, line)` tuples and writes
  `dim("[web01]") + line` **atomically**, line by line. Line-level atomicity
  prevents mid-line garbage (the actual ugly case).
- Default to **status lines** (`web01 ✓ stage`, `web02 … activate`) under
  parallel unless `-v`; stream raw detail only on failure. Keeps it readable
  when `max` is high.

```
[web01] systemctl restart nginx
[web02] systemctl restart nginx
[web03] … activate        (status line, no raw stream)
```

**What relay does NOT do — and why:**

| rejected | reason |
|---|---|
| parallel phases within one target | fights Lua (single-threaded); phases are ordered by design |
| DAG `needs`/`deps` between phases | spec + execute + render = a build system; array order is simpler |
| async `ctx.run` returning a future | second execution model; out of scope |
| cross-target deps ("web needs db") | ordered members under `serial`, or two tasks in sequence (`relay deploy db && relay deploy web`) |

**The boundary: relay owns cross-target fan-out; the build tool owns
intra-machine parallelism.** Don't look for "run two `ctx.run` in parallel" in
relay — call your build tool from a single `ctx.run` and let it schedule
internally; relay sees one command and one result. The build-once /
deploy-many shape is a pinned build phase (`target = "localhost"` or the build
host) followed by a per-target fan-out deploy.

```lua
-- The build tool parallelizes internally; relay runs one subprocess.
ctx.localhost.run("make -j8 build")
```

## 11. Example gallery

Each example is complete and runnable. They progress from the four-step mental
model to the advanced cases, in order of how much of the API they touch.

### 11.1 Run one command (ad-hoc, no Lua)

```sh
relay exec web01 -- uname -a
relay exec web01 -- systemctl status nginx
```

### 11.2 The minimal deploy (write a file, reload)

```lua
local CONF = [[
server {
    listen 80;
    server_name example.com;
    root /var/www/example;
}
]]

local svc = require("recipe.service")   -- init dispatch (§11.17)

host({ name = "web01", hostname = "web01.example.com", user = "deploy", sudo = true })

task("deploy", function(ctx)
  ctx.fs.write("/usr/local/etc/nginx/sites/example.conf", CONF, { mode = "0644" })
  ctx.run("nginx -t")               -- validate config
  svc.reload(ctx, "nginx")          -- graceful where the init supports it
end)
```

That is a complete, correct, deployable script. No `app{}`, no `ctx.paths`, no
jail, no executor choice, no per-op `as_user`. This is the v3 north star.

One thing it does *not* do, so that the example stays one screen: undo the
write when `nginx -t` rejects it. `run` raises on non-zero, so the task fails
before the reload and nginx keeps serving the old config from memory — but the
broken file is on disk, and the next reload from anywhere (logrotate, a
reboot, another operator) picks it up. A production version reads the old
content first and restores it in `finally`
([§6.2](#62-failure-handling-on_failure-and-finally)); write-then-validate is
only safe when something puts the file back.

### 11.3 Install packages, enable a service, write a config

```lua
local svc = require("recipe.service")

host({ name = "web01", hostname = "web01.example.com", user = "deploy", sudo = true })

local VHOST = [[
server { listen {{.port}}; server_name {{.host}}; root {{.root}}; }
]]

task("bootstrap", function(ctx)
  ctx.run("apt-get update")
  ctx.run("apt-get install -y nginx certbot ufw",
          { env = { DEBIAN_FRONTEND = "noninteractive" } })   -- a deploy has no tty to answer debconf
  local conf = assert(ctx.localhost.fs.read("nginx.conf"))
  ctx.fs.write("/etc/nginx/nginx.conf", conf, { mode = "0644" })
  ctx.fs.write("/etc/nginx/sites-enabled/app.conf",              -- {{.key}} only (Appendix A)
               relay.render(VHOST, { port = 8080,
                                     host = "app.example.com",
                                     root = "/var/www/app/current" }),
               { mode = "0644" })
  svc.enable(ctx, "nginx")
  svc.restart(ctx, "nginx")
  ctx.run("ufw allow OpenSSH")            -- BEFORE enable, or the next deploy can't connect
  ctx.run("ufw allow 'Nginx Full'")
  ctx.run("ufw --force enable")
end)
```

> **The `ufw allow OpenSSH` line is not optional.** `ufw`'s default policy is
> deny-incoming, and `--force` is precisely the flag that skips its
> *"Command may disrupt existing ssh connections. Proceed (y|n)?"* prompt — the
> one interactive guard against this, removed because a deploy has no tty. The
> failure is delayed, which is what makes it bad: `ufw` permits established
> connections, so the current session survives and the task reports success.
> The *next* connection is refused, and relay has locked itself out of the
> host. Recovery is console or rescue access, not another deploy.
>
> `OpenSSH` is a Debian/Ubuntu app profile for port 22. A host declaring a
> non-default `port` ([§5.1](#51-host--the-one-required-declaration)) needs
> that port allowed explicitly (`ufw allow 2222/tcp`); the profile will not
> cover it.

### 11.4 Conditional on remote state

```lua
task("ensure-user", function(ctx)
  local r = ctx.run("id -u myapp", { ignore_exit = true })   -- portable probe
  if r.exit_code ~= 0 then
    ctx.run("useradd -r -s /usr/sbin/nologin myapp")         -- Linux; FreeBSD is `pw useradd`
    ctx.log.info("created user myapp")
  else
    ctx.log.info("user myapp already exists")
  end
end)
```

`id` is portable; `useradd` is not — FreeBSD has `pw useradd -n myapp -s
/usr/sbin/nologin`. A script that runs on both branches on
`ctx.self.platform` ([§6](#6-tasks-and-ctx)), which is what that field is for.

### 11.5 Capture command output and branch

```lua
task("scale-workers", function(ctx)
  local load = ctx.run("cut -d' ' -f1 /proc/loadavg").stdout   -- Linux; FreeBSD: `sysctl -n vm.loadavg`
  local workers = assert(tonumber(load), "unreadable loadavg: " .. load) > 4 and 8 or 2
  ctx.run({ "myapp", "set", "workers", tostring(workers) })   -- argv: a value goes in a slot
end)
```

### 11.6 Local build, remote artifact deploy (with the capistrano recipe)

A release-based deploy uses a recipe — a plain Lua module over core primitives
(defined in [§11.14](#1114-a-deploy-recipe-plain-require)). You hand it the
facts; it returns deploy + rollback task specs:

```lua
local cap  = require("recipe.capistrano")
local svc  = require("recipe.service")
local site = cap.new({
  name    = "myapp",
  target  = "web01",
  tarball = "build/myapp-linux-amd64.tar.gz",
  shared  = { files = { ".env" } },
  build   = function(ctx) ctx.run("make release-linux-amd64") end,   -- ctx IS the build target (recipe pins the build phase to localhost)
  restart = function(ctx) svc.restart(ctx, "myapp") end,
  health  = "http://web01.example.com/healthz",
})

host({ name = "web01", hostname = "web01.example.com", user = "deploy", sudo = true })

task("deploy",   site.deploy)
task("rollback", site.rollback)
```

Copy the recipe into your config dir and edit any line — it's your code, not
relay's. §11.14 shows the whole file.

### 11.7 Atomic pointer swap (the activate/rollback primitive)

`fs.symlink{atomic=true}` is the zero-window swap every release-style deploy
is built on — create a temp symlink, `rename(2)` over the target. A recipe
calls it; you can too:

```lua
task("activate", function(ctx)
  local release = relay.path.join("/var/www/myapp/releases", ctx.vars.release_id)  -- your deploy's id
  ctx.fs.symlink(release, "/var/www/myapp/current", { atomic = true })
end)
```

### 11.8 Healthcheck with retry

```lua
host({ name = "api01", hostname = "api01.example.com", user = "deploy", sudo = true })

task("deploy", {
  target = "api01",
  phases = {
    -- ... stage, activate, restart ...
    { name = "healthcheck", run = function(ctx)
        local r, err = ctx.localhost.http.check("https://api.example.com/healthz", {
          expect_status = 200,
          timeout       = 5,
          retries       = 5,
          retry_wait    = 2,
        })
        -- reads don't raise; assert to fail the phase on an unhealthy response
        assert(r and r.status == 200,
               "healthcheck failed: " .. (err or ("status " .. (r and r.status or "?"))))
      end },
  },
})
```

The probe runs from `ctx.localhost` — the operator — so it checks the endpoint
the way a user reaches it, through the load balancer and TLS. `ctx.http.check`
would probe from the target itself, which answers a different question
(§7.3).

### 11.9 Idempotent guard

```lua
host({ name = "app01", hostname = "app01.example.com", user = "deploy", sudo = true })

task("migrate", function(ctx)
  local app_dir = "/var/www/myapp/current"
  -- Only run the migration if the marker file is absent
  ctx.run({ relay.path.join(app_dir, "migrate"), "up" },
          { unless = { "test", "-f", relay.path.join(app_dir, ".migrated") } })
  -- The guard is argv too: a computed path never goes into a shell string (§7.1).
end)
```

### 11.10 Env-driven config (deploy flavors)

```lua
local git = require("recipe.git")   -- §11.16

-- relay.env returns `default` for unset OR empty (go-lua's os.getenv can't tell them apart)
local env      = relay.env("APP_ENV", "staging")
local branch   = relay.env("BRANCH", "main")

task("deploy", function(ctx)

  ctx.localhost.run("make release")

  local r, herr = ctx.localhost.http.check(health, { expect_status = 200 })

```

### 11.11 Multi-host group deploy

```lua
host({ name = "web01", hostname = "web01.example.com", user = "deploy", sudo = true })
host({ name = "web02", hostname = "web02.example.com", user = "deploy", sudo = true })
group({ name = "web", members = { "web01", "web02" } })

local cap  = require("recipe.capistrano")
local svc  = require("recipe.service")
local site = cap.new({
  name    = "myapp",
  target  = "web",                        -- a group: phases run once per member
  tarball = "build/app.tar.gz",
  build   = function(ctx) ctx.run("make release") end,   -- → a pinned phase, once
  restart = function(ctx)
    svc.restart(ctx, "myapp")
    ctx.log.info("deployed to " .. ctx.self.name)
  end,
})

task("deploy",   site.deploy)
task("rollback", site.rollback)
```

`build` becomes a pinned phase (runs once, on the operator); the release/activate/
restart phases fan out across the group, `ctx` rebound per member.

### 11.12 Build on a separate host, deploy to the target

```lua
local svc = require("recipe.service")

host({ name = "build00", hostname = "build00.example.net", user = "ci" })
host({ name = "web01",   hostname = "web01.example.com",   user = "deploy", sudo = true })

task("deploy", {
  target = "web01",
  phases = {
    { name = "build", target = "build00", run = function(ctx)
        ctx.run("make release", { cwd = "/srv/repo" })   -- ctx IS build00
        local sha = ctx.run({"git", "-C", "/srv/repo", "rev-parse", "--short", "HEAD"}).stdout
        -- build00 -> operator (typed download; no build00->web01 ssh needed)
        ctx.fs.download("/srv/repo/build/app.tar.gz", "tmp/app-" .. sha .. ".tar.gz")
        ctx.shared.artifact = "tmp/app-" .. sha .. ".tar.gz"   -- operator-side; hand off
      end },
    { name = "deploy", run = function(ctx)
        -- operator -> web01 (ctx.shared read here on web01; the file lives on the operator)
        ctx.fs.upload(ctx.shared.artifact, "/var/www/myapp/app.tar.gz")
        ctx.fs.extract("/var/www/myapp/app.tar.gz", "/var/www/myapp")
        svc.restart(ctx, "myapp")
      end },
  },
})
```

The build-time SHA is unknowable at declaration time and uncomputable on
`web01` (the build ran on `build00`); `ctx.shared` is the only bridge. Scope
rule and the `parallel` footgun are in [§6 (`ctx.shared`)](#6-tasks-and-ctx).

### 11.13 FreeBSD jail deploy (the advanced case)

build-on-host, stage-into-jail deploy written twice, once on a root agent

### 11.14 A deploy recipe (plain `require`)

A release layout is not a relay feature — it is conventions (a directory
structure, a shared dir, a symlink swap, a restart), every piece a core
primitive. So a "capistrano deploy" is a plain Lua module over those
primitives. relay ships it as a readable, copyable file (`relay init` places a
copy in your config dir, so `require("recipe.capistrano")` resolves; §9); edit
any line.

The full module lives at
[`examples/recipe/capistrano.lua`](../examples/recipe/capistrano.lua)
(`relay init` drops a copy in your config dir, so `require("recipe.capistrano")`
resolves; §9). Its shape: a factory `M.new(cfg)` returns two task specs —
`deploy` (build → release → activate → cleanup) and `rollback` — over
`fs.symlink{atomic=true}`, `fs.readlink`, `fs.list`, `fs.remove`, plus
`check_health`/`prune` helpers. Edit any line.

Using it (a one-screen deploy):

```lua
local cap  = require("recipe.capistrano")
local svc  = require("recipe.service")
local site = cap.new({
  name = "astro-site", target = "web01", root = "/var/www/astro",
  tarball = "build/astro.tar.gz", shared = { files = { ".env" } },
  restart = function(ctx) svc.restart(ctx, "astro") end,
  health  = "https://astro.example.com/healthz",
})
host({ name = "web01", hostname = "astro.example.com", user = "deploy", sudo = true })
task("deploy", site.deploy)   -- "web01" resolves HERE, not in cap.new (§5)
```

Other deploy shapes (docker-compose, git-checkout, binary-replace) are the same
kind of module — none of them need core support, because everything they do is
`fs.*`, `run`, and an atomic symlink. This is what it means for
relay to ship primitives, not a deploy model. Package install is too — `run`
plus `ctx.self.platform.package_manager`, no `ctx.pkg`; see §11.15.

### 11.15 A package recipe (the other recipe shape)

Package install is the same story as the release layout: not a primitive, just
`run` + `ctx.self.platform.package_manager`. relay ships no `ctx.pkg` on
purpose — there are too many managers (apt, dnf, apk, pkg, zypper, …), each
with its own install flags, presence probes, and lock/update semantics, to bake
one shape that is right for all of them. A recipe over the primitives is honest
and trivially editable. Where capistrano (§11.14) is a *task-spec factory*, a
package recipe is the other shape — a bag of `ctx`-taking functions you call
from a phase:

The full module lives at [`examples/recipe/pkg.lua`](../examples/recipe/pkg.lua).
Its shape: a per-manager dispatch table (apt worked out, the rest sketched)
keyed by `ctx.self.platform.package_manager`, exposed as `M.installed(ctx,
name)` (a read) and `M.ensure(ctx, names)` (an idempotent action). Edit the
dispatch table for your fleet.

Using it (the §11.3 bootstrap, rewritten over the recipe):

```lua
local pkg = require("recipe.pkg")
local svc = require("recipe.service")

host({ name = "web01", hostname = "web01.example.com", user = "deploy", sudo = true })

task("bootstrap", function(ctx)
  pkg.ensure(ctx, { "nginx", "certbot", "ufw" })   -- core run + detection, editable
  local conf = assert(ctx.localhost.fs.read("nginx.conf"))
  ctx.fs.write("/etc/nginx/nginx.conf", conf, { mode = "0644" })
  svc.enable(ctx, "nginx")
  svc.restart(ctx, "nginx")
end)
```

`require` resolves deterministically against the config file's directory:
`<config_dir>/?.lua` and `<config_dir>/?/init.lua`. Not consulted: the process
CWD, `LUA_PATH`, system Lua dirs, C modules. Whether a config resolves depends
only on the repo's contents. The one sanctioned escape hatch is visible at the
top of a file:

```lua
package.path = package.path .. ";/opt/shared-deploy/?.lua"
```

### 11.16 A git recipe

Core ships no `git` op. By the rule in [§11.17](#1117-the-corerecipe-line) it
never could: driving `git` means spawning a foreign binary, and that is what
`run` is for. `git`'s own shape says the same thing twice over — it is the same
binary everywhere, so a core op would abstract no difference, and it would have
to bake exactly one answer to every question the tool leaves open: ff-only vs
rebase vs `reset --hard`, submodules, LFS, sparse checkout, tags vs branches.
Recipe form hands all of that back.

The module lives at [`examples/recipe/git.lua`](../examples/recipe/git.lua)
(`relay init` drops a copy in your config dir). Its shape is the package
recipe's — a bag of `ctx`-taking functions — with one deliberate difference:
**the first argument is an executor, not `ctx`.**

```lua
local git = require("recipe.git")

git.sync(ctx,                url, "/opt/site/vendor", { branch = "main" })
git.sync(ctx.host,           url, "/home/deploy/src", { strategy = "reset" })
git.sync(ctx.on("build00"),  url, "/srv/app",         { submodules = true })
local head = assert(git.head(ctx.localhost, "."))     -- { branch, sha, dirty }
```

That is the whole namespace story, and it is why the recipe form is *safer*
here rather than merely smaller. The executor you pass decides where git runs
and which filesystem it sees, together. On a jail target `git.sync(ctx, ...)`
is `jexec`-ed git on jail paths — hooks and repo-local `.git/config`
(`core.sshCommand`, `diff.external`, …) execute inside the confinement that
owns those files. `git.sync(ctx.host, ...)` is the host's git on host paths.
There is no argument spelling "this machine's git, that machine's paths": no op
argument can name a mountpoint (§10.2). Cross the boundary
with `fs.*` and a tagged path (§10.3) — the build-on-host, stage-into-jail
pattern — which is what tagged paths exist for.

A core `git.*` had the opposite property: `dir`/`dest` was just an argument, so
`ctx.host.git.clone(url, ctx.path("/opt/app"))` type-checked while asking the
host's git, as root, to run jail-owned hooks against a path a jail-planted
symlink could redirect anywhere. Guarding that needed a dispatch-time rule tying
each `git.*` path to its executor's namespace. The recipe deletes the rule
instead of enforcing it. Someone who hardcodes `/usr/jail/web/opt/site` into a
host-side `run` still gets exactly what they asked for — that is their call to
make, and it is visibly a raw host path rather than an argument that looked
right.

Two properties of the jail case are worth stating because they are *not*
restrictions the recipe imposes — they follow from where the command runs.
Jail-side git needs git installed in the jail (a missing binary is `run`'s own
"not found", nothing git-specific). And a routed jail's SSH connection lands on
the physical host, so a `jexec`-ed git cannot see the forwarded ssh-agent
(§5.1): a private repo cloned *inside* a jail needs a deploy key there, or
clone host-side and stage in.

The probe functions (`head`, `is_clone_of`) pass `read_only = true` to `run`
(§7.1). Without it `--dry-run` stubs them to `exit_code = 0, stdout = ""` and
every caller reads a fabricated sha; with it they are classified reads and
really execute, exactly like the core reads they replace.

### 11.17 The core/recipe line

One rule decides what is an op and what is a module you can edit:

> **What the agent implements in-process is core. What drives a foreign binary
> is a recipe.**

Three tiers, because the rule needs its boundary stated or it looks violated
the first time someone greps the agent for `exec`:

| Tier | Rule | Examples |
|---|---|---|
| **Agent internals** | any binary; not user surface, so no contract | `ssh`, `jls` and `jexec` (§10.2), platform detection (§6) |
| **Core ops** | in-process in the agent; never drives a tool it does not ship | `fs` (syscalls, `rename(2)`, checksums), `http` (`net/http`), `log`, `sleep` |
| **Recipes** | drives a foreign binary — `run` plus argv and output parsing | `pkg` (§11.15), `git` (§11.16), `service` (below) |

`run` is core and is the exception that proves the shape: it *is* the exec
primitive rather than a wrapper over one. Everything in the recipe tier is
`run` with a name on it.

The rule is not aesthetic. A core op that shells out has to bake the tool's
policy, and it does it invisibly, in a binary you cannot edit — apt's flags,
git's merge strategy, whether `enable` also starts the service. A recipe puts
the same decision in a Lua file in your config dir, where it is `relay init`
output you own rather than a spec clause you argue with.

**Service control is the worked example.** relay ships three modules rather
than one `ctx.service`:

```lua
local svc = require("recipe.service")     -- dispatches on ctx.self.platform.init
svc.restart(ctx, "nginx")
svc.enable(ctx, "nginx")                  -- persist the boot flag, start nothing
svc.enable(ctx, "nginx", { now = true })  -- systemd's --now; raises on rc.d
svc.disable(ctx, "nginx")                 -- the other half of the lifecycle
local s = assert(svc.status(ctx, "nginx"))   -- { running, enabled, state }
```

The dispatcher holds only what the two inits disagree about. The substance is in
[`examples/recipe/systemd.lua`](../examples/recipe/systemd.lua) and
[`examples/recipe/rcd.lua`](../examples/recipe/rcd.lua), kept apart because the
two inits do not agree and a portable-looking op could only hide that:

- **`enable` is not one operation.** systemd's enables *and starts*; rc.d's
  `sysrc nginx_enable=YES` persists a flag and starts nothing. The recipes make
  both verbs mean "persist the flag" and put systemd's `--now` behind an opt,
  so the portable spelling is portable. A core op would have had to pick one
  meaning and be wrong on one platform.
- **rc.d spans two tools.** `service` runs it now; `sysrc` decides whether it
  survives a reboot. A single verb over two binaries is exactly the seam worth
  making visible.
- **`state` is not portable and never was.** systemd's `SubState`
  (`active`/`failed`/`activating`/…) has no rc.d counterpart; rc.d reports
  `running` or `stopped` and nothing finer, because an rc.d status line is
  prose and go-lua has no pattern engine (Appendix A). Branch on `running`.
- **`{ user = true }`** is systemd's user manager. It lives in
  `recipe/systemd.lua`, where it is obviously platform-specific, instead of
  hanging off a portable-looking op with no stated rc.d behavior.

Shape follows §11.15 rather than §11.16: `service.lua`'s first argument is
`ctx`, not an executor, because dispatch reads `ctx.self.platform.init` and
`self` lives only on `ctx` ([§6](#6-tasks-and-ctx)) — every
platform-dispatching recipe is target-only for that reason, `pkg` included. The
per-init modules take an executor, so a different machine is reachable by
naming its init once:

```lua
local rcd = require("recipe.rcd")
rcd.restart(ctx.host, "nginx")            -- the jailer, not the jail
rcd.restart(ctx, "nginx")                 -- jexec-ed into the jail (§10.2)
```

`status` passes `read_only = true` for the same reason every recipe probe does
(§11.15): without it `--dry-run` stubs the probe and every service reads as
stopped.

What the move costs, stated rather than buried: rc.d's `state` is coarser than
a Go implementation could make it, and a restart — the closing line of most
deploys — now needs a `require`. `relay init` drops all three modules in your
config dir, so it is one line at the top of a file you already have.

**And nothing stops you skipping all of it.** The recipe is the recommendation,
not a gate; `run` is core, and an init binary is just a binary:

```lua
local unit = "myapp.service"
ctx.run("systemctl restart nginx")                    -- fine, and sometimes right
ctx.run({"systemctl", "restart", "--no-block", unit}) -- argv: `unit` is variable data
```

Do that when you want systemd's own surface — a flag the recipe does not
expose, `systemd-run`, a unit template, `journalctl` in the same breath — or
when the fleet is systemd-only and a `require` for one line is not worth it.
What you give up is exactly what the recipe was buying: the script now names a
platform, so it raises `command not found` on the first FreeBSD host it meets,
and `enable` means whatever the local init thinks it means. That is a
legitimate trade on a homogeneous fleet and a bug on a mixed one. This is also
why the examples throughout this spec call `svc.restart` rather than
`systemctl`: they are copy-paste sources, and the portable spelling is the one
worth copying. Ad-hoc is the other exception — `relay exec web01 -- systemctl
restart nginx` ([§9](#9-cli)) is one command on one box you are looking at, not
a deploy script that outlives the decision.

## 12. Calling conventions

One rule set, no exceptions:

1. **Actions** (verbs that do something): required operands **positional**, in
   subject-object order (`src, dst` / `archive, dest` / `target, link`), then
   **one optional trailing opts table**. Nothing required hides in opts;
   nothing optional is positional. When an operand is a *set* whose members
   are individually optional but not collectively — `fs.chown`'s
   `{ owner, group }`, where either may be omitted and both may not — it is a
   **required positional table**, still an operand, not the opts table. The
   alternative spelling (`chown(path, owner, group?)`) is the optional
   positional this rule exists to forbid, and it makes
   `chown(p, nil, "www")` the way to set a group.

2. **Declarations** (`host`, `vars`, `group`, `jail`): a **single spec table**.
   Declarations are records, not calls-with-arguments.

3. **`run`'s two forms by purpose, not ceremony:** a string runs as a shell
   command; a table runs as an argv array with no shell. Both are primary.

4. **Modes are octal strings** (`"0644"`). Integers are rejected at the call
   site (dispatch time, §4.3), or by `relay validate` when the mode is literal.

5. **No variadic argument lists, no overloads by arity.**

LuaLS stubs are regenerated from Go descriptors (`lua/api/`) so arity and field
names are machine-checked in the editor.

## 13. Result shapes

Three shapes, by purpose:

| Op kind | Shape | Example |
|---|---|---|
| `run` | `{ exit_code, stdout, stderr, ran, executed }` | `{ exit_code = 0, stdout = "...", stderr = "", ran = true, executed = "sudo -n -u root /usr/sbin/service nginx restart" }` |
| mutating `fs` | `{ changed }` (+ `dry_run` under `--dry-run`) | `{ changed = true }` |
| `fs.mktemp` | a path string — never `{ changed }`, including under `--dry-run`, which returns a synthetic path ([§4.4](#44-dry-run)) | `"/tmp/relay.a8f3c1"` |
| read ops | `(value, err)` — value + nil err, or nil/false + err | `fs.read → string, err` · `fs.exists → bool, err` · `fs.stat → { … }, err` · `http.check → { status, body, headers, url, elapsed, attempts }, err` |

Notes on `run`:
- `stdout` and `stderr` are **also streamed live** to the operator's console as
  they arrive; the result holds the full captured text after exit.
- With `tty = true`, `stderr` is empty (folded into the pty's single stream);
  see [§7.1](#71-run).
- `exit_code` is the wait status: `0` success, `1–255` non-zero, `128 + signal`
  for a signal kill (including a `timeout` kill).
- `timed_out` is `true` only when the command was killed by `timeout` (§7.1);
  absent otherwise. Branch on it (with `ignore_exit = true`) to tell a hang from
  a normal non-zero exit.
- `executed` is the exact post-wrap command string relay ran (or, under
  `--dry-run`, would have run): the escalation prefix (`sudo -n -u root …`,
  `doas -u …`, `jexec -u …`) plus resolved argv, `cwd`, and env. Lets a script
  log or branch on what actually executed; on failure the same string appears
  on the error ([§6.1](#61-error-model)). Env and argv appear **verbatim**,
  except values marked secret via `relay.secret` / `relay.secret_file` (§7.1),
  which show as `<redacted>` — the real value still ran. (A command that prints
  its own env leaks it via stdout; that is the program's doing, not relay's —
  see §7.1.)
- `ran` is whether the command executed: `true` after dispatch, `false` when
  skipped by `onlyif`/`unless` or under `--dry-run`. Those two stay
  distinguishable when both apply: guards execute under `--dry-run`
  ([§4.4](#44-dry-run)) and `dry_run` marks a *stub*, so a guard-skipped op
  carries `ran = false` alone. Not a state-change claim — relay cannot know
  whether an arbitrary command altered the host; branch on
  `exit_code`/`stdout` for that. (Mutating ops use `changed` for real
  state-change; `run` uses `ran` precisely because it can't.)
- `changed` (mutating ops) is `true` when the op actually altered state, `false`
  when it was a no-op (target already in desired state — idempotency). Under
  `--dry-run` it is an **optimistic prediction** (`true`), set so downstream ops
  in a cascade are traced — not a real state-change claim; pair with `dry_run`
  to know.

Principle: **reads return `(value, err)` (never raising); write ops report
whether they changed (`changed`); `run` reports whether it ran (`ran`) plus the
full execution.** Every op's result is documented at its call site in
[§7](#7-operations-core).

## 14. Migration: v2 → v3

A mechanical rewrite. v3 breaks the API by design.

| v2 | v3 | Notes |
|---|---|---|
| `ctx.target.run(...)` | `ctx.run(...)` | `ctx` is the executor; `ctx.target` removed |
| `ctx.target.fs.*` | `ctx.fs.*` | all op modules moved up to `ctx` |
| `run({"a","b"})` (table primary) | `run("a b")` (string primary) **or** `run({"a","b"})` | both work; string is now the documented default |
| `run("shell", { shell = true })` | `run("shell")` | shell is the default for strings; `shell` opt removed |
| `service.restart(svc, { as_user = "root" })` | `require("recipe.service").restart(ctx, svc)` + `host{ sudo = true }` | no core service op (§11.17); privilege declared on host, inherited |
| `fs.write(p, c, { as_user = "root" })` | `fs.write(p, c)` + `host{ sudo = true }` | same |
| per-op `as_user = "..."` | per-op `as = "..."` | override, renamed |
| `ctx.target.as("root")` | `phase{ as = "root" }` or per-op `as = "root"` | block-scoped view removed; use phase default or per-op |
| `host{ ssh_user=..., deploy_user=... }` | `host{ user = ... }` | one field; per-op `as` to differ |
| `host{ privilege = { method="sudo", as_user="root", mode="non-interactive", escalation="sudoers" } }` | `host{ as="root", escalate={ via="sudoers" } }` | or just `sudo = true` |
| `host{ platform = { ... } }` (required, hard-fail) | `host{ expect = { ... } }` (optional assertion) | auto-detected by default |
| `app{}` / `ctx.paths` / `ctx.release.*` | **removed from core** | no deploy model baked in; capistrano is a recipe (§11.14) |
| `ctx.pkg.*` (`ensure`/`installed`) | **removed from core** | too many managers to bake; pkg is a recipe (§11.15) |
| `ctx.git.*` (`clone`/`sync`/`head`) | **removed from core** | abstracts no platform difference — `run` plus parsing — while baking one branch strategy; git is a recipe (§11.16). Probes stay real reads via `run { read_only = true }` (§7.1) |
| `host{}`/`jail{}`/`vars{}`/`group{}` (return ignored) | each returns a **ref** | capture for typo-safe references; optional |
| `ctx.app` / `ctx.paths` / `ctx.release.*` | `ctx.vars` (opt-in `vars{}`, §5.2) | release shape → recipe |
| `ctx.release_id` | **removed from core** | capistrano concern; the recipe (§11.14) sources its own id in `M.new` (plan time, closure-captured); a custom deploy can use `ctx.vars.release_id` |
| `local function env(name, def) ... end` | `relay.env(name, def)` | built-in; kill the hand-rolled helper |
| `ctx.target_name` | `ctx.self.name` | target identity moved under `ctx.self` |
| `ctx.localhost` | `ctx.localhost` | unchanged (`local` is a Lua keyword) |
| `ctx.host` (jail) | `ctx.host` (jail) | unchanged; jailer executor (identity via `ctx.self.host`) |
| `jail{ jname = "web" }` | `jail{ match = { name = "web" } }` | the default; `match` also selects on `hostname`/`jid`/`path`, or a predicate (§10.2) |
| `ctx.self.jname` | `ctx.self.jail` | the whole resolved `jls` row — `{ jid, name, hostname, path }` |
| `ctx.fs_root()` + string concat | `fs_access` + tagged paths | jail `fs.*` runs inside the jail by default (§10.2); the mountpoint is never script text |
| `ctx.on(name)` | `ctx.on(ref \| "name")` | now also accepts a ref from `host{}`/`jail{}` |
| `eval` / `eval_file` | `eval` / `eval_file` | unchanged; advanced |
| `phases` body with `ctx.localhost.run(...)` for build | pinned phase: `{ name="build", target="localhost", run=... }` | build runs once on the operator, not per target (§6) |
| (no equivalent) | `finally = function(ctx, summary)` | always-run per-member cleanup hook (§6.2) |
| tagged paths (`executor.path`) | tagged paths (`executor.path`) | unchanged |
| `mode = "0644"` | `mode = "0644"` | unchanged |

**Net effect on the v2 README example** (a single-host artifact deploy):

v2 (~22 lines of body, `{ as_user = "root" }` × 2, `ctx.target` everywhere):

```lua
app({ name="myapp", root="/var/www/myapp", deploy_user="deploy", keep_releases=5,
      shared={ dirs={"logs"}, files={".env"} } })
host({ name="web01", hostname="web01.example.com", ssh_user="deploy",
       privilege={ method="sudo", as_user="root", mode="non-interactive" },
       expect={ os="linux", arch="amd64", init="systemd", package_manager="apt" } })
task("deploy", { target="web01", phases={
  { name="build", run=function(ctx) ctx.localhost.run({"make","release"}) end },
  { name="release", run=function(ctx)
      ctx.target.fs.upload("build/myapp-linux-amd64.tar.gz", ctx.paths.release.."/app.tar.gz")
      ctx.target.fs.extract(ctx.paths.release.."/app.tar.gz", ctx.paths.release)
      ctx.target.fs.symlink(ctx.paths.shared.."/.env", ctx.paths.release.."/.env")
  end },
  { name="activate", run=function(ctx)
      ctx.target.release.activate(ctx.paths.release, ctx.paths.current)
      ctx.target.service.restart("myapp", { as_user="root" })
      ctx.localhost.http.check("http://web01.example.com/healthz", { expect_status=200 })
  end },
  { name="cleanup", run=function(ctx)
      ctx.target.release.prune(ctx.paths.releases, { keep=ctx.app.keep_releases })
  end },
}})
```

v3 (same deploy, same safety, less ceremony — and the release shape is now a
recipe you can read and edit, not a baked-in keyword):

```lua
local site = require("recipe.capistrano").new({
  name="myapp", target="web01", root="/var/www/myapp",
  tarball="build/myapp-linux-amd64.tar.gz", shared={ files={".env"} },
  build  =function(ctx) ctx.run("make release") end,   -- ctx IS the build target
  restart=function(ctx) require("recipe.service").restart(ctx, "myapp") end,
  health ="http://web01.example.com/healthz",
})
host({ name="web01", hostname="web01.example.com", user="deploy", sudo=true })
task("deploy", site.deploy)
```

The required `platform` declaration is gone (now optional `expect`);
both `as_user` repetitions, every `ctx.target.` prefix, the
`deploy_user`/`ssh_user` split, and the `privilege` subtable are gone too. Nothing about safety is lost: the host declares root once, every op logs
its identity, and per-op `as` remains for overrides.

## 15. Open questions

These are deliberately unresolved for the iteration round. The body cites them
**by anchor and title, never by number** — the numbers here renumber as
questions resolve, and a citation that names one cannot survive that.

1. <a id="oq-agent-lua-identity"></a>**Agent Lua identity.** v2 had `ctx.as_agent(u).eval(...)` for whole-script
   identity and `as(u)` for per-op. Does v3's "privilege declared on host,
   inherited" model extend cleanly into `eval`, or does `eval` need its own
   `as` story? Leaning: `eval` inherits the host default like everything else;
   drop `as_agent` unless a real script needs it.

2. <a id="oq-stdin-streaming"></a>**Large/streaming stdin.** `opts.stdin` (§7.1) is a string held fully in
   memory — fine for config files, SQL dumps, and prompt replies, but not for a
   multi-GB database restore or a pipe source. Add `opts.stdin_file = "<path>"`
   so the agent opens the file and streams it to the child's stdin (the path is
   in the executor's own namespace; for a local file use `ctx.localhost`'s)?
   Leaning: yes — `stdin` for the common small case, `stdin_file` for the
   large/streaming case. An even more general `stdin = { file = "..." }` form
   is rejected as over-engineering until a real script needs it.

3. <a id="oq-tty-default"></a>**`tty` default: `false` vs `auto`.** v3 defaults `tty = false` so a script
   means the same in CI and a terminal (§7.1). v2 defaulted to "auto" — on when
   the operator's stdout was a TTY — which made the result shape (separate
   `stderr` vs merged) depend on where `relay` ran. Is predictability worth
   losing the "interactive command feels interactive in a real terminal"
   convenience? Leaning: yes, default `false`; offer `tty = "auto"` as an
   explicit value if anyone wants the old behavior.

4. <a id="oq-port-forwarding"></a>**SSH port forwarding.** v3 adds agent forwarding (`host{ forward_agent =
   true }`, §5.1) — the common case, for private-repo git clones on a target.
   Port forwarding (`-L`/`-R`/`-D`) is not yet specified. It would let a phase
   reach a target-internal service from `ctx.localhost` (e.g.
   `ctx.localhost.http.check` against a DB admin port tunneled out of the
   target), or expose a local port to the target. Proposed shape:
   `host{ forward = { { local = 5432, remote = "localhost:5432" } } }`.
   Leaning: defer until a real deploy needs it — port forwarding is more
   `relay shell` / ad-hoc territory than deploy phases, and `ctx.http.check`
   on the target already reaches target-local endpoints without a tunnel.

5. <a id="oq-phase-expect"></a>**Phase-level hard preconditions.** v3 has soft guards (`onlyif`/`unless`/
   `when`, all *skip*) and hard stops (`host{ expect=... }` at connect, Lua
   `assert` inline), but no phase-scoped hard precondition that runs when the
   phase runs and fails the phase (not just skips it). Proposed:
   `phase.expect = function(ctx) return bool end` — a hard sibling of soft
   `when`. Leaning: defer — Lua `assert` at the top of the phase body already
   fails the phase with a custom message, and `when` covers the skip case, so
   the gap is narrow. Revisit if repeated `assert(ctx..., "...")` boilerplate
   at every phase top becomes a pattern.

6. <a id="oq-fanout-knobs"></a>**Remaining fan-out knobs.** The failure policy per `strategy` and the
   `fail_fast` field / `--fail-fast` flag are settled in
   [§10.7](#107-concurrency-fan-out-not-dags). Still open: (a) the `rolling`
   gate shape — a healthcheck function `gate = function(ctx) ... return bool`
   vs a simple `delay = "30s"`; (b) the default `max` when unspecified for
   `parallel` (leaning: 5, to bound connection load and console noise) and
   `rolling` (leaning: 1, strict canary).

7. <a id="oq-jail-metadata"></a>**Metadata link for direct-SSH jails.** §5.4 makes a direct-SSH jail a
   plain `host{}`, with no functional link to the physical machine it runs on
   (reach it via a second `host{}` + `ctx.on(...)`). Should a `host{}` accept
   an informational `jail_of = "prod00"` field — purely metadata for
   `relay doctor`/logging/aggregation, no execution effect — so a fleet view
   can group a jail with its host without two declarations implying a routing
   relationship? Leaning: defer until tooling actually wants the grouping; the
   execution model is complete without it.

8. <a id="oq-pinned-finally"></a>**`finally` for pinned phases.** A pinned phase is fail-fast-gated and
   member `finally` never runs against a pinned target ([§6.2](#62-failure-handling-on_failure-and-finally)),
   so always-run cleanup on a pinned target (build00's workdir, a
   half-applied migration) lives in the pinned phase's own body — `pcall` /
   `fs.withlock` scoping. Is that enough, or does a pinned phase need its own
   `finally` field? Leaning: defer — body-scoped cleanup covers the known
   cases; revisit if real scripts grow `pcall` boilerplate at the top of
   every pinned phase.

9. <a id="oq-per-jail-lock"></a>**Per-jail deploy locks.** `host{ lock }` serializes the physical machine,
   jails included ([§5.1](#51-host--the-one-required-declaration)) — correct
   for the host-vs-jail race, coarse for a jailer running twenty independent
   jails, whose deploys are serialized across sessions despite disjoint
   filesystems. Should `jail{ lock }` exist as a second, finer lock taken in
   addition to the jailer's? Leaning: defer — `ctx.fs.withlock` in a phase
   already gives per-jail serialization with `lock` left off, and a second
   declared lock needs an ordering rule (jailer's first, always) to avoid
   introducing a deadlock relay does not have today. Revisit if the
   many-jails-per-box case shows up with real scripts.

10. <a id="oq-http-unix-socket"></a>**`http` over a unix socket.** [§7.3](#73-http) addresses an endpoint by
    URL, which covers TCP and nothing else. Real targets expose admin
    endpoints on unix sockets — a container runtime, php-fpm's status page,
    an app's own control socket — and reaching one today means `run` of
    `curl --unix-socket`, which needs curl on the box and throws away the
    typed result. Proposed shape: `opts.unix_socket = "/var/run/docker.sock"`,
    the URL's host ignored, which is a `Transport.DialContext` in Go.
    Leaning: defer — the deploy-relevant question ("is my service up?") is
    normally reachable over loopback TCP, and the field can be added later
    without changing anything that exists.

### 15.1 Decisions log

Resolved during iteration; each is folded into the body. Kept as a record.

- **`service` is a recipe, not a core op** — the core/recipe line is "what the agent implements in-process is core; what drives a foreign binary is a recipe" ([§11.17](#1117-the-corerecipe-line)), and driving `systemctl`/`service`/`sysrc` is `run` with a name on it. Split per init (`recipe/systemd.lua`, `recipe/rcd.lua`, plus a `recipe/service.lua` dispatcher) because `enable` means "enable + start" on one and "persist a flag" on the other; one core verb could only hide that. Supersedes the earlier decision to add `service.reload` to core.
- **No `app{}` / release verbs in core** — a release layout is a recipe ([§11.14](#1114-a-deploy-recipe-plain-require)).
- **No `git` op in core** — it abstracts no platform difference and would bake one branch strategy; git is a recipe over `run` ([§11.16](#1116-a-git-recipe)), and `run { read_only = true }` keeps its probes classified as reads.
- **Jail `fs.*` runs inside the jail by default** — `fs_access = "attach"` forks a helper, `jail_attach(2)`s it, and runs the ordinary `fs` code there, so the kernel resolves paths and no jail-planted symlink can redirect a host-side root write. `"mountpoint"` keeps the host-side translated form for fleets with no root at all, with its three differences stated rather than implied. See [§10.2](#102-freebsd-jails).
- **`http` on a jail target stays on the host's network stack** — unlike `fs` and `run` it addresses an endpoint named in its argument rather than the machine's own resources, so the executor picks a vantage point, not a namespace. Routing it in would have to follow `fs_access` (the attached helper gets the jail's VNET; a `"mountpoint"` agent cannot attach), making one line mean two stacks depending on a privilege declaration. A loopback URL on a jail target raises instead of quietly probing the host. [§10.2](#102-freebsd-jails).
- **Jail lookup is `match`, not `jname`** — a selector over the `jls` row, because which identifier survives a jail restart (`jid` never, `name` sometimes, `host.hostname` usually) is a property of the jail manager, not something relay can assume. [§10.2](#102-freebsd-jails).
- **Per-task privilege default** — `task{}`/phase `as` narrows the host default; full precedence in [§8](#8-privilege-the-common-case).
- **Recipe library** — plain Lua modules (`require`), not `relay.recipe.*`; capistrano, pkg, git, and the two init modules behind `service` ship as examples ([§11.14](#1114-a-deploy-recipe-plain-require), [§11.15](#1115-a-package-recipe-the-other-recipe-shape), [§11.16](#1116-a-git-recipe), [§11.17](#1117-the-corerecipe-line)).
- **`as` over `as_user`** — `as`, consistent across host/task/phase/op.
- **Config templating is `relay.render`, a cut-down `text/template`** — go-lua has no `gsub`, so writing a config with N placeholders was `..` and `string.format`. relay is Go, so `text/template`'s parser is free; its *language* is not, and embedding it whole would re-admit a bigger language than the pattern engine v3 removed. Resolution: keep the parser, cut the grammar to literal text + `{{.key}}` (everything else is a parse error), `missingkey=error`, numbers rendered as Lua's `tostring`, no escaping, optional `delims`. Plus `relay.replace` for the plain-text one-placeholder case. Rendering is planner-side string work, so there is no `fs.template` op and no protocol change — `fs.write` takes the rendered string ([§7.2](#72-fs), Appendix A). Renders only: parsing structured output is a separate gap.
- **`local_` stays, `"localhost"` is the common path** — the reserved target name (§5.1) covers the bare operator; `local_` survives only for named configured local targets.
- **No `relay local` subcommand** — `relay exec localhost -- <cmd>` is the one-liner (§5.1, §9).
- **`relay exec` inherits the host's privilege default** — `as`/`escalate` apply exactly as they would to the same command in a phase, with `--as <user>` as the per-command override. The alternative (always the connection user unless `--as` is passed) would make one command mean two different things depending on whether it ran through a task, and `exec`'s pitch is that the declared target configuration is reused — its lock, its `user`, its escalation. See [§9](#9-cli).
- **`finally` hook — shipped** ([§6.2](#62-failure-handling-on_failure-and-finally)), with the flat phase model.
- **`http` is a complete client for three jobs, and TLS is a host declaration** — relay is Go, so `net/http` and its TLS stack are already linked in; the question was never what relay can afford to expose but what it means to expose. The answer is the three things a deploy does over HTTP — probe a service, call a webhook, fetch an artifact from somewhere that wants credentials — specified completely: `query`/`form` encoding (go-lua has no pattern engine, so a script cannot correctly encode a value it did not write), `body_file`/`out_file` so bulk bytes never enter a Lua string, `basic_auth` and `relay.secret`-markable header/query/form values, `max_body` + `truncated`, `follow_redirects`/`max_redirects`, `proxy`, and a result carrying `headers`/`url`/`attempts`/`size`. Dry-run follows the arguments, not the op name (RFC 9110's safe set executes; every other method — and any call carrying `out_file`, since writing a file is a state change — gets an optimistic stub). TLS is a `tls` sub-table declared on `host{}` and merged per call field by field, because a private CA is a fleet fact and not a call-site one — `ca`/`ca_pem`, `cert`/`key`, `server_name`, `insecure` (warned every call, linted by `relay validate`). `ca_pem` exists and `key_pem` deliberately does not: a bundle is public material that lives in the repo next to `relay.lua`, a private key belongs on the machine that uses it. Cookie jar, response streaming into Lua, websockets/SSE/HTTP/3, JSON, and TLS version pinning are named non-features, so a recipe author knows the edge of the surface. ([§7.3](#73-http), [§5.1](#51-host--the-one-required-declaration), [§4.4](#44-dry-run), [§9](#9-cli)).
- **`escalate.password` — a secret, not a dead bool** — `nil` (NOPASSWD, default) or a `relay.secret`/`relay.secret_file` marker fed to `sudo -S` on stdin; single-hop only (`A` = the ssh user, never `a→b→c`). The ssh user is the capability ceiling — if it lacks a path to the identity, declare a second `host{}` and pin the phase there. See [§10.4](#104-privilege-in-depth).

## Appendix A — go-lua gotchas

relay embeds [Shopify/go-lua](https://github.com/Shopify/go-lua), which is not
PUC-Lua. The differences are finite and documented; v3 ships helpers so none of
them bite silently.

- **No pattern engine.** `string.match`, `string.gmatch`, `string.gsub` do not
  exist (`attempt to call a nil value`). `string.find` is plain-substring only
  (`s:find(needle, 1, true)`). Use `relay.split` and the `relay.path.*`
  helpers for the deploy staples, `relay.replace` / `relay.render` for the
  write-a-config staple; use plain `find` for substring tests.
  Agent Lua carries a best-effort pattern shim but do not write portable
  scripts against it.
- **No octal literals.** `0644` is decimal 644, not the permission. Modes are
  octal **strings** — `mode = "0644"`. An integer mode is a dispatch-time error
  (§4.3).
- **`os.getenv` returns `""` not `nil` for unset vars**, and `""` is truthy in
  Lua, so `os.getenv("X") or default` never falls back. Use `relay.env(name,
  default)`, which treats unset-or-empty as "not configured."
- **`local` is a keyword.** `ctx.local.run(...)` is a syntax error. The local
  executor is `ctx.localhost`; the reserved target name is `"localhost"`
  (no declaration); the host flag for a *named* local target is `local_`
  (§5.1).
- **`relay.goos` / `relay.goarch`** are the *operator* machine's platform
  (where `relay` runs), not the target's. Use them to branch on where the
  deploy is driven *from* (e.g. skip a POSIX-only local step on a Windows
  operator); the target's platform lives on `ctx.self.platform`
  ([§6](#6-tasks-and-ctx)) — the agent's reported value, always present.

```lua
-- relay global: operator-side helpers + the one string op go-lua can't do
relay.env(name, default?)      -> string|nil   -- getenv with the "" / nil fix
relay.split(s, sep)            -> string[]     -- plain-text split. Needed:
                                               --   go-lua has no gmatch/gsub
                                               --   (no pattern engine) and
                                               --   Lua has no string.split.
relay.replace(s, from, to, n?) -> string, int  -- plain-text replace + count of
                                               --   replacements. `from` is a
                                               --   literal, never a pattern; an
                                               --   empty `from` is an error; `n`
                                               --   omitted replaces every
                                               --   occurrence.
relay.render(tmpl, vars, opts?) -> string      -- `{{.key}}` substitution over a
                                               --   flat table — the config
                                               --   templating helper. Grammar is
                                               --   text + single-field actions
                                               --   and nothing else; contract
                                               --   below.
relay.goos, relay.goarch                       -- operator platform constants
relay.secret(v)                -> marker        -- tag an `env` value secret: redacted in
                                               --   records (executed/errors/audit);
                                               --   the real value still reaches the
                                               --   child. `env` values only, not argv
                                               --   (§7.1).
relay.secret_file(path)        -> marker        -- tag a dotenv so every key parsed from
                                               --   it is secret; used in `env_files` (§7.1).

-- relay.path: POSIX path math. Wraps Go's `path` package, slash-only —
-- never `path/filepath`, which would import the operator's OS separator
-- into target paths (a Windows operator joining "/etc" + "nginx" must get
-- "/etc/nginx", not "\etc\nginx"). Every path a script builds flows into a
-- target fs/run op, and targets are POSIX (linux/freebsd); forward slash is
-- also accepted by Go's os layer on Windows for the rare operator-local
-- path, so POSIX join is correct on both sides.
--
-- Each helper accepts `string | Path` (§10.3). Outputs that are still paths
-- preserve the input tag (first path-like arg's namespace); outputs that are
-- bare fragments return a plain string. `tostring(p)` drops a Path to a string.
relay.path.join(elem...)       -> string|Path  -- join + clean: empties skipped,
                                               --   ".." resolved. Tag preserved
                                               --   (first path-like arg);
                                               --   mixed namespaces = error
relay.path.clean(p)            -> string|Path  -- collapse . / .. / //; tag kept
relay.path.dir(p)              -> string|Path  -- parent dir (Go path.Dir); tag kept
relay.path.base(p)             -> string       -- last element (Go path.Base); a
                                               --   fragment, namespace-less
relay.path.ext(p)              -> string       -- extension incl. dot (".gz"); fragment
relay.path.split(p)            -> string|Path, string  -- dir, file; dir keeps the
                                                  --   trailing slash (Go path.Split),
                                                  --   tag kept on dir, file is a
                                                  --   fragment. Distinct from
                                                  --   relay.split (a string split)
relay.path.match(pattern, name) -> boolean, string?  -- shell glob *,?,[];
                                                     --   err on bad pattern
```

`relay.replace` and `relay.render` are pure string functions with no
operator-side state, so both runtimes carry them — a `scripts/*.lua` agent
script renders the same way a phase body does ([§4.2](#42-two-lua-runtimes)).

**Config templating — `relay.render`.** Writing a config with N placeholders is
the most common deploy write, and `..` with `string.format` is a poor tool for
it once N passes two. `relay.render` is the substitution form:

```lua
local VHOST = [[
server {
  listen {{.port}};
  server_name {{.host}};
  root {{.root}};
}
]]

ctx.fs.write("/etc/nginx/sites-enabled/app.conf",
             relay.render(VHOST, { port = 8080,
                                   host = "app.example.com",
                                   root = ctx.vars.root }),
             { mode = "0644" })
```

It is Go's `text/template` **parser** with the grammar cut to one sentence: a
template is literal text and `{{.key}}` actions, nothing else. Pipelines,
functions, `if`/`range`/`with`, nested templates, variables, comments, and
whitespace-trim markers (`{{- .key}}`) are **parse errors**, not silent
no-ops. That is the entire language; there is no second page of it.

Cutting the grammar rather than embedding `text/template` whole is the same
call [§3](#3-design-principles) makes about the pattern engine. v3 removed
Lua's pattern language and shipped narrow typed helpers; re-admitting a
*larger* language through the back door — one with conditionals, its own
function namespace, and errors that only appear at render time — would trade
the gap for something worse than the gap. Widening later (a bare
`{{if .key}}`) is one deliberate decision; narrowing after scripts depend on
it is not a decision at all.

| Rule | Behavior |
|---|---|
| Grammar | text + `{{.key}}`, one field deep. `{{.a.b}}` is an error — `vars` is a flat table |
| Missing key | **error**, naming the key. Go's default renders `<no value>` into the file; a silently wrong config is not something relay ships (`missingkey=error`) |
| Unused key | allowed — one `vars` table may feed several templates |
| Value types | string, number, boolean, or a `relay.secret`/`relay.secret_file` marker. `nil`, table, function = error |
| Numbers | rendered exactly as `tostring(n)` renders them in Lua (`%.14g`), so `{{.port}}` and `.. port` can never produce two different files |
| Escaping | **none.** A value carrying a newline or a quote breaks the target's config syntax exactly as `..` would. `render` substitutes; it does not quote |
| Delimiters | `{{ }}`, or `opts.delims = { "<<", ">>" }` (two distinct non-empty strings) for a file that legitimately contains `{{` — Helm values, Prometheus rules, a Grafana dashboard |
| Parse time | every call parses. `relay validate` additionally parses the calls whose template argument is a **literal**, so a typo'd action is caught with no connection ([§9](#9-cli)) |

**A rendered string is not a sanitized string.** Feeding one into a shell-form
`run` is the same injection shape as `..`, and `relay validate`'s
static-analysis pass flags it the same way ([§9](#9-cli)). Use the argv form.

**Secrets render, and stay out of records by construction.** A
`relay.secret(...)` value substitutes its real content, and nothing further is
needed: `fs.write` never puts file bytes in a record — only length and checksum
ride the protocol ([§7.2](#72-fs)) — and dry-run prints no file diff. The one
remaining leak is a script logging its own rendered config
(`ctx.log.info(conf)`), which is the operator's `log.info(password)` to make.
Secrets in **argv** stay forbidden regardless ([§7.1](#71-run)).

**`relay.replace` is the smaller tool** — the one- or two-placeholder case, and
fixing up captured output. Plain-text `from` (no pattern engine to fall back
to), and a replacement count so `assert(n == 1)` is available where "the
placeholder was actually there" matters:

```lua
local conf, n = relay.replace(base, "__PORT__", tostring(port))
assert(n == 1, "template drift: __PORT__ not found")
```

## Appendix B — what v3 keeps from v2

v3 is a reaction to v2's *defaults*, not its *architecture*. Preserved
unchanged:

- **Typed ops over shell.** Native agent ops (checksum-verified writes, atomic
  symlink swaps, idempotent guards, in-process HTTP probes) remain the
  foundation; v3 only stops *requiring* the table form of `run`, and narrows
  "typed op" to what the agent implements itself ([§11.17](#1117-the-corerecipe-line)).
- **Execute-as-you-go.** Phase bodies run at deploy time against open
  connections; every op returns its real result; branching is ordinary Lua.
  One execution moment, not two.
- **Verified declarations.** When you assert `host{ expect=... }` or register a
  `jail{}`, the agent checks it at connect and fails loudly on mismatch. v3
  makes assertion *optional*, not *unverified*.
- **Deterministic `require`.** Rooted at the config file's directory; no CWD,
  no `LUA_PATH`, no C modules. Agent Lua has no `require`.
- **The agent-Lua boundary.** `eval` / `eval_file` ship a self-contained script
  to the target; data crosses as `args`/`return`. Bare ops are legal there
  because an agent script runs in one place by construction.
- **LuaLS stubs + `relay doc`.** Generated from Go descriptors so the editor
  machine-checks every call; `relay doc` reads the same surface in the terminal.
- **The privilege *mechanics*.** Worker vs. sudoers, drop vs. raise, `jexec`
  identity, the three error sites — all unchanged. v3 changes *what the user
  has to write*, not *what the agent does*.
- **The protobuf protocol and the agent's native implementations.** v3 is a
  Lua-surface redesign; the only protocol addition is the connect-time version
  handshake (§4.1, #46) — no existing op or field is reinterpreted, so no
  protocol change is required to ship the Lua surface itself.

Two agent-side exceptions to that last pair, both in §10.2: jail `fs.*` now
defaults to an attached helper rather than mountpoint concatenation (a new
native implementation, though the op set and its Lua surface are unchanged),
and the jail is located by a `jls` sweep plus a `match` selector rather than a
single `jls -j <jname>`.

The summary of v3 in one sentence: **v2 made the safe form mandatory; v3 makes
the simple form default and keeps the safe form one step away.**

## Appendix C — Design rationale

The body states the rules. This appendix collects the *why* — the rejected
alternatives each decision argues against — in one place, out of the reading
path.

**`user` and not `ssh_user` + `deploy_user`.** In the common case the ssh
user and the acting user are the same person. v2 had three overlapping fields;
v3 has one, with per-op `as` to override. A host whose acting identity differs
from its ssh user uses `sudo` ([§8](#8-privilege-the-common-case)) or per-op
`as`.

**`vars{}` and not `app{}`.** v2 / v3-rc had `app{}` hardcode the capistrano
release shape (`ctx.paths.{release,current,shared,…}`) and verbs
(`ctx.release.*`) into `ctx` — one strategy privileged, the shape frozen.
`vars{}` is generic key/value with per-target resolution; the capistrano shape
lives in a recipe ([§11.14](#1114-a-deploy-recipe-plain-require)), where you
can change any line.

**Single-target inference is not v1's inference.** v1 inferred scope from an
absent field — silent and open-ended. v3's single-target inference is fenced:
it resolves to the *sole* declared target or errors. The simple path stays the
default path; the moment a second target appears, the rule turns explicit.

**Split `as` from `escalate`.** A field named `sudo` whose value is an
identity (`sudo = "postgres"`) conflates a tool with an identity — "sudo is
postgres" is nonsense — and leaves no way to say "I have sudo but default to
myself." On a shared host where `deploy` runs most ops as `deploy` and needs
root only occasionally, `sudo = true` would force root as the default and push
you to add `as = "deploy"` per non-root op — inverted repetition.
`escalate = "sudo"` with no `as` says exactly "default to myself, escalate on
demand" (per-op `as = "root"` where needed).

**Not v2's "escalation requires the word."** v2 made each call site repeat
`as_user = "root"` so a reader could grep escalation at the op. v3 moves the
*default* to the host (one declaration, greppable) and keeps *overrides* at the
op (still greppable, still logged). The reader still sees every root
touchpoint — in the host block and in any `as =` override — without twenty
copies of the same literal.

**In-process, not shelling out, is what makes an op an op.** v2 grew core
modules by usefulness, which has no stopping condition: `pkg`, `git`,
`service`, and eventually every tool anyone deploys with. v3 draws the line at
implementation rather than usefulness — the agent's own syscalls and Go
libraries are ops; anything that spawns someone else's binary is a Lua module
you can read ([§11.17](#1117-the-corerecipe-line)).

The line is not tidiness. A core op over a foreign tool has to bake that tool's
policy, and bakes it where nobody can see or change it: apt's flags, git's
merge strategy, whether `enable` also starts the service. v2's `service.*` is
the clearest case. It presented one verb set over systemd and rc.d, and the
verbs were not the same operation — `enable` started the service on systemd and
only wrote a boot flag on rc.d; `state` was documented as not portable;
`enabled` was `nil` on inits with no such concept; `{ user = true }` existed
only on systemd. Four leaks in one op, all of them the same leak: an
abstraction over things that do not agree.

Splitting it into `recipe/systemd.lua` and `recipe/rcd.lua` lets each be honest,
and `recipe/service.lua` is where an operator decides what the disagreeing
verbs mean for their fleet. That is the same trade `pkg` and `git` made, and it
costs the same thing: one `require`, and rc.d's `state` gets coarser than Go
could have made it, because a recipe cannot parse an rc.d status line without a
pattern engine. Worth it — the alternative is a portable-looking op that is not
portable, which is worse than an honest one that admits where it splits.

**Two jail `fs` modes, not one.** v2 had exactly one: prefix the jail path with
the mountpoint and let the host kernel resolve it. That is not a confinement
boundary. Every component below the mountpoint is writable from inside the
jail, so a symlink planted at any of them redirects the write — and since the
op runs with the agent's host identity, a root agent following one writes
anywhere on the host. The jail's root reaches the host's root, through the
supported spelling, with no exploit beyond `ln -s`. Nor is it merely a security
problem: absolute symlinks *inside* the jail resolve against the host's `/`, so
the release layout every deploy uses (`current -> /opt/app/releases/…`) reads
the wrong file even with nobody attacking.

Attaching fixes both by not doing path arithmetic at all — `jail_attach(2)`,
then ordinary `fs` code, with the kernel resolving exactly as it would for a
process in the jail. It also fixes the quieter mismatch: `owner = "www"`
resolves against the jail's passwd, not the host's, which is what the caller
meant.

But attaching is root-only, and a real class of fleets has no root anywhere —
the deploy user exists on both sides with the same uid (jails share the host's
UID space), owns its own files through the mountpoint, and holds a few narrow
sudoers rules for the handful of commands that need more. Deleting mountpoint
mode would delete that fleet's deploy. So both modes ship, `"attach"` is the
default, and `"mountpoint"` has to be typed — the unsafe-on-root form is
reachable, but only deliberately, and its three differences (host passwd,
host-side symlink resolution, no confinement) are stated in the body rather
than discovered later. Rejected alternative: keep one mode and harden it with
`O_RESOLVE_BENEATH`. It rejects absolute symlinks outright, so the release
layout stops working; keeping it means emulating `chroot` path resolution in
userspace, which is reimplementing the kernel's namei — and the passwd
mismatch survives anyway.
